# LungfishCLI

Line numbers were checked at commit a0eec8b32. When a line has moved, search for the named symbol.

## Purpose

The `lungfish-cli` command tree, built on swift-argument-parser. Every GUI operation has a CLI command that reproduces it (CLI parity), and the app runs many operations by spawning this binary. Commands parse options, materialize inputs, call a LungfishWorkflow pipeline and report progress. Scientific logic belongs in LungfishWorkflow, not in a command.

## Allowed imports

LungfishCore, LungfishIO, LungfishWorkflow and ArgumentParser. Never LungfishKit, a leaf UI module, LungfishApp, AppKit or SwiftUI (memory file project_module_architecture.md).

The command files live in Sources/LungfishCLI/Commands. Find a subcommand by its type name. Most FASTQ, bundle, fetch and workflow subcommands have a file named for their type, such as FastqTrimSubcommand.swift. A type that uses a file-private helper stays beside the helper. So FastqCommand.swift keeps FastqDemultiplexSubcommand and FastqScoutSubcommand, FetchCommand.swift keeps NCBISubcommand and ENAFastaSubcommand, and MetadataCommand.swift keeps MetadataSetSubcommand and MetadataImportSubcommand.

## Where a Kraken2 run starts in the CLI

`lungfish-cli kraken2 classify` is `ClassifyCommand` (Commands/ClassifyCommand.swift line 31), the one subcommand of the `Kraken2Command` group (Commands/Kraken2Command.swift) that `LungfishCLI` lists beside `esviritu` and `taxtriage`. `lungfish-cli conda classify` is the same type, still registered as a `conda` subcommand in Commands/CondaCommand.swift line 41. Both spellings register `ClassifyCommand` itself and never a wrapper, because tests, `RecordedCLICommand` among them, cast a parsed root to it, and `Kraken2ClassifyCommandTests` pins that they parse to equal options. A run records the command line as typed, so a `kraken2 classify` run records that spelling. A run inside another process, such as a test's, records the `kraken2 classify` command its parsed options spell (`canonicalArguments()` in Commands/ClassifyCommand+CommandLine.swift). Since Phase 2.7 (decision E11) the Kraken2 rows the classification wizard starts, `ClassificationCLIInvocationBuilder` and the batch replay command name `kraken2 classify`. The FASTQ operations dialog writes no classify command, because the classification, EsViritu and TaxTriage wizards it embeds start their runs through their own routes and record their own commands (decision D1 of Phase 2.8). Since Phase 2.10 its `FASTQOperationLaunchRequest` (Sources/LungfishApp/Views/FASTQ/FASTQOperationDialogState.swift) has no classify case, and a wizard's Run sets the dialog's `embeddedClassifierCapture` in its place. The `run` of `ClassifyCommand` (line 159) calls `execute(adjustServices:)` (line 167), which builds `Kraken2AnalysisRunTool` (Sources/LungfishWorkflow/Metagenomics/Kraken2AnalysisRunTool.swift, with the unit in Kraken2AnalysisRunTool+Unit.swift and the finalize in Kraken2AnalysisRunTool+Finalize.swift) and runs it through `AnalysisRunExecutor` with `Kraken2ResultIndexer` (Commands/ClassifyCommand+Index.swift line 17). The unit materializes virtual FASTQ through `FASTQCLIMaterializer` into `<root>/.lungfish-classify-inputs/`, which the result folder keeps (decision E3), plans one input under `--read-format auto`, or a `--paired` pair with `--unpaired` files, through `KrakenReadSetPlanner` (`Kraken2RunRequest.planReadSet` in Sources/LungfishWorkflow/Metagenomics/Kraken2RunRequest+Planning.swift line 115, which `planReadSet` in Commands/ClassifyCommand+ReadSets.swift line 78 calls), then runs `ClassificationPipeline.shared`. EsViritu is `lungfish-cli esviritu detect` (`EsVirituCommand.DetectSubcommand`, Commands/EsVirituCommand.swift line 73), which runs `EsVirituAnalysisRunTool` through the same executor and plans a bundle in Commands/EsVirituCommand+ReadSets.swift. Mapping is `lungfish-cli map` (Commands/MapCommand.swift, which resolves its inputs through `MappingInputResolver`, the call the Map Reads window makes, and calls `ManagedMappingPipeline`). `taxtriage run` plans each sample in Commands/TaxTriageCommand+ReadSets.swift, and `assemble` resolves its reads through `AssemblyReadSetResolution` in Commands/AssembleCommand.swift, with its read-layout helpers in Commands/AssembleCommand+ReadSets.swift. Line numbers in this section were checked at commit 3b7460c33.

## Where a GATK run starts in the CLI

`lungfish-cli gatk` is `GATKCLICommand` (Commands/GATKCommand.swift line 9), a group of ten subcommands. Each subcommand builds a `GATKPipelineExecutionRequest` (Sources/LungfishWorkflow/Variants/GATKPipelineExecutionRequest.swift) and calls `runOrPreview` (line 37). Without `--execute`, or with `--dry-run`, it prints the GATK commands and runs nothing. With `--execute` it runs `GATKPipelineExecutor` (Sources/LungfishWorkflow/Variants/GATKPipelineExecutor.swift) on the request that `recorded(_:arguments:)` returns (Commands/GATKCommand+CommandLine.swift line 24), and the record names that `lungfish-cli` command as its `argv` and `reproducibleCommand`. Each step keeps the GATK argv it ran. The command is the line this process was started with when that line names `gatk <subcommand>`, as typed, else the subcommand's `canonicalArguments()`, which writes every option that has a default with its value. `GATKCLIExecutableSubcommand` (line 96) requires `canonicalArguments()`, and `GATKCommandRecordedCommandLineTests` fails until a new subcommand has a case there. `variants call --caller gatk` (Commands/VariantsCommand+CallGATK.swift) runs HaplotypeCaller with the same executor, attaches the VCF into `variants/gatk/` with `GATKBundleVariantAttachmentService` and names the `lungfish-cli` command in both records. The app's GATK row runs that command on `CLIVariantCallingRunner` and records it, and the app has no other GATK route since Phase 2.12. Line numbers in this section were checked at commit 2e327ec2a.

## Where an IQ-TREE run starts in the CLI

`lungfish-cli tree infer iqtree` is `TreeCommand.InferIQTreeSubcommand` (Commands/TreeInferIQTreeCommand.swift line 8, `run` at line 90), registered in Commands/TreeCommand.swift. Its helpers sit in two files beside it. Commands/TreeInferIQTreeStaging.swift stages the in-scope rows under tip IDs t0001 and onward (`stageIQTreeRows`, line 52), writes artifacts/iqtree/tip-map.tsv (`writeIQTreeTipMap`, line 96), finds the outgroup clade for the reroot (`iqtreeOutgroupRootNodeID`, line 109) and reads the drawn seed from run.log (`parseIQTreeSeed`, line 129). Commands/TreeInferIQTreeInference.swift records the support labels in IQ-TREE's order (`iqtreeSupportLabels`, line 6) and builds the manifest's inference summary from run.iqtree through `IQTreeReportParser` (`iqtreeInferenceSummary`, line 50). Reserved `--extra-args` flags, the model-selection-only rule and the codon frame rule come from `IQTreeOptionRules` in Sources/LungfishIO/Bundles/IQTreeOptionRules.swift, shared with the Build Tree dialog. Line numbers in this section were checked at commit 58370dd8e.

## What each leaf writes for a machine reader

Every leaf command has one row in `CLIEventContractTable`. The row says whether the leaf emits events, prints one JSON result, prints a private stream shape that a later sub-phase retires, or prints human text only. A command that is added, renamed or removed edits its row in the same commit, or `CLIEventContractCoverageTests` fails. A new private stream shape is a `.legacy` row with the sub-phase that retires it, and the test that lists the shapes left fails until its list says so too. A leaf that emits events also needs a transcript under Tests/Fixtures/cli-events/commands, and docs/formats/cli-events.md describes the table.

## Contracts this module owns

- The argv a command accepts must match what the GUI records as its cliCommand, so a copied command reruns the same analysis.
- `tree infer iqtree` replays byte for byte only with `--threads 1` and a fixed `--seed`. Without `--threads` it passes `-T AUTO`, and a multithreaded IQ-TREE run gives slightly different branch lengths each time (docs/contracts/CLI-EQUIVALENCE.md, Tests/LungfishAppTests/IQTreeInferenceReplayTests.swift).
- Commands the app drives through `CLISubprocessTransport` emit `CLIEvent` lines (Sources/LungfishWorkflow/CLIEvents/CLIEvent.swift). The app reads them from a pipe, where `print` buffers, so write each event line with `printEventLine` (Output/CLIOutput.swift), which flushes it. An unflushed event reaches the Operations Panel only when the command exits. `LungfishCLIMain` installs `CLITerminationSignals` (Support/CLITerminationSignals.swift) before any command runs, so SIGINT, SIGTERM and SIGHUP stop every tool tree in `NativeProcessRegistry` and the CLI ends by that signal. `import fastq`, `workflow run`, `kraken2 classify` (also spelled `conda classify`), `esviritu detect`, `variants call` (every caller), `esviritu export detections`, `blast export table`, `kraken2 export table`, `nao-mgs export table`, `nvd export contigs`, `fastq export sample-barcodes`, `fastq export reads`, `metadata export --output`, `provenance export`, `taxtriage export organism-matrix`, `taxtriage export batch-report`, `taxtriage export results` and `extract sequence` with no region turn the first SIGTERM into task cancellation through `SIGTERMCancellation` so their cleanup runs. `provenance export` calls `runCancellingOnSIGTERM` itself, since its `--format` names the report format and it has no `GlobalOptions`. It builds the report in a hidden sibling of the output folder, reaches `ViewerExportLeaf.checkpointAfterStaging` and publishes only after it, so a cancel exits 125 and leaves the output folder as it was. A cancelled `workflow run` exits 125 (`CLIExitCode.cancelled`), and a cancelled `kraken2 classify` or `esviritu detect` exits 125 through `AnalysisRunExecutor` (`AnalysisRunExitCode.cancelled`). A cancelled `variants call` exits 125 after it writes a `cancelled` record under `<bundle>/provenance/cancelled`, through `runCancellingOnSIGTERM`. Every viewer export leaf runs under `ViewerExportLeaf.run` in Support/ViewerExportLeaf.swift, which exits 3 on a refusal, 64 on a failure and 125 on a cancel and writes no output and no record in any of the three. A new long-running command that owns child tools follows `docs/contracts/RUNNING-A-TOOL.md`.
- The `build-db kraken2`, `build-db esviritu` and `build-db taxtriage` cores, `buildDatabase(in:options:...)` in Commands/BuildDbCommand+Kraken2Core.swift, Commands/BuildDbCommand+EsVirituCore.swift and Commands/BuildDbCommand+TaxTriageCore.swift, stop when the task that runs them is cancelled. The cancel comes from the analysis run executor's index step (`Kraken2ResultIndexer`, `EsVirituResultIndexing` and `TaxTriageResultIndexer`) under a cancelled `kraken2 classify`, `esviritu detect` or `taxtriage run`, because a standalone `build-db` has no `SIGTERMCancellation` and ends by the signal. A core checks before each sample folder it reads or cleans up, before it writes the database, before the EsViritu BAM move, after the samtools pass and before it writes the record, and throws `CancellationError` at the first check after the cancel. It puts back the database of an earlier build and writes no record of a failed build, and the executor ends the run `cancelled` without the finalize's outputs or steps (decision E5 of Phase 2.7). A cancel undoes no step that finished before it. Kraken2 folders the cleanup compacted stay compacted, BAMs the build moved to `bams` or that markdup rewrote stay so, `_temp` folders the cleanup removed stay removed, and no record names those steps. A cancel after the check before the record is not seen, so the build completes and leaves its database and the database's sidecar, which the cancelled run's root record does not name. Tests/LungfishCLITests/BuildDbCancellationTests.swift pins the checks, and the `build-db taxtriage` core makes the same checks before each sample folder it reads or cleans up. Its cleanup takes two forms (decision T5 of Phase 2.8). The command's removes `top/` before the record, as the app's in-process route has always had it, and the executor's keeps `top/`, runs after the record and returns one removal step (Tests/LungfishCLITests/BuildDbTaxTriageIndexTests.swift). The `build-db kraken2` cleanup leaves a sample folder as it is, with one information line and no step for it in the build's record, when the folder's own record is one `build-db` may not replace (`BuildDbCommand.mayReplaceProvenance`, the classifier's) and names `classification.kraken`, `classification-result.json` or `classification.kraken.idx.sqlite`, because the compaction would remove the per-read output and rewrite the result sidecar while that record states their digests (2.10 FXA2, Tests/LungfishCLITests/BuildDbRecordedRemovalTests.swift).
- Every scientific top-level command has a provenance policy entry in Sources/LungfishWorkflow/Provenance/ScientificProvenancePolicy.swift, checked by ScientificCLIProvenanceCoverageTests. `cliCommand(path:)` takes the exact row of `cliCommandPathPolicies`, else the row of the path's longest registered prefix, else the entry of the group that starts the path, and never the entry of its last component (2.7 E16). `kraken2 classify` and `conda classify` hold one exact row, and a leaf of `conda`, `debug`, `demo` or `storage` holds no entry unless a row names it. Tests/LungfishCLITests/ScientificProvenancePolicyLeafTests.swift walks `LungfishCLI.configuration` and pins the entry of every registered leaf, hidden ones included, so a new leaf needs its row there in the commit that registers it, and `testTheHelpIndexListsExactlyTheRegisteredLeaves` fails until Tests/Fixtures/golden/cli-help is recaptured. A leaf that resolves to no entry needs a reason in `ScientificCLIProvenanceCoverageTests.recordsNothing`, by its own path or by its command, as `conda run` and `demo fetch` have (2.8 P6). The entries set no field a run records, since nothing outside tests reads them.
- Managed tools are resolved through `WorkflowEngineLaunch.resolve`, never `/usr/bin/env <tool>` (memory file project_cli_subprocess_bare_path.md).

## Tests

Target LungfishCLITests in Tests/LungfishCLITests. Run only it with `swift test --skip-update --filter LungfishCLITests`. Process-fork suites (CLIExitCodeProcessTests and others) run in the integration tier, not the unit tier (see Tests/AGENTS.md).
