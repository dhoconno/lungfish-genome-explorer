# Dependency set 2026.2

Dependency set `2026.2`, dated 2026-08-18, replaces `2026.1`. It moves 31
pinned tools, pipelines, databases and bootstrap components, refreshes the
SwiftPM graph, and carries two product fixes that the sweep's own verification
turned up.

Full verification record, including every command and its output:
`docs/reports/2026-08-18-dependency-sweep-2026.2-results.md`.

## What users will notice

### Optional tools may reinstall on the first launch after updating

Reconciliation compares full conda build strings, not just versions, so a tool
whose version did not change can still be reinstalled when upstream republished
it against a newer interpreter or dependency set. On a machine sitting at
2026.1 with the full toolset installed, five environments reinstall for a build
change alone at an unchanged version: cutadapt, flye, lofreq, whatshap and
pysam. Nothing about those tools' behavior changes.

The complete plan for such a machine is in the next section. Only tools already
installed are affected. A tool never installed stays uninstalled.

### Kraken2 20260626 indexes rename the SARS-CoV-2 species

NCBI renamed the species. In the 20260626 indexes the level-S row reads
`Betacoronavirus pandemicum` under taxid 3418604, and
`Severe acute respiratory syndrome coronavirus 2` (taxid 2697049) is demoted to
the S1 rank beneath it. Bracken aggregates at species level and therefore
reports the new name.

Classification itself is unaffected and the taxonomy id is carried through
unchanged by every parser. Anything that matched the old display name by text
will no longer match. Saved searches, filters and notes that name the old
species should be rechecked against taxid 3418604.

Older indexes are unaffected: 20240904 rolls the same reads up to
`Severe acute respiratory syndrome-related coronavirus`, taxid 694009.

### Bracken abundance now works on Apple Silicon

Bracken abundance estimation previously failed on every Apple Silicon install
and produced no abundance table. The only arm64-installable bioconda package
ships no Bracken driver, so Lungfish synthesizes a launcher around the
underlying `est_abundance.py`, and that inner script takes a different command
line than the real driver. Lungfish now detects which of the two it is talking
to, per environment, and builds the matching arguments.

Two consequences worth knowing:

- Domain-level (`D`) profiling is not available against a synthesized launcher,
  because the inner script accepts only `K,P,C,O,F,G,S`. It degrades with a
  message naming the accepted levels rather than failing obscurely. Domain is
  deliberately not silently substituted with kingdom, since the two are
  different taxa in the same report.
- A machine that has a genuine Bracken driver from another source keeps using
  it unchanged.

### New Bracken installs are built from source at v3.1

Installing or repairing the Metagenomics pack now compiles Bracken 3.1 from a
checksum-pinned source tarball over a pinned conda toolchain (Python 3.11, a C++
compiler, and OpenMP), instead of installing the driverless bioconda 1.0.0
package. A source build carries the real driver, supports domain-level
profiling, and removes both limitations described above for fresh installs. The
synthesized-launcher path remains for environments that still hold the bioconda
build, and `tools update` preserves any working Bracken environment it finds,
whether source-built by the pack, by hand, or installed from bioconda.

### A Bracken you built yourself is no longer overwritten by an update

If you built Bracken from source into the `bracken` environment, updating tools
leaves it exactly where it is. Earlier sets would have replaced it with the
pinned bioconda build.

The reason is that the arm64 bioconda package is not an improvement on a source
build. It is the only build installable on this architecture, it ships no
Bracken driver at all, and Lungfish has to synthesize a launcher around
`est_abundance.py` to use it. A source build, by contrast, carries the real
driver, supports domain-level profiling, and is typically a much newer version
(3.0.1 at the time of writing, against a pin of 1.0.0). Reinstalling over it
would leave you with strictly less than you had.

Lungfish could not see this before because a source build writes no conda
metadata. The environment therefore looked unverifiable, which reconciliation
treats as a reason to reinstall. The manifest's `bracken` entry now carries
`preserveExistingInstall`, which says: if this environment already holds every
executable the entry declares, keep it and report that you did. `lungfish-cli
tools update --plan` prints a `preserve` line for it instead of a `reinstall`
line.

This is a per-tool exception and bracken is the only tool that has it. Every
other tool still reinstalls when its provenance cannot be read, and bracken
itself still installs normally when the environment is absent, still upgrades
on a genuine version or build change, and is still reinstalled if its
executables have gone missing.

To take the pinned bioconda build deliberately, remove the environment and let
the pack reinstall it: `lungfish conda remove bracken`, then reinstall the
Metagenomics pack from Plugin Manager. With no environment on disk there is
nothing to preserve, so the pin is applied.

### Kraken2 special database builds remain unavailable on Apple Silicon

Building the SILVA and Greengenes databases needs `bracken-build`, which the
arm64 package does not ship. The build fails early and explicitly naming the
missing tool. Prebuilt Kraken2 catalog databases are unaffected.

### bwa-mem2 self-reports the wrong version

`bioconda::bwa-mem2=2.3=hda5e58c_0` prints `2.2.1` when asked for its version.
The package ships 2.3 binaries and records 2.3 correctly in its own metadata;
only the string baked into the binary is stale, and no newer arm64 build
exists. This is an upstream packaging defect with no effect on results. Version
conformance asserts this one tool against package metadata instead of its
self-report.

That is 22 environment reinstalls, one advisory database update, one bootstrap
update, and 3.62 GB to download. Seventeen are version moves (`specChanged`)
and five are build changes at an unchanged version (`buildChanged`: cutadapt,
flye, lofreq, whatshap and pysam).

Bracken is not among them. It was originally planned as a `metadataMismatch`
reinstall, because that root's environment holds a source build and so carries
no conda record of the pinned package. Applying that plan against a clone of
the root replaced a working Bracken 3.0.1 with the driverless 1.0.0 package:
`bin/` dropped from 294 files to 120, and `bracken -v` began printing
`est_abundance.py` usage. The entry now opts into `preserveExistingInstall`, so
the environment is reported and left alone.

The Kraken2 index update does not appear here because catalog database updates
are advisory and offered separately rather than forced during a tool update.

To take a Kraken2 index update: in the app, open Plugin Manager, go to the
Databases tab, and press **Update** on any row showing an "Update available"
badge. From the command line, run `lungfish conda db update <name> --yes` (for
example `lungfish conda db update Viral --yes`), or `--all` to update every
database that advertises one. Either route replaces the installed index with
the pinned build and keeps the old copy until the new one verifies.

## Verification

| tier | result |
| --- | --- |
| Tier 1, toolset conformance | GATE PASS, 189 tests, 0 failures, 0 skips, after every bump group |
| Tier 2, golden fixtures | 12 recipes / 13 outputs: 13 same, 0 different, 0 missing at set 2026.2 |
| Tier 3, live pipelines | BLOCKED on this machine |
| Full test suite | 13433 executed, 1 failure, environmental and confirmed by isolated rerun |
| Python tooling suite | 411 tests, OK |

Tier 2 recorded two accepted differences against the 2026.1 goldens. deacon
0.16.0 adds one additive key, `check_pairs`, to its filter summary with every
numeric field unchanged. The megahit recipe now runs single threaded, because
at two threads its contig count flipped with machine load and could fail the
gate for a reason unrelated to any dependency change; the recorded numbers are
unchanged.

Still outstanding, none of it blocking the manifest itself:

- **Tier 3 is blocked on this machine.** Neither Apple Containers nor a running
  Docker daemon is available, so the TaxTriage pipeline cannot run, and the
  EsViritu database is not provisioned into the isolated verify root. The
  TaxTriage v3.3.8 report schema is therefore unverified against a live run.
- **savont end to end on real ONT data is pending manual verification.** The
  0.6.3 bump is covered by a CLI contract test asserting every flag Lungfish
  emits still exists, and by require-mode conformance, but a full-length MHC
  genotyping run on real reads needs the user's own data.
- **GUI walkthroughs are pending.** The fresh-install and upgrade walkthroughs
  need Computer Use access. This now includes the Plugin Manager Databases tab's
  new **Update** button, which is covered by unit tests but has never been
  rendered.
- **The CI toolset-conformance dispatch is pending a branch push.**

One caveat worth carrying forward: the kraken2 golden is byte identical to
2026.1 despite the index moving to 20260626, because that recipe's three
synthetic reads are all unclassified and it never touches the index taxonomy.
The unchanged golden is not evidence that the new taxonomy was verified. The
species rename is covered by `Kraken2BrackenConformanceTests`, which matches on
taxonomy id.

- The 20260626 Kraken2 indexes follow NCBI in renaming the SARS-CoV-2 species
