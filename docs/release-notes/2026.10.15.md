# Lungfish 2026.10.15

Channel: Preview

Previous versioned release: v2026.10.14

Stable baseline: v2026.9.78

Dependency set: 2026.2

Preview builds are under rapid iterative development. Features may be incomplete, change quickly, or require additional feedback.

This release carries Phases 2.7 and 2.8, which shipped no Preview of their own. Lungfish Genome Explorer (LGE) now starts Kraken2 and EsViritu runs from the Tools > Classification menu through `lungfish-cli kraken2 classify` and `lungfish-cli esviritu detect`, so a new result opens at once and its Provenance tab shows the command's own record. A failed or cancelled run keeps its folder for review, a degraded Bracken profile and a negative control no longer fail a Kraken2 run, and the Provenance tab says how a run ended. Cancelling a TaxTriage run now stops Nextflow and its tasks on the Mac, the TaxTriage row keeps its bar from moving back, and a TaxTriage record states its database, its Nextflow version, its ignored task failures and the reads it keeps. Kraken2 and EsViritu records name the files they remove and keep, the Provenance tab gains a Step Tools row, and Methods Section gives each tool of a pipe its own version. `lungfish-cli genotype export-labkey` writes a stable `cohort_id` for each smart cohort, a reverse-strand gene that a sequence end clips keeps its reading frame, and Extract Reads works on a one-folder EsViritu result. From this release on, LGE is signed with a Developer ID certificate from Apple's G2 certificate authority. The GUI walk of this release ran as the locked-screen substitute, so the owner check list under Checks still to run blocks a Stable promotion.

## Classification

**Classifiers through the command line.** Kraken2 and EsViritu runs that you start from the Tools > Classification menu now run through `lungfish-cli kraken2 classify` and `lungfish-cli esviritu detect`, the commands that you can run in a terminal, and Copy CLI Command copies the command that ran. The rows, their labels and the results look as before, apart from the lines described under Classifier rows. The command builds the viewer database as part of the run, so a new Kraken2 result opens at once, where it built the database the first time you selected it. A result made by an earlier release still builds its database on first selection. Until 2.9 a hidden setting brings back the in-process route, for example while you report a problem. In Terminal, `defaults write com.lungfish.browser.preview ClassifierLaunchRoute.kraken2.single legacy` does it for single Kraken2 runs, and the keys `ClassifierLaunchRoute.kraken2.batch`, `ClassifierLaunchRoute.esviritu.single` and `ClassifierLaunchRoute.esviritu.batch` do it for the other runs. The app reads the key each time a run starts, and `defaults delete` with the same key returns to the command line. A run started with no project open still runs in process.

**The record of an app run.** The record of a Kraken2 or EsViritu result that the app makes is now the command's record. Its Provenance tab shows the Workflow `lungfish.classify` for Kraken2, where it showed `Metagenomics Classification`, `Metagenomics Profiling` or `Classification Batch`, and `lungfish.esviritu.detect` for EsViritu, where it showed `EsViritu Batch`. Tool reads `lungfish-cli` and its version, where it named the first step the app ran, such as `Lungfish EsViritu Batch`, and Executable reads `<external>/lungfish-cli`. The steps, inputs and outputs are the ones the command ran and wrote, the viewer database build among them. In the Inspector's Analyses section, the entry of an EsViritu run on single-end reads lists `Paired-end: no` where it listed `Input read layout: single_end`.

**Failed and cancelled runs.** A Kraken2 or EsViritu run that fails or that you cancel now keeps its result folder, hidden from the sidebar, with its record, where a failed or cancelled single run deleted its folder. The next time you open the project the Operations Panel lists the folder as a Failed run or Cancelled run with its size on disk, and Remove Partial Output deletes it after a confirmation. A cancel gives `lungfish-cli` 6 seconds to record `cancelled` with exit status 125 before the app stops it, and a cancel that arrives while the run is still being planned leaves no folder.

**A degraded Bracken profile.** A Kraken2 run whose Bracken profile cannot be made now ends with exit status 0, where `kraken2 classify` and `conda classify` ended with 64 and wrote a failed record. The record says `completed` and marks the profile degraded with its reason, the output holds a warning line that names the reason, and the Operations Panel row still reads Completed with Warnings. The help of `kraken2 classify` now says that a Bracken profile that cannot be made leaves the classification complete with a warning and exit 0.

**Negative controls.** A Kraken2 run on a sample with nothing classified, such as a negative control, now completes and records why no Bracken profile was made, where it failed with an empty report and the app removed the folder. With a Bracken profile requested the row reads Completed with Warnings, and the result opens with every read unclassified. The sunburst of such a result still reads No classification data while the table lists the unclassified reads.

**The command spelling.** The app now shows Kraken2 runs from the Tools > Classification menu as `lungfish-cli kraken2 classify`, where 2026.10.14 showed `conda classify`. The record of such a run names `kraken2 classify` too. `conda classify` stays registered, and a command recorded with it still replays.

**EsViritu results.** EsViritu results now keep the coverage windows and the assembly summary tables of each sample, a few kilobytes each, which the database build used to delete, and the move of each sample's BAM file is a recorded step. When you run `lungfish-cli esviritu detect` with `--project` or `--batch`, a sample whose id holds characters other than letters, digits, `_` and `-`, such as `Patient.07`, is named `Patient_07` in its folder, its tables, the summary, the manifest and `esviritu.sqlite`. Before, the viewer's index dropped every detection of such a sample.

**Kept copies of virtual reads.** A sample whose reads come from a virtual bundle, such as a barcode bundle from demultiplexing, runs from a copy of its reads that stays in a hidden folder of the result, `.lungfish-esviritu-inputs` for EsViritu and `.lungfish-classify-inputs` for Kraken2, so the record names files that exist. An EsViritu result on a virtual bundle grows by the uncompressed size of those reads, where 2026.10.14 deleted the copy when the run ended. A Kraken2 result keeps the copy that 2026.10.14 already kept, which moves from `.lungfish-provenance/intermediates/classification-inputs` to `.lungfish-classify-inputs`, so its size does not change, except that a run on reads that hold pairs and single reads now also keeps the header-only mate and any compression copy that it staged beside each single-read file. A TaxTriage result keeps its own copy in `.lungfish-taxtriage-inputs`, as the TaxTriage section describes. LGE keeps all three folders with the result and builds no cleanup for them.

**Sample order.** When Kraken2 or EsViritu runs on several files at once, LGE now orders the samples, and numbers files that share a name, in English alphabetical order on every Mac. On a Mac set to another language, a batch can list its samples, and number files that share a name, in a different order than 2026.10.14 did. In Swedish, for example, a name that starts with ä moves from after z to beside a.

**Results from later releases.** A Kraken2 result now opens even when its Bracken profile stopped for a reason this release does not know. Before, the whole result failed to load unless the reason was one of seven. No release writes such a reason yet, so every result made by a released build opens as it did. A later release is planned to write a new reason, and 2026.10.14 and earlier will not open those results. This release shows an unknown reason as the word the result stores, and only when the result holds no message of its own.

**Extracting reads from a one-folder EsViritu result.** Extract Reads… on an EsViritu result that keeps its BAM files in a `bams` folder beside its database, the one-folder layout that an import writes, ended with "No BAM file found for sample" and the sample's name. LGE now tries the BAM path that the result's database records for the sample first, joined to the result folder, and uses it only when it names an existing file inside that folder. A path with `..`, an absolute path outside the folder and a link that leaves it still fall back to the older lookups, which end in the same message when they find nothing. `lungfish-cli extract reads --by-classifier` and the read count estimate of the extraction dialog follow the same rule.

## TaxTriage

**Cancelling TaxTriage.** Cancelling a TaxTriage run from its row in the Operations Panel (Cmd-Shift-P) now stops Nextflow and every task it started on this Mac. LGE sends a stop signal to the whole process tree and ends what is left after 4 seconds, so the row reads `Cancelling...` for about 4 to 5 seconds and then reads Cancelled with the detail `Cancelled by user`. No alert appears and the sidebar gains no result. Before, a cancel stopped nothing. The row read Cancelled while Nextflow ran on, the run's record said `failed` with exit status -1, and LGE deleted Nextflow's `work/` folder under the running pipeline. The cancelled run's folder stays hidden with its `nextflow.log`, and its record now says `cancelled` with exit status 125. In a run of several samples, a cancel ends the run at the next sample, records the cancel and writes no result for the batch. A cancel that arrives while the run collects its output files wins, and nothing more is written into the source bundles or their manifests.

**The TaxTriage row.** The row `TaxTriage (N samples)` no longer drops its bar from 100 percent to 95 percent when `Building TaxTriage database…` starts, and the bar stays at 100 percent. One failed sample now reads `1 failed sample (1 report)` where it read `1 failed samples (1 reports)`, and the log line reads `1 TaxTriage sample failed` followed by the sample and its reason. A run that ignored errored tasks logs one warning line for each cause, where it logged an information paragraph, a warning paragraph and a warning headline with the counts. The warning, the row's detail and the paragraph that `lungfish-cli taxtriage run` prints begin `Some TaxTriage tasks failed` where they began `TaxTriage completed with errors`, and the command closes with `TaxTriage completed with warnings in 12.3s` where it closed with `TaxTriage completed with errors in 12.3s`. The last progress message of every run is `TaxTriage pipeline complete`, which the viewer's overlay shows while the database builds, and a run with errored tasks no longer sends the whole paragraph there or to the command's last progress line. The label Completed with Warnings and the detail of a clean run are unchanged. After a cancel, a run over several source bundles no longer writes a `taxtriage-ref-<run>.json` file into each bundle, and the row's log carries no `Database build failed` warning. A database build that fails without a cancel still logs it. For one affected sample, the result summary that the command prints reads `Ignored sample failures: 1 across 1 sample`.

**TaxTriage records.** The record of a TaxTriage sample now names its tool `taxtriage` where it named `TaxTriage`, and it records the Kraken2 database that the run used, the Nextflow version and each task that TaxTriage ignored. The database is recorded with its path, the sizes of `hash.k2d`, `opts.k2d` and `taxo.k2d`, an identity status of unpinned because nothing is hashed, and its catalog entry, source URL and source policy from the database's install receipt when that install ended with status 0. The Nextflow version comes from the banner in `nextflow.log`. Each ignored task is one line in the error output of the TaxTriage step that begins `Warning: TaxTriage ignored the failure of` and names the task, the sample, the exit status, the attempts when there were several and the key line of the task's error output when the log held one. The run still records `completed` with exit status 0. The record of a run of several samples holds the same lines on each sample's `taxtriage` step. Records made by earlier releases keep the name `TaxTriage`.

**Kept inputs.** A TaxTriage result now keeps a hidden `.lungfish-taxtriage-inputs` folder with the joined or materialized reads that its record names, from the app and from `taxtriage run`. The folder can be as large as the sample. `taxtriage run` no longer removes it, so it stays with the output folder, a failed run's included. The app writes these reads into the result's own folder, where it wrote them into a project temporary folder that it removed when the run ended.

Known limit. A cancel stops the process tree on this Mac only. A Docker container that Nextflow started may keep running until it finishes, so run `docker ps` after a cancel to see whether one is left. A cancel that arrives while LGE waits for Docker Desktop to start can take longer than the 10 seconds the Operations Panel allows. The row is then forced to Cancelled with a warning that the worker did not respond, and the bundle stays locked until the worker exits. That wait is not fixed in this release.

Known limit. Copy CLI Command on the row of a one-sample TaxTriage run copies a `taxtriage run` command whose `--output` is the app's own result folder, so running it writes into that folder again. A row for several samples offers no command. The recorded command of a TaxTriage row changes in a later release.

Known limit. When you run `lungfish-cli taxtriage run` on several samples, one Nextflow run processes them all, and the app runs one Nextflow run for each sample. Nobody has compared the results of the two ways yet, and a comparison on real tools is planned for a later release.

Known limit. The record that the app writes for a TaxTriage sample still names `count/`, `fastp/` and `top/` files that LGE removes after the database build, so some names in it point at files that are gone. A later release settles that.

## The Operations Panel

**Classifier rows.** The labels and results of Kraken2 and EsViritu rows are unchanged, and some of their lines change. A Kraken2 batch logs every pipeline message, and a failed sample's reason at error. A result that builds a viewer database also logs the builder's lines, such as `Parsed N classification rows…` and `Built database at … with N rows`. Every EsViritu run, of one sample or several, shows `Writing the EsViritu batch summary…` before its database line, as the row's detail, in the log and in the viewer's progress overlay. An EsViritu batch logs a failed sample's last log lines before the reason, with lines over 400 characters cut and leading lines dropped past 4,096 bytes. A Kraken2 run whose Bracken profile is degraded also logs the reason as an information line beside its warning line. A run on a virtual bundle shows one materialization line, `Materializing pointer dataset...`, where it also showed `Materializing virtual FASTQ...` before it and `Materialization complete` after it. The progress bar never moves back, so an EsViritu stage that starts again leaves the bar where it was. A completed run whose result the app cannot read back reads Completed with Warnings and logs one warning line.

## The Provenance tab and records

**The Provenance tab says how a run ended.** Run Summary has a Run Status row that reads Completed, Failed, Cancelled or Not finished, or Not recorded for an older record that never said. The status line under the section title now reads Complete record or Incomplete record, because it judges the record and not the run, so a cancelled run can have a complete record. A record that cannot hold a process ID, such as one written since 2026.10.14 or an alignment or tree record written by this release, shows no Process ID row instead of Not recorded.

**Alignment and tree records.** Alignment, tree and genotype workbook export records written by this release state how the run ended, name the app or CLI as `<external>/<name>` and record no process ID or inherited conda value. An alignment or tree made by this release now reads Complete record in the Provenance tab, where 2026.10.14 showed Older record format, and can export as a script. One made by an earlier release still reads Older record format.

**Words in the Provenance tab.** The status line reads `Invalid record` and `Stale record` where it read `Invalid` and `Stale`, and the Warnings titles read Incomplete record, Invalid record and Stale record where they read Incomplete provenance, Invalid provenance and Stale provenance. Rest the pointer on the status line and a tooltip reads "The status line says whether the record holds every fact LGE expects. Run Status says how the run ended." VoiceOver reads the same help. A verified record that states no status now reads Run Status Not recorded, where the tab showed Completed. A step's Command names a file inside a project whose folder name holds a space the way Files & Outputs does, as `Inputs/reads.fastq`, and the project folder alone reads in quotes. Complete record, Incomplete record, Older record format, Missing provenance and No provenance required read as before.

**Step Tools.** When the Tool row of Run Summary reads `lungfish-cli`, as it does for a Kraken2 or EsViritu result made through the command line route, a Step Tools row follows it. It names each program other than LGE that the run used, with the version from that step's own record, such as `kraken2 v2.17.1, gzip system`. LGE's own steps, such as `lungfish-cli fastq materialize` and `lungfish-kraken2-index`, stay out of the row, and Lineage still lists every step. A step that recorded no version adds its tool alone, and the row never reads the tool lock. The Copy text of the section carries the row too.

**Records name the files they keep.** A Kraken2 or EsViritu record used to name files that the run, or the database build after it, then deleted or replaced, with no step that said so. Each removal now has a step that names what it removed, with the digest and size that an earlier step recorded, and Lineage lists it. A Kraken2 run records `Lungfish Kraken2 Output Removal` after `gzip` for the raw per-read output, and `Lungfish Classification Interleaved Split Removal` for the two halves of an interleaved file, which are scratch. The kraken2 step names the durable interleaved file and not the halves. `build-db kraken2` records `lungfish-kraken2-index` and `gzip` steps for its compaction and one `Lungfish Kraken2 Output Removal` for each raw output and old index it removed. `build-db esviritu` records `Lungfish EsViritu BAM Relocation Source Removal` for the BAM and index that it moved out of `_temp/`, and `Lungfish Markdup Replacement` for the BAM that markdup replaced, with the digest from before the markdup. A Kraken2 run on reads that hold pairs and single reads keeps the header-only mate and any compression copy that it staged beside each single-read file, in `.lungfish-classify-inputs`, and the record of a Kraken2 batch names the staged files that each sample kept.

**Grouped FASTQ results.** The record of a grouped result from the FASTQ/FASTA Operations window named the command `lungfish gui fastq-grouped-result --operation <kind>`, which no `lungfish-cli` command defines. A request that ran one command is unchanged. A group that mixes FASTA and FASTQ inputs runs one command for each input, and its record now holds one step for each command with the `lungfish-cli` command line that ran. The run's command is the shell form of those commands, `/bin/sh -lc` over the commands joined by `&&`, although no shell ran, and the files sit on the run with no step claiming one. A script export of such a record and `lungfish-cli provenance` therefore read the run's outputs as written by the last command, until a later release gives each step its own files. Records made by earlier releases keep the old command.

**Long error lines.** A record keeps only whole lines of a long error log. When a log is over 10,240 characters and its first line is over 2,048 characters or its last line over 8,192, that line is now left out and not cut, so a log of one long line keeps only the truncation marker. A cut line could keep part of a file path that names your folders. When the long line is the error itself, the record no longer holds it.

## Interrupted writes and external drives

**Signing files and bundle outputs.** Signature and key files are now written the way records are, so a crash or a pulled drive leaves the whole old file or the whole new one, never an empty file. On an ExFAT drive, opening the project puts back a copy that an interrupted write left aside, as it does for records. A bundle's record no longer lists as outputs its own record, its signature and key files, or the app's own state files such as `.genotype-viewstate.json`.

**Genotype annotation commands.** The `lungfish-cli` genotype commands that write `annotations.json` and its record now publish the two as a pair and, if the second write fails, restore both to what they were, signature files included. A command that finds `annotations.json` missing beside an interrupted ExFAT swap reads the newest saved copy in memory, renames nothing and prints one warning line for each bundle that names the recovery.

## Tool versions in records

**One version parser.** Records now name the right tool version in more cases. A version line that holds the storage folder's name, a path or a citation number no longer gives the version, nor does the usage text of a tool or the echoed Java command of a wrapper, and a failed micromamba probe records none. `mapPacBio.sh` records 40.02 where it recorded 0.40, and hifiasm is probed with `--version` only.

**Genotyping tool versions.** The minimap2, samtools and pysam steps of a MiSeq Amplicon MHC Genotyping run recorded the version `unknown`. They now record the version of the package installed in the environment that ran them, and the pysam filter step names its package. The unpinned tools sheet no longer lists these steps.

## Methods text

**Methods Section.** Methods Section exports now describe Kraken2, Bracken, EsViritu, MAFFT, IQ-TREE, LoFreq and iVar by what they did, and report Kraken2's confidence threshold, minimum hit groups and paired-end mode, Bracken's read length in bp, level and minimum reads per taxon, and EsViritu's quality filtering and read layout. Steps named samtools sort, merge or index are described with samtools once, by the subcommands that ran, and the Tool Versions table lists samtools once. Bracken's level and EsViritu's quality switch no longer read as a minimum length and a quality score. Each tool of a pipe reports only its own parameters, so iVar's base quality no longer reads as a samtools mapping quality.

**Piped tools.** In a pipe, each tool's sentence and Tool Versions row now take that stage's own version, package and conda environment. A later tool in a pipe took the first tool's, so the sentence for iVar gave the version and package of samtools, and a pipe of fastp, minimap2 and samtools gave minimap2 and samtools the identity of fastp. Each tool now states its own.

## Reads and quality control

**FASTQ Quality Report.** The FASTQ view's own Quality Report is removed. Nothing in the app had started it since April, when Click to Compute on the quality sparklines began to open the QC & Reporting tools. Refresh QC Summary in those tools measures every read and records the statistics it saves in the bundle. The 2026.10.14 note that a Quality Report rewrites the metadata file no longer applies. The Dataset Statistics section of the Inspector keeps its Quality Report row, which reads Cached once the quality distributions exist and Not Computed before.

**Importing reads.** The progress bar of a FASTQ import now only moves forward, where it dropped back near the start with each sample. The row's log gains the human text of the command, such as the sample list, the steps and each sample's platform decision, at information level. A failed import's row no longer carries the detail `CLI exited with status 64`, and the failure is reported once. If a program that the import started is still running when the import ends, the import now fails and adds no bundle, where it used to add the bundle and then fail. A cancel gives the command 5 seconds to remove its staging folders. If the `lungfish-cli` that the app uses is older than the app, the import ends Failed with the message "This copy of lungfish-cli at `<path>` is older than the app and cannot report import progress. Reinstall Lungfish Genome Explorer."

## Genotyping

**Stable cohort ids in `genotype export-labkey`.** `lungfish-cli genotype export-labkey` writes `cohort_id` in `smart_cohorts.csv` as a lower-case UUID that names the cohort, where it was the row number. Deleting, dismissing, restoring or renaming one cohort no longer changes another cohort's `cohort_id`. The id is unique within one bundle's export. A cohort with the same scope and name has the same id in every bundle, the four built-in cohorts included, so a LabKey list that holds the cohorts of several bundles needs the bundle in its key. A list keyed on the old row numbers needs a fresh import. The app stores each cohort's id in `annotations.json` at the next save that writes the annotations, and until then the export derives the same id from the cohort's scope and name. An earlier release drops the stored ids at its next save, and the next export derives them again, which gives the same values unless a stored id differed from the derived one.

## Translations

**Clipped reverse-strand genes.** A coding sequence on the reverse strand whose start lies beyond the end of the sequence, or beyond the edge of the window that the viewer holds, was translated from the first base LGE could read, which put it in the wrong frame. One pinned case read `SVR*R` where the protein is `QYGS`. LGE now starts the first codon at base ((p - r) mod 3) of the bases it read, with p the phase of the gene's original 5′-most segment and r the coding bases lost before the first base read. A loss at the 3′ end only shortens the protein, so a clipped protein is always the in-frame tail of the unclipped one, and a phase recorded on a later segment is not used. A forward gene whose first exon is missing follows the same rule. One rule now serves the translation in the viewer and the Inspector, the annotation drawer, the amino acid and consequence in a variant's hover, the variant table and its export, and the protein that comes with an extracted CDS annotation. A variant's residue number counts in the whole protein, so a clipped gene reads `W5R` where it read `W1R`.

**Variant table export.** The export now reads a coding feature that the viewer has not translated yet with the same rule as the viewer. A clipped reverse-strand gene no longer ends the export with `sequenceReadFailed`, and a gene that lies wholly past the end of the chromosome no longer ends the whole export either. Its rows keep the coding-feature label with a blank consequence, as the viewer shows. A gene that spans the origin of a circular sequence is joined in transcription order, where the export joined it in ascending order. The bases of a reverse-strand feature now complement ambiguity codes (R and Y, K and M, B and V, D and H) as the viewer does, where the export left them unchanged. No exported field changes for that, because a codon that holds an ambiguity code translates to X either way.

## Command line

**Classifier options.** `kraken2 classify` and `esviritu detect` take `--project`, which makes the result folder under Analyses with the viewer database and the source bundle entries, as the app does, and `--batch`, which groups the inputs into samples by their file names and runs each sample in its own folder. `kraken2 classify` also takes `--db-digest`, a SHA-256 that the database's install receipt must hold, checked before anything is written. A plain `--output` keeps the one-folder result of earlier releases.

**Events and exit statuses.** Under `--format json`, `kraken2 classify`, `conda classify` and `esviritu detect` print version 2 events on standard output and nothing else, where they printed none, and in text mode their errors and warnings go to standard error. A failed `esviritu detect` run exits 64 where it exited 1, and a failed materialization after its folder exists exits 64 where it exited 3. A SIGTERM cancels each of the three commands, records `cancelled` and exits 125. A `kraken2 classify` run that the command refuses before it starts leaves no folder and no record, where it used to write a failure record, and the reason goes to standard error.

**Database builds.** `build-db kraken2`, `build-db esviritu` and `build-db taxtriage` print version 2 events under `--format json`, with their human text on standard error, and their text mode is unchanged. `build-db esviritu` also reads a one-folder result, which an import writes.

**Import in text mode.** With `--format json`, `import fastq` prints the shared version 2 events, where it printed a private stream that only the app read. Without it, the command prints the same text on standard output as before, minus the JSON lines that carried the per-step lines and the recipe read deltas, which the bundle's metadata keeps. A notice, apart from the `--platform` notice, and a skipped sample now also print as `⚠` lines on standard error, and `--quiet` drops them.

**Help text of `-o` and `--output`.** The help of `kraken2 classify` and `conda classify` said that a run without `-o` writes to the current directory, and it writes to `./classification-<db>` with `<db>` in lower case. The help of `esviritu detect` said the same, and it writes to `./esviritu-<sample>`. Both helps now name the folder. The help of `taxtriage run` now says that with several samples one Nextflow run processes them all and writes their results to the `-o` folder. The CLI reference appendix of the user manual says the same.

**Cancelling a database build.** `build-db kraken2` and `build-db esviritu` now check for a cancel between sample folders and before each step that writes or removes something. A cancel ends the build with the cancellation, puts the database of an earlier build back and writes no record of a failed build, and the read count pass of `build-db esviritu` stops at the first BAM it has left. A step that finished before the cancel stays done and no record names it, so folders that Kraken2 had compacted, BAMs that EsViritu had moved and `_temp` folders that it had removed stay as they were left. A cancel that arrives after the last check is not seen, and the build completes. `build-db taxtriage` has no such check yet.

**GATK commands record their command.** The record of `lungfish-cli gatk <subcommand> --execute` now names the `lungfish-cli gatk` command as the run's command, and each step keeps the GATK command it ran. Before, the record named only `gatk HaplotypeCaller ...`, so the check that decides whether a file with a record beside it came from a `lungfish-cli` run refused the VCF of such a run, and attaching it ended with the alert "Use an Import Workflow for Scientific Data". The record now passes that check. The command is the line the process was started with, or the line that the parsed options spell when something else ran the command, with every option that has a default written out. A dry run still runs nothing and writes no record. A run that you start from the app's variant calling still records its first GATK command as its command, until a `lungfish-cli` command attaches the VCF to a bundle.

## Releases

**Release signing.** From this release on, LGE is signed with a Developer ID certificate from Apple's G2 certificate authority, which replaces the certificate that was due to expire on 1 February 2027. You see no change, and updates keep arriving.

**For contributors.** `scripts/release/developer_id.py` lists the Developer ID identities with `show` and proves a certificate with `verify`. `release.py configure-machine` takes `--certificate-sha1` or `--certificate-policy newest-g2`, with `--replace`, and `release.py doctor` prints the issuer and expiry of the selected certificate and fails for an expired one. The runbook is `docs/development/developer-id.md`.

## For contributors

This release carries Phases 2.7 and 2.8, which shipped no Preview of their own. `docs/plans/2026-10-11-phase-2-7.md` and `docs/plans/2026-10-11-phase-2-8.md` record the lanes, the expert panels' rulings and the final candidates.

TaxTriage and its stand-in engine:

- `TaxTriageStandInEngine` in `Tests/Support/LungfishTestSupport` is a stand-in micromamba and Nextflow. It records each launch's argv, environment, samplesheet bytes and FASTQ records for each input, and it has switches for a clean run, failed samples, ignored task failures, a launch that waits for a cancel and a launch that traps TERM and keeps a heartbeat child. No test runs a real TaxTriage run, so a real run is a row of the owner check list.
- `AppDelegate.TaxTriageLaunchSeam.makeRunner` and `TaxTriageCommand.RunSubcommand.makePipeline` are task-local factories that tests set, with today's constructions as defaults. No settable static and no `nonisolated(unsafe)` was added. `TaxTriageStandInEngineReplayTests`, `TaxTriagePipelineCancelReplayTests`, `TaxTriageOperationRowTextReplayTests` and `TaxTriageKeptInputsReplayTests` end in `ReplayTests`, so they run serially in the integration tier.
- `TaxTriageEngineProcess` spawns the engine through `ProcessManager.spawnStoppable` and binds the task's cancel to the returned stop, with a 4 second grace. The public `spawn`, `runAndWait`, `NextflowRunner`, `SnakemakeRunner` and `WorkflowRunner` keep ToolProcess's 500 milliseconds. The end of `runTaxTriage` now lives in `AppDelegate+TaxTriageCompletion.swift` and the provenance section of the pipeline in `TaxTriagePipeline+Provenance.swift`.
- `TaxTriageRecordFacts` builds the record facts as values. `ProvenanceEnvelope.readSetPlansBySample` gives each sample's plan, and `readSetPlan` takes the released keyed plan only when the record says it ran one sample. `TaxTriageReadSetPlanner.materializationDirectoryName` names the kept inputs folder once for the app and the command.

Records and the parity suite:

- A named file that is missing or holds another digest is accepted by the classifier parity suite only when a later step of the same record names it with the stated digest as input, or a removal step of the same result names it by path, no earlier than the naming within one record and with the digest when the file holds other bytes. A removal step never excuses the run level of a record, which names only files that exist. `RecordedRemovalStep` records a removal, `ClassifierParityNamedFileRuleTests` pins the rule on hand-built facts, and the suite masks each side's own LGE version on A-against-C step facts.
- `ClassifierCLIRealToolCancelReplayTests` cancels and fails a real Kraken2 run through the built `lungfish-cli`. It needs `lungfish-cli` beside the test bundle and `seqkit`, `kraken2` and the Viral database in `~/.lungfish-stable`, and `LUNGFISH_REQUIRE_TOOLS=1` turns a missing one into a failure. A watcher on the command's process id checks that no byte is written into the project after the command exits. The parity route suite no longer adds files to `~/Library/Preferences`.
- `ClassifyCommand.execute(adjustServices:)` and `AssembleCommand.execute(pipeline:)` take stand-ins, and `recordedCommandLine(_:fallback:)` records the argv as typed when it names the command and the command that the parsed options spell otherwise. `ClassifyCommand+CommandLine.swift`, `AssembleCommand+CommandLine.swift` and `GATKCommand+CommandLine.swift` hold those commands, and the Kraken2 executor column of the parity suite now runs through `ClassifyCommand.execute`.
- `ScientificProvenancePolicyLeafTests` walks `LungfishCLI.configuration`, hidden leaves and the parser's own `help` included, so a leaf that a lane registers needs its pinned row at once. `ScientificCLIProvenanceCoverageTests.recordsNothing` gives a reason for each group and leaf that records nothing, with their own reasons for `conda run` and `demo fetch`.
- `BrackenProfileDegradationReason` is a plain enum with the seven released cases and `unknown(String)`. `init(rawValue:)` never fails, `rawValue` is the stored token and an unknown reason writes back byte for byte. A test pins the seven released tokens, and a later release writes the next reason.

### The operations dialog and the importer

- `FASTQOperationCLIInvocationBuilder` throws `FASTQOperationCLIInvocationError.classifierLaunchHasNoDialogCommand(tool:)` for a classify request, which keeps the case as dialog state. Only tests reached those rows, and they gave `conda classify` as one argument and gave `esviritu detect` and `taxtriage run` input paths that neither command accepts. `FASTQOperationDispatchFreezeTests` pins the first word the dispatcher passes, the row words and the shipped parser's reading of each of the 10 request kinds.
- `FASTQBatchImporter.encodeLogEvent` is deleted, because no production code called it since `import fastq` moved to version 2 events. `ImportLogEventRecorder` in `LungfishTestSupport` collects `ImportLogEvent` values for tests, and the tests of the JSON are gone.
