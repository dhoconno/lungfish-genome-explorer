# Lungfish 2026.11.11

Channel: Preview

Previous versioned release: v2026.11.10

Stable baseline: v2026.11.7

Dependency set: 2026.2

Preview builds are under rapid iterative development. Features may be incomplete, change quickly, or require additional feedback.

This Preview closes three known issues of 2026.11.10. Trimming paired reads and Viral Recon no longer hold all the reads in memory. A TaxTriage result that reads another sample's BAM now says so in the app. Older results of Viral Recon, Call Variants, trimming, a FASTQ import with a recipe and Demultiplex Barcodes now show what went wrong. In `lungfish-cli`, the RNA-seq commands gain a UMI plan, a limit on the loci a STAR read may map to, a sparsity option for STAR indexes and the import of a UMI run. The Preview also changes which genes `rnaseq index-plan --tenx-filter gencode-2020-A` keeps, so read What works differently if you planned an index with 2026.11.10.

## What works differently

- **Trimming paired reads and Viral Recon no longer hold all the reads in memory.** The Lungfish helper `lungfish-cli` now puts the reads in their fixed shuffled order one part at a time and reuses the same memory for every part. At 19.3 million read pairs, the helper used 0.19 GB of memory for trimming, against 10.7 GB in 2026.11.10, and 0.18 GB for preparing the reads for Viral Recon, against 11.1 GB. The fastp program that does the trimming uses memory of its own besides, a little over 1 GB at that size. The 0.18 GB for Viral Recon was measured on a debug build of the helper. Lungfish now checks the free disk space before either run. When the disk is too small, it stops before it writes anything and says how much space the run needs and how much is free. At 19.3 million read pairs the trim used about 19 GB of disk space at its peak, and the check asks for about 25 GB free, which leaves a margin over what the run uses. The reads come out in the same order as before, so every result is the same.
- **A TaxTriage result that reads another sample's BAM now says so.** When a sample has no BAM file of its own and Lungfish reads another file from the minimap2 folder whose name fits it, for example `S1_2.bam` for sample S1, the result's action bar, the Inspector and the BLAST Verify row in the Operations panel now say so and say what to do. Before, the alignment, its coverage and the reads sent to BLAST came from that file with no warning, and it may hold another sample's reads. Nothing is refused and no count changes.
- **Older results of five more kinds show what went wrong.** A result that an earlier version made wrong with Viral Recon, Call Variants, FASTQ trimming, a FASTQ import that ran a recipe or Demultiplex Barcodes now shows what went wrong and what to do, in the viewer and on the Inspector's Provenance tab. In 2026.11.10 these five showed nothing, so you had to use the redo lines of the 2026.11.8 notes.
- **`rnaseq index-plan --tenx-filter gencode-2020-A` now follows 10x's rule.** In 2026.11.10 it tested each gene's biotype alone. On GENCODE v32 it kept 887 genes that 10x's GRCh38-2020-A reference leaves out, and it accepted RefSeq and Ensembl sets. It now keeps the 36,601 genes that 10x keeps and refuses a set with no `gene_type` and `transcript_type`. The refusal names `--tenx-filter mkgtf-3.0.0` for a set whose genes carry a `gene_biotype`. On the RefSeq set Macaca_fascicularis_5.0, `gencode-2020-A` kept 26,810 genes in 2026.11.10 and is now refused, and `mkgtf-3.0.0` keeps 20,627, since its list does not name lncRNA. `index-adopt` refuses a run of an index planned with 2026.11.10 under `gencode-2020-A`, in words that name both rule versions, so plan such an index again. The kept gene ids keep GENCODE's version suffix, such as `ENSG00000243485.5`, so drop the suffix before you compare a matrix with Cell Ranger's.

## What's new

- **Plan a UMI count for a Linux machine.** In `lungfish-cli rnaseq quant --write-plan`, a sample sheet with a `kit` column plans the UMI branch. The one kit is `quartz-seq2-x910`, Quartz-Seq2 primer X910 with ATCAATC and then a 16-base UMI on Read 1. The plan checks each pair's layout, extracts the UMI with umi_tools, maps the kept read with STAR 2.7.11b on the set's adopted index, and counts UMIs per gene with featureCounts and umi_tools, so a count is molecules. The kit fixes the chain, so leave out `--chain`, `--trim`, `--k` and `--decoys`. Name a kit for every sample or for none, and rename any other column called `kit`, such as a library prep kit, since Lungfish reads it as the UMI kit.
- **Set the most loci a STAR read may map to.** `lungfish-cli rnaseq quant --write-plan --star-multimap-nmax <n>` sets STAR's `--outFilterMultimapNmax` for the chains `star-2.7.11b-genecounts`, `star-2.7.3a-genecounts` and `star-2.7.11b-featurecounts`. With no option STAR keeps its default of 10. The deposited counts of GSE304256 need a limit at or above the most loci any of its read pairs maps to. Its authors did not document the limit, and 1000 matched the six runs measured. On `star-2.7.11b-featurecounts` a larger limit also changes the exon counts, since `-M` counts each alignment of a read that maps to more loci. The other chains refuse the option in words.
- **Choose the suffix-array sparsity of a STAR index.** `lungfish-cli rnaseq index-plan --genomeSAsparseD <n>` takes a whole number from 1 and defaults to 2. A larger value needs less memory and maps more slowly. It also changes which reads map. On 2 million reads of a 30 Mb slice of GRCh38, 114,955 reads mapped to the slice at sparsity 1. The alignments of 28,357 reads differed between sparsity 1 and 2, and 279 rows of STAR's GeneCounts table differed, so compare counts only between indexes of the same value. STAR's own default is 1. A value of 1 needs about twice the suffix-array memory of 2, so `index-plan` refuses it unless you give `--request-memory-mib`.
- **Import the counts of a UMI run.** `lungfish-cli import rnaseq --adopt` now reads the UMI branch's count of UMIs per gene. For a run of the `star-salmon` chain, which is STAR and then salmon on STAR's transcriptome alignments, the record now lists the files that the import left out. A UMI sample whose layout check failed has no counts and is refused in the check's words, and it never falls back to counting without UMIs. A batch that mixes two alignment scorings, `none` and `errorModel`, is refused in words, so adopt each kind as its own batch.

## Things to know

- **The action bar can cut the end of a long TaxTriage notice.** It shows the notice on one line. For a result built before 2026.11.6 the warning that the file may be another sample's comes late in the text, where the cut can hide it. Hover over the line or read the `BAM note:` row of the Inspector to see all of it.
- **A saved BLAST Verify verdict carries none of these words.** Verify logs the words in the Operations row while it runs, but the record that `blast submit` writes holds none. If you put the sample's own BAM back and rebuild the database, a verdict saved from the earlier run shows no warning.
- **An old result can show nothing.** A result that `lungfish-cli` made before 29 September 2026, and a Viral Recon result of builds 1618 to about 5900, can show no note about what went wrong, since its record names no build the app can read. A cancelled or failed trim of build 12972 or older can show the trim words beside a result that holds no reads.
- **Poly-G tails at import.** A FASTQ import that uses Trim Galore decides for itself whether to cut poly-G tails, and the import's provenance record keeps Trim Galore's own answer, which the import sheet does not show. A recipe you write yourself that turns fastp's poly-G option off passes no flag, so fastp decides from the instrument in the read name.

## Known issues

Each row is open in this build. It says what can go wrong, who can meet it and what Lungfish already tells you.

- **Verify with BLAST can judge an imported EsViritu result by organism names.** The judge then reads the first word of a name, so a top hit named "Rotavirus C" can count as supporting "Rotavirus A". A native EsViritu result is judged by its tax ID and is not affected. A result judged by names shows a line that begins `Judged by organism names` under its summary. A result saved by an earlier version shows no such line.
- **Demultiplex Barcodes with Exact Bare Barcode has no chance floor.** On 150-base reads that carry none of your barcodes, each 8-base barcode still matches about 0.44% of the reads by chance, about 5% for 12 barcodes, and each barcode that matches becomes a sample file. The dialog says so when you pick the engine, and a run that makes sample files warns in its summary and its Operations row. Cutadapt, the default engine, has the floor.
- **A custom kit of very short barcodes defeats the chance floor.** When about half of all random read starts would match a barcode, as with a 384-sample plate of barcodes of 4 and 5 bases, the floor cannot tell a pool from a file with no barcode, and chance matches can become sample files. The summary says so, and the Operations row and the Log show the floor's own line.
- **The chance floor is a measured 1 in 1,000 for each barcode.** A 12-base kit built for the test that allows one error published a false sample in 3 of 147 real cuts, and the default Illumina kit in none of 147. A false sample holds about 0.4% of the reads, as a real small sample does. The window says that such a barcode can pass in about one run in 1,000 and tells you to check samples with few reads against your sample sheet.
- **Extract Reads can fit another sample's BAM to a sample.** It happens when no BAM path is recorded for a sample, the sample has no BAM of its own, and one file such as `S1_2.bam` or `S1.5.dedup.bam` belongs to another sample. The scan then gives that file to `S1`, and `S1` reads it.

One more row concerns Viral Recon.

- **Viral Recon on single-end Illumina reads lets fastp guess the adapter** from the head of the staged file. Whether that changes a result is not settled. The one single-end run measured gave one result in the file's order and with seeds 1 to 3.

The limits in the 2026.11.8, 2026.11.9 and 2026.11.10 notes still apply, except the one on Illumina amplicon genotyping, which 2026.11.10 fixed, and the three that this version closes.
