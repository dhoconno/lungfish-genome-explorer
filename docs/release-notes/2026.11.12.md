# Lungfish 2026.11.12

Channel: Preview

Previous versioned release: v2026.11.11

Stable baseline: v2026.11.7

Dependency set: 2026.2

Preview builds are under rapid iterative development. Features may be incomplete, change quickly, or require additional feedback.

This Preview closes four known issues of 2026.11.11 and narrows a fifth. Verify with BLAST and Extract Reads, and Viral Recon on single-end reads, no longer have the known issues that 2026.11.11 listed. Demultiplex Barcodes now stops before it makes sample files that its check for chance matches cannot vouch for, and older results made from the Fluidigm kit or from very short barcodes show a warning. In `lungfish-cli`, `rnaseq quant --write-plan` plans single-end reads, and a batch for an HTCondor pool releases a job that could not fetch an input file. The Linux plans of Phase 5.3 gave the counts of the reproduction scripts on public data. One new known issue is open, older results from a custom list of dual indexes, which show no warning yet.

## What works differently

- **Demultiplex Barcodes with Cutadapt stops when its check for chance matches cannot judge the barcodes.** When the barcodes of a kit match about half of all reads or more by chance, as the built-in Fluidigm Access Array kit does and as a very short custom kit can, the run now stops before it makes any sample file. It does the same for a custom list of dual indexes at Both Ends with no sample sheet. The message says why. For the Fluidigm kit it points to ONT Fluidigm Sample Split and to the engine Read Names, and for a list of dual indexes it points to Read Names. Every message also names Keep Unchecked Samples (`--keep-unchecked-samples` on the command line), which makes the sample files anyway so that you can check each one yourself.
- **Exact Bare Barcode stops when the barcodes are in the read names.** If the read names carry two or more of the barcodes of your list, the run now stops before it makes any file and points you to the engine Read Names, because a search of the read sequences finds those barcodes only by chance. Choose Keep Unchecked Samples only if the read sequences carry the barcodes too, then check each sample against your sample sheet.
- **Extract Reads no longer gives a TaxTriage sample another sample's reads.** It happened when the sample's own BAM file was missing and the result listed the other sample, such as `S1_2.bam` for sample S1. Extract Reads now says that no BAM file was found. A result that lists no samples still reads the one file whose name fits and says which file it read.
- **Verify with BLAST… no longer counts a read as supporting an EsViritu row when its best match is another virus that only starts with the same word,** such as Rotavirus C for Rotavirus A. This applies to a row judged by organism names, as an imported result is. Such a read now counts neither for nor against the row, and a best match whose name starts with another word counts against it, even when it is the same virus under another name. The line `Judged by organism names` under the summary says how a row was judged. On the same basis, a read pair with one mate that only starts with the row's first word and one mate that contradicts it now reads Contradicted, where it read Ambiguous. If you ran Verify with BLAST… on such a row before, run it again.

Two more changes concern Viral Recon and older results.

- **Viral Recon now names the Illumina adapters for single-end samples,** so the same reads give the same trimmed result whatever order they are stored in. A run of paired reads is unchanged.
- **Older results of five kinds show a warning.** A Viral Recon result, a TaxTriage extraction, a BLAST check of an EsViritu row, a Demultiplex Barcodes result of the Fluidigm kit or of very short barcodes, and an Exact Bare Barcode result on barcodes in the read names, each made by an earlier version, now show what may be wrong and what to do. The words are in a band above the viewer and in the Warnings of the Inspector's Provenance tab.

## What's new

- **Plan single-end reads for a Linux machine.** `lungfish-cli rnaseq quant --write-plan` now plans single-end reads from a sample sheet whose r2 cell is empty, so fill r2 for every read pair. The chains salmon, star-2.7.3a-genecounts, star-2.7.11b-genecounts and star-2.7.11b-featurecounts take single-end reads, and the STAR then salmon chains, star-salmon and star-salmon-errormodel, refuse them in words. A sample sheet holds samples of one layout, so write single-end samples and read pairs in two plan folders. Of the four chains that take single-end reads, only star-2.7.3a-genecounts has been checked against a deposit, GSE152418, on 7 of its 34 samples. The other three are tested on their plans and are not yet measured on single-end reads.
- **A batch for an HTCondor pool releases a job that could not fetch an input file.** Before, a batch released only a job that had finished and could not send its files back. It now also releases a job held with code 13, which could not fetch an input file and never ran. Both kinds share one limit of two releases for a job, and a job held a third time stays held. If its reason says the transfer made no progress, run `condor_release <ClusterId>.<ProcId>` once the staging folder answers. The batch's `README.txt` says so and gives a `condor_q -hold` line that shows each hold's code and count. A batch written before this version keeps its old rule and README.
- **The Linux plans of Phase 5.3 gave the counts of the reproduction scripts on public data.** The plans that `lungfish-cli` writes for a Linux machine ran on CHTC's Linux machines. STAR's GeneCounts for the six runs of GSE304256, with the multimapping limit set to 1000, equal the deposited counts and the scripts' counts, and 0 of 106,308 cells differ in each run. For GSE152418, the 14 single-end runs of seven samples equal the scripts' tables byte for byte, and the two runs of each sample, summed, equal the deposited counts on every gene of those seven samples of 34. STAR GeneCounts and featureCounts equal the scripts' counts on the seven runs of GSE290671. STAR then salmon gave `quant.sf` files byte-identical to the scripts' on the four runs of GSE225770. STARsolo gave the 5.0 script's barcodes and count matrices, byte for byte, on three public 10x data sets. The technical record says that each of the three sets passes every bar of its comparison with 10x's own matrices and gives the main figures.

## Things to know

- **Demultiplex Barcodes.** A barcode not in your pool can still pass as a sample, in about one run in 1,000 for each one and more often in amplicon files, and the summary and the Operations Panel say so. A false sample holds about 0.4% of the reads, as a real small sample does, so check samples with few reads against your sample sheet.
- **Exact Bare Barcode checks no chance.** On reads that do not carry the chosen barcodes, it makes a sample file for any barcode found by chance anywhere in a read, and in amplicon reads one such file can hold most of the reads. Use it only for reads that carry those barcodes, and check the sample files against your sample sheet.
- **The Viral Recon warning also shows on a result of paired reads only.** Its first words name single-end reads, and it asks you to run again only if the run used them.
- **A saved BLAST check can show no warning.** A check of a TaxTriage row with no tax ID, or of a NAO-MGS call with tax ID 0, shows none, though this version judges its reads by names differently. Run such a check again.
- **An extraction saved as a loose FASTQ file by the command line may show no warning.** Nobody has checked it.

The limits in the 2026.11.8, 2026.11.9, 2026.11.10 and 2026.11.11 notes still apply, except the one on Illumina amplicon genotyping, which 2026.11.10 fixed, the three known issues of 2026.11.10 that 2026.11.11 closed, and the known issues of 2026.11.11 that this version closes or narrows.

## Known issues

Each row is open in this build. It says what can go wrong, who can meet it and what Lungfish already tells you.

- **Earlier results from a custom list of dual indexes.** Before this version, Demultiplex Barcodes with Cutadapt could make sample files from reads that carry no barcode when you gave a custom list of dual indexes at Both Ends with no sample sheet. In tests on real reads with no such barcodes, 96 pairs of 8 bases placed 8.1% and 11.3% of the reads in samples by chance at error 0, and 74.0% and 82.2% at error 0.15. The Inspector does not yet warn about such a result. If you made one, check that each sample holds the reads you expect, or run it again with the engine Read Names when the indexes are in the read names. A new run is refused unless you choose Keep Unchecked Samples. The refusal also covers long indexes that would give no chance match, such as 16-base sides at error 0, and Keep Unchecked Samples runs those. Changed in 2026.11.13. A Custom Definition of dual indexes is searched only at the read ends, so a new run needs no Keep Unchecked Samples, and results of Previews up to 2026.11.11 show a warning in the Inspector. The warning does not cover a result that 2026.11.12 made with Keep Unchecked Samples, so check those samples against your sample sheet.
- **Earlier results from a Custom Definition of dual indexes at 5' End or 3' End.** In this version, Demultiplex Barcodes with a custom dual-index barcode file at 5' End or 3' End and no sample sheet left the reads of the reverse strand in Unassigned, and the sample files of such a run can hold reads that matched by chance, enough in an amplicon pool to fill a sample. The Inspector does not yet warn about such a result. Preview 2026.11.13 stops this setup and says why, and it shows a warning on results that this version and earlier versions made. If you made one, run it again at Both Ends with 2026.11.13 or later, and if your barcodes sit some bases in from the read ends, set 5' Distance and 3' Distance to that many bases.
- **Two rows of a Custom Definition of dual indexes that swap.** In this version, a Custom Definition of dual indexes at Both Ends with no sample sheet ran only if you chose Keep Unchecked Samples, and Demultiplex Barcodes then looked for the secondary sequence of each row just as you wrote it. When your definition listed the i5 primer's barcodes, which appear reverse complemented at the end of the read, and two rows had first barcodes that matched and secondary sequences that were reverse complements of each other, each within the error rate, those two samples got each other's reads with no warning. The Inspector does not yet warn about such a result. Preview 2026.11.13 reads the secondary sequence the way your reads carry it or stops and says why, and it shows a warning on results that this version and earlier versions made. Run such a split again with 2026.11.13 or later.
