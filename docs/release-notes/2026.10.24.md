# Lungfish 2026.10.24

Channel: Preview

Previous versioned release: v2026.10.23

Stable baseline: v2026.9.78

Dependency set: 2026.2

Preview builds are under rapid iterative development. Features may be incomplete, change quickly, or require additional feedback.

This Preview adds a way to clean up FASTQ reads on a Linux machine and bring the results back to the Mac. You write a plan folder on the Mac, run it on any x86-64 Linux machine that holds the Lungfish tool image, through an HTCondor pool or a plain launcher script, and import what comes back as FASTQ bundles, one sample or a whole batch. On the Mac, Optimize storage with Automatic now reorders every short-read import whatever its size and leaves long reads as they are, and an import checks for free disk before BBTools clumpify reorders a sample's reads.

## What's new

### Pre-process reads on a Linux machine

- **Write a plan on the Mac.** Choose File > Import Center… (Cmd-Shift-I), open Sequencing Reads and click the Plan for a Linux Machine card. Choose the read files, or one folder of them. The sheet asks for the staging folder, which is the absolute path of the folder on the Linux machine that the jobs read from, the threads per job (8 to start) and the clumpify memory in GB (16 to start). Write Plan… asks for a new folder and writes the plan into it. Nothing is imported and nothing is submitted. On the command line, `lungfish-cli import fastq <reads> --write-plan <folder> --staging-folder <path>` does the same and also takes a recipe and a sample sheet. The sheet takes no recipe, so use `--recipe` on the command line.
- **The clumping box follows the reads.** The plan sheet's Optimize storage box opens on with BBTools clumpify. A moment later Lungfish reads the headers of the first sample's reads and clears the box for Oxford Nanopore, PacBio and Unknown reads. It stays on for Illumina, Element and MGI reads of any size. With the box clear the plan stores the reads without reordering, and you can tick it to reorder long reads.
- **What the plan folder holds.** One folder for each sample with its plan, and `README.txt` with the commands for both ways to run the batch. `staging-files.json` lists every file the jobs read, with its size and SHA-256 and, for each file except the image, the file on the Mac to copy or link. `run.dag` and `sample.sub` run the batch on an HTCondor pool, and `jobs.tsv` and `run-local.sh` run it on one machine. The plan fixes every setting and pins the image, its tool list and each database by SHA-256, so every machine runs the same tools.
- **Run on an HTCondor pool.** Copy or link the files that `staging-files.json` lists to their places in the staging folder, copy the plan folder to the machine you submit from and run `condor_submit_dag run.dag` inside it. At most 10 jobs run at once, and `run.dag.status` shows the state of every sample. The jobs ask for machines that reach the staging folder, run EL9 or later and are x86-64. That test names a machine attribute that only the pool we tested on is known to set, so on another pool write the plan with `--job-requirements '<expression>'`.
- **Run on any Linux machine.** Copy the plan folder to the machine, make a data folder that holds the files `staging-files.json` lists (for Apptainer the image goes in its `images/` folder), and run `sh run-local.sh --runtime apptainer --data <data folder>` from inside the plan folder, or `sh run-local.sh --runtime docker --image <image> --data <data folder>`. It runs at most 10 samples at once (`--jobs <n>` changes that). With Apptainer it refuses an image whose SHA-256 is not the plan's. Each sample leaves a `result/` folder with its run record, reports and reads. A Mac with Docker can run it too.
- **Bring the results back.** For each sample, copy the files inside its `result/` folder into that sample's folder on the Mac, next to the `plan.json` the Mac wrote. `README.txt` gives one `rsync` loop that does this for every sample. Do not copy the logs or a `plan.json` back from the Linux side. Then import one sample folder or a whole batch folder with the Linux Run Result card on the Sequencing Reads tab of the Import Center, or a batch with `lungfish-cli import fastq <batch folder> --adopt --project <project>`.
- **Checks before anything is written.** Lungfish checks the size and SHA-256 of each returned read file against the run record before it writes a bundle, and it refuses a file that differs and names it. A batch is imported whole, so when any sample is refused, nothing is imported and every refused sample is listed by name with its reason. A sample is refused when its files still sit in `result/`, and the line says to copy them out, or when the project already holds a bundle with its name. If a batch import stops after some samples, because the disk is full or you click Cancel, the bundles it made stay whole and the message names them. Delete them and import the batch again. They appear in the sidebar within a few seconds.
- **The card's row.** A batch makes one bundle a sample, and its row in the Operations Panel ends `Imported 3 samples` for three. A refusal or a failed write ends the row Failed with the reason, and Cancel ends it Cancelled.
- **What the bundle records.** Each sample becomes one FASTQ bundle whose Provenance tab names the Linux run. Its Runtime section shows Steps ran on (the Linux kernel and machine), Steps ran with (the build and SHA-256 of the Lungfish executor), Leftover processes, and the facts the launcher passed, under Reported by the launcher. Lungfish shows those facts as given and does not check them. A `run-local.sh` run passes Machine name, CPU architecture, Operating system, Container runtime, Container runtime version, Image SHA-256 (Apptainer) or Container image ID (Docker), and Launcher. Each step of the run shows its Version and build.

### The plan command

- **The app's executor and image are the defaults.** `--write-plan` uses the Linux executor and the image record that the app holds, so it needs the staging folder and no executor or image file. `--executor-manifest`, `--image` (an `image.json`) and `--image-tool-manifest` are optional and name ones you built.
- **The sample sheet is comma-separated.** A tab-separated sheet is refused with a message that says to write it as `samples.csv`.
- **What the plan asks of the pool.** The plan has no retry lines, since a job that ends without all its listed files is held whatever its exit code and a retry never acted. It asks HTCondor to release a held job by itself, at most twice, when its run exited 0 and only sending its files back stalled. A job's work space follows its recipe: 10.61 times the size of its read files for wastewater and 5.03 times for VSP2, since wastewater runs used about twice as much per byte.

### Storage records

- **How the stored file was written.** The storage step of a FASTQ import on the Mac now records the program that wrote the compressed file, the compression level that took effect and, for BBTools clumpify, the number of groups clumpify split the reads into. The Provenance tab shows them as Compressed by, Compression level and Clumpify groups. An import made with an earlier release shows as it did.

## What works differently

### Reads and downloads

- **Optimize storage for short and long reads.** With Automatic, the default of `lungfish-cli import fastq`, an import of short reads (Illumina, Element, MGI or Ultima) is now reordered with BBTools clumpify whatever its size, and clumpify splits a large sample into groups to fit its memory. Long reads from Oxford Nanopore or PacBio, and reads whose platform is Unknown, are not reordered with Automatic, because clumpify works well only on accurate reads. Ultima reads are not recognized from their headers and read as Unknown unless you name the platform (`--platform ultima`). In the Import FASTQ sheet the Optimize storage box now opens on for short reads of any size and stays off for long reads and Unknown reads.
- **A named tool always counts.** A clumping tool that you name, such as `--clumping-tool bbtools`, is now used for Oxford Nanopore and PacBio reads too, where before it was ignored. Reads whose platform is Unknown are reordered only when you name a clumping tool.
- **Free disk before reordering.** Before BBTools clumpify reorders a sample on the Mac, Lungfish checks that the disk holding the project has free space of about five times the size of the sample's read files. With less, that sample is not imported and its original files are kept, and the other samples of the import go on. Free up space on that disk or turn off Optimize storage, then import again. On the command line, `--no-optimize-storage` skips the reordering. The Trim Galore choice also reorders reads and has no such check.

## Things to know

### Linux runs

- **The image is not inside Lungfish.** A plan names the Lungfish tool image, a file named like `lge-tools-<id>.sif`, by its SHA-256, and the jobs read it from the `images/` folder of the staging folder. Lungfish does not include or download it, and `staging-files.json` lists it with no file on the Mac to copy. Ask the person who looks after your Linux machine or pool for that file.
- **Docker needs the image made into a Docker image.** `run-local.sh --runtime docker` runs a Docker image for linux/amd64 made from that file. The Lungfish source, not the app, has a script for it: `bash scripts/linux/launcher-tier.sh image --sif <image file> --record <record file>`, with absolute paths. It checks the file against the size and SHA-256 that the app's image record pins, reads it in a helper container that Docker runs with its privileged flag, and leaves the image `lge-tools:<first 12 characters of the SHA-256>` for `--image`. On a Mac with Apple silicon, Docker runs the image's x86-64 programs under emulation.
- **A plan with no platform is planned as short reads.** For long reads, pass `--platform ont` or `--platform pacbio` with `--write-plan`, or an Automatic plan reorders them. The plan sheet passes no platform.
- **Reruns.** `run-local.sh` retries nothing and skips a sample that has a `result/` folder, so delete that folder to run the sample again.
- **Disk and memory of a job.** The disk and memory each job asks for come from runs of small samples. Watch the first jobs of a large sample, and give a sample more disk with a `request_disk` column, in whole GB, in the sample sheet.
- **Held jobs on a pool.** A held job waits, and the batch does not finish until you deal with it. A job can be held even after its run finished, when sending its files to the staging folder stops making progress, and the automatic release has not yet been seen to fire on a real pool. `condor_q -hold -af ClusterId ProcId DAGNodeName ExitCode HoldReason` names the held sample, its exit code and the reason. In the sample's log, "Job was evicted" and then "Job was held" are one hold, not a move to another machine. With exit code 0, leave the job. Otherwise follow `README.txt`: copy the sample's run record aside, since running the sample again replaces it, remove the job with `condor_rm`, and run `condor_submit_dag run.dag` again to run only the samples that did not finish.
- **The adopted bundle's platform.** A returned folder holds no reads to infer a platform from, so the adopted bundle keeps the platform the plan gave, and its record says the platform was not inferred.
- **The acceptance run.** We planned three small public runs on a Mac, a viral capture (SRR35520572) and two wastewater runs (SRR24403534 and SRR38262740), as two batches, VSP2 and wastewater. Each batch ran on an HTCondor pool and was imported whole into one project. Against the Mac's own import of the same reads, all three samples had the same reads and read counts, and two had the same stored order too. Clumpify split SRR24403534 into 13 groups and stored its reads in another order, as the next section says. SRR38262740 also ran through `run-local.sh` with Apptainer in a pool job and matched in full, and with Docker on a Mac under emulation, where the executor's self-check passed and the run, the copy and the batch import each exited 0. Scaled to a 61.6 GB sample at one thread, no job would pass 36 hours, half the 72-hour limit of the pool.

### Reads and downloads

- **Large imports need more room and time.** A large short-read import on the Mac now reorders its reads, so it takes longer and needs free disk of about five times its read files while it runs. The five is about four times the read files that one Linux run needed beyond its reads and tools, plus a quarter as a margin.
- **Same reads, usually a smaller file.** Reordering keeps every read and changes only their order and the size of the stored file, so read counts do not change.
- **Two imports of one large sample.** Two imports of the same large sample can store its reads in a different order. The reads, read counts and summary quality numbers are the same, and only the read-length and quality charts, drawn from the first 100,000 stored reads, can differ slightly. The order can change only when clumpify splits the sample into more than one group.

### If you repeat earlier work

- **Imports.** A large short-read import that 2026.10.23 stored without reordering is reordered by this release, so its stored file is usually smaller and its reads come in another order, with the same read count.

### Everything else

The limits under Things to know in the 2026.10.23 notes still apply, except where a change above says otherwise.

## Updating

Choose Check for Updates… in the app menu, and Sparkle offers this release, installs it and relaunches the app. This release adds no tool to install on the Mac. The app now holds the Lungfish executor for Linux, about 59 MB, which each plan lists in `staging-files.json` as a file to copy to the staging folder.

Dependency set 2026.2 is unchanged from v2026.10.23, and no entry of the tool lock changed. The Ribosomal RNA Removal Data (deacon-ribokmers) is a pinned download of 10,107,947 bytes with SHA-256 f88286f607bc062ef872b55cac9aff1d447f7106068cafefef72a3ba8e49ede6, built with deacon 0.16.0 on one thread from BBMap's ribokmers.fa.gz. The Human Read Removal Data (deacon-panhuman) is pinned by SHA-256 at 3,279,263,603 bytes, and its source link points to github.com/bede/deacon. The file `third-party-tools-lock.linux-64.json` holds the tools of the Linux tier and does not change the Mac tools. No pinned tool or pipeline moved.
