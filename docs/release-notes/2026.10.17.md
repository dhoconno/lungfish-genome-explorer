# Lungfish 2026.10.17

Channel: Preview

Previous versioned release: v2026.10.16

Stable baseline: v2026.9.78

Dependency set: 2026.2

Preview builds are under rapid iterative development. Features may be incomplete, change quickly, or require additional feedback.

This release fixes two defects and makes the log of an EsViritu run say what the run is doing. In the read stack of Lungfish Genome Explorer (LGE), reads to the left of the window that you first looked at no longer sit below a band of blank rows after a pan. An EsViritu run no longer stops after one hour, a limit that ended a sample of 25 million reads while minimap2 was still aligning it. The log of an EsViritu run now names each EsViritu step and shows a running count of the reads processed in each of its three alignment rounds, where it repeated `Quality filtering reads...` and then showed nothing during the alignment. The owner check list under Checks still to run blocks a Stable promotion, and this release adds rows 25 and 26 to it.

## Read viewer

**Blank rows after a pan.** With Limit visible rows off, its default, a pan to the left in the read stack could leave the reads there below a band of blank rows. It showed on about half of a 29.7 kb genome in an EsViritu BAM. LGE keeps a layout of the rows and reuses it while you pan. It had made that layout with the reads of the first window first, where the window is the stretch of the genome on screen. Each read to the left of that window then took a row below all of that window's rows, so the band was as tall as the stack of reads in the first window. With Sort reads by on Position, its default, LGE now packs the reads in the order of their start positions, whichever window is on screen. The reads at the left of the genome start in the top row, and LGE still reuses the layout while you pan.

**Other sorts.** With Limit visible rows off and Sort reads by on Strand, Mapping Quality, Read Name, Insert Size or Base at Position, the reads of the window still go first so that they stay at the top. LGE now packs the reads again when the window moves, so the layout follows the window.

**A row limit.** With Limit visible rows on, the read stack of a bundle's alignment now keeps its rows for the reads of every window that a short pan reaches before LGE packs again, where it kept them only for the window on screen when it packed.

## EsViritu

**No time limit.** An EsViritu run now has no time limit, as 2026.10.16 did for PrimalScheme3, Olivar and varVAMP runs. Before, LGE stopped a run after the larger of one hour and one second for each 10 MB of input. That ended a sample of 25 million reads rich in SARS-CoV-2 while minimap2 was still aligning its reads. Cancel in the Operations Panel still stops a run. The change covers runs from the Tools menu and runs of `lungfish-cli esviritu detect`.

**The log names each step.** The log of an EsViritu row in the Operations Panel, which View Log opens, now names each EsViritu step when it starts. During each of EsViritu's three alignment rounds it also shows a running count of the reads that minimap2 has processed, such as `Aligning reads to viral references (round 1): 4,000,000 reads processed...`. Each round counts from zero. The row's detail and the viewer's progress overlay show the same line, and in a run of several samples it begins with `Sample 1/2 (<sample>): `. The progress line of `lungfish-cli esviritu detect` shows the same text. The bar moves when a step or a round starts and holds while a round counts, so the rising count is what shows that the run goes on. The lines `Screening for viral signatures...` and `Assembling viral contigs...` no longer appear, because the log follows the steps that EsViritu names and not keywords in its output.

| Part of the run | 2026.10.16 | 2026.10.17 |
|---|---|---|
| Quality filtering | `Quality filtering reads...` repeated whenever a line of fastp's report matched a keyword, seven times in a small test run | `Quality filtering reads...` once, then `Counting the reads that passed filtering...` |
| Each alignment round | No new line, so the row kept its last quality filtering line for the whole round | `Aligning reads to viral references (round 1)...` when the round starts, then `Aligning reads to viral references (round 1): 4,000,000 reads processed...` with a count that rises as reads are processed. Rounds 2 and 3 read the same way |
| The other steps | `Screening for viral signatures...`, `Assembling viral contigs...` and other lines that matched a keyword in EsViritu's output, many of them repeated | One line for each step, in run order. `Comparing the reads that viral references share...`, `Grouping viral references that share reads...` and `Selecting one reference for each group...` follow rounds 1 and 2. `Building consensus sequences...`, `Calculating coverage statistics...`, `Calculating coverage along each genome...`, `Assigning taxonomy to consensus sequences...`, `Writing the detection tables...`, `Building taxonomic profile...` and `Writing the EsViritu HTML report...` follow round 3 |

## Known issues

Known limit. A cancelled or failed EsViritu run keeps its working files, for example a partial BAM and the trimmed reads, in its folder under Analyses. They came to about 15 GB for a sample of 25 million reads. If the Operations Panel lists the stopped run when you next open the project, Remove Partial Output… on its row deletes the folder after a confirmation.

Known limit. A large sample rich in one virus can take an EsViritu run several hours, and the run has no time limit, so it goes on until it ends or you cancel it. The rising count in the log shows that it goes on, and Cancel in the Operations Panel stops it.

Known limit. The TaxTriage launch from the Tools > Classification menu still runs in the app, and Copy CLI Command on its row still copies a `lungfish-cli taxtriage` command whose `--output` is the app's own result folder, so running it writes into that folder again. Change `--output` to a new folder before you run it. A row for several samples offers no command. A later release changes the recorded command of a TaxTriage row.

Known limit. On that route, a sample that fails in a run of several samples still gets a completed TaxTriage entry, with the batch summary, in its source bundle's manifest.

Known limit. The record that the app writes for a TaxTriage sample still names `count/`, `fastp/` and `top/` files that LGE removes after the database build, so some names in it point at files that are gone. The record at the top of an app run of several samples also still files the classifier choice and the sample count as options you chose, and its sample steps carry no Nextflow version and no pipeline source. A later release moves the app's launch onto the shared record.

Known limit. The batch folder of a `lungfish-cli taxtriage run --project` run of several samples holds no aggregate `taxtriage-result.json`, which the app's own batch run writes and which the viewer and the row read. A later release settles that with the move of the app's launch onto the command.

Known limit. `build-db taxtriage --force` on a result that `taxtriage run --project` made still runs the earlier cleanup, which deletes the kept `top/` and replaces `taxtriage.sqlite` after the record named it, so the record then names a top report that is gone and the old digest.

The EsViritu change and the read pack change:

- `EsVirituProgressParser` in `Sources/LungfishWorkflow/Metagenomics/EsVirituProgressParser.swift` replaces the free function `parseEsVirituProgressLine`. It reads EsViritu's `Starting <step>...` lines and minimap2's `mapped <n> sequences` lines, counts the alignment rounds, and never lets the progress fraction fall. A step it does not know reads `Running the EsViritu step <name>...`. `EsVirituPipeline.detect` keeps one parser for each run in an `OSAllocatedUnfairLock`, and `EsVirituProgressParserTests` feeds it EsViritu's color-coded log lines.
- `EsVirituPipeline.detect` passes `timeout: .infinity` to `CondaManager.runTool`, which `CondaFamilyProcess.limit(seconds:)` reads as no limit, and the estimate from the input size is gone. With the old parser removed, `EsVirituPipeline.swift` falls from 855 to 819 lines, and its entry in `scripts/ratchets/file-size.baseline` follows.
- `requestBackgroundPack` and the test helper `testDrainPendingPack` no longer take a prioritized region. The pack reads `ReadPackCacheKey.prioritizedRegion`, so a cached layout is never ordered for a region that its key does not record. The key holds no region for unlimited rows with Position sort. Otherwise it holds the window's quantized range in the bundle path and the exact window in `prepareDetachedReadLayout`. `ReadLayoutCacheTests` gains `testPanningLeftWithUnlimitedRowsKeepsEarlierReadsInTheTopRows`, which waits for the real background pack, and `testPanningWithUnlimitedRowsUnderStrandSortRepacks`.

Fixtures and the module map:

- `Tests/Fixtures/golden/classifiers/esviritu/bundle-input-probe.txt` was recaptured with `golden.py capture --only classifiers` after a compare that differed only in this file. Its progress line now names each step and each of the three alignment rounds.
- `docs/architecture/MODULES.md` was regenerated after the new parser file and the read pack edits.
