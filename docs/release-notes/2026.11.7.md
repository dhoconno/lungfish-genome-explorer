# Lungfish 2026.11.7

Channel: Stable

Previous versioned release: v2026.11.6

Stable baseline: v2026.10.29

Dependency set: 2026.2

This Stable release brings the work since Stable 2026.10.29. It corrects results that Stable 2026.10.29 could show or make, such as TaxTriage read counts, Kraken 2 totals, the Mean Q of a merged FASTQ bundle and a few reads that Demultiplex Barcodes gave to the wrong sample. Some numbers and files change, so read What works differently before you compare with old results.

## What works differently

### Reads, pairs and counts

- **A FASTQ file that holds read pairs together with merged or single reads is read in full before it is paired.** With 50,000 or more pairs, `fastq deinterleave`, `map`, `assemble` and the classifiers could pair unrelated reads silently. A mixed file now stops `fastq deinterleave` with its counts, so split it again with `--unpaired` and rerun any analysis of it or of its R1 and R2 files. Imported reads need no new import.
- **Read pairs named like SRR123.1.1 and SRR123.1.2 now run as pairs.** They ran as single reads, so a Kraken 2 total was about double the number of pairs, a map showed no paired reads and a third file of unpaired reads was left out. Import and run such a sample again. Pairs named _1 and _2 still run as single reads.
- **A NAO-MGS read pair's second mate could be counted at the first base of a reference without being placed,** so Unique Reads read low. New imports are right. Import the original results file again and remove the old result.
- **Unique Reads showed 1 for rows that were never counted, and a dash now means not counted.** EsViritu and NVD exports write Unique Reads right after Read Count (Mapped Reads in NVD), empty where the table shows a dash, and NVD also writes Aln Length, so columns after them move right. Update a script that reads them by column number.
- **Kraken 2 and NAO-MGS counts.** With several samples picked in a Kraken 2 batch, the bar under the table and the sunburst gave a row's share of all their reads, and now give its own sample's. A sample with no total of its own showed the batch's total as its own, and now shows its own reads with no percent. A NAO-MGS result's Taxa count counts each taxon once, not once for each sample that has it.
- **A FASTA list's GC Content counts every base,** where it averaged its records. A protein record shows a dash for GC. A short peptide such as MKTAYGHSSRV now opens as protein, and a protein record with U, B, Z, J or O opens instead of stopping the whole file.
- **The Mean Q of a merged FASTQ bundle or an older Nanopore import in chunks is one figure for all its reads.** It averaged the Phred scores of the files, which could read 9 to 16 Phred units too high when one file was poor. It is now labeled Mean Q (error rate), so read it with Q20 and Q30.
- **Bundles of several files are read once and as pairs.** Mapping, classifying or running EsViritu on several files of one bundle counted each file as the whole bundle, so read counts and depth came out multiplied. A bundle that `lungfish-cli extract reads --by-id` makes from two `--source` files is now read as a pair, and operations that read one file refuse it in words, where they read the R1 file alone, so run them again on one file of the bundle.

### TaxTriage

- **TaxTriage read counts are corrected.** Since April 2026, a row could read 0 or too few Reads for an organism with more than one reference sequence, such as the eight segments of Influenza A, so a negative control could look clean. Reads now show TaxTriage's own count (# Reads Aligned). Open each result once in a project you can edit, which recounts it, and export again any table made from it. Extract Reads and BLAST Verify then use every reference of the organism, and Extract Reads skips duplicates, so it can write fewer reads than Reads shows. If a clean control with no organism has lost its report, Lungfish says so and hides the old counts, so import the run's folder again.
- **A TaxTriage result says when a negative control cannot be read as clean.** If a control failed, is missing, had a step the pipeline skipped after an error, or shares a name with another sample once spaces and symbols are removed, the viewer notes it, the organism matrix and results table say Not checked, not No or a blank cell, and the batch report says what to try. A control named like NTC 1 or Water (blank) keeps its flag. Export an earlier result again to correct it.
- **An imported TaxTriage run keeps its negative controls, run settings and database name.** A run imported by an earlier version reads Not recorded above its table, so import its folder again and export again anything made from the old import, which may say No for contamination.
- **A sample whose reads file has a symbol in its name now runs in TaxTriage,** where it stopped with no result. Two samples whose reads files shared a name in folders with a space in the path were both analyzed on the second file. Run such samples again.
- **A TaxTriage sample no longer takes another sample's BAM file.** Since July 2026, Stable 2026.10.29 among them, a result's database could give a sample whose own BAM was missing another sample's file, so its alignment view, Unique Reads and Extract Reads came from the other sample. A file now goes only to the sample whose name it starts with, then a dot, underscore or hyphen, and to the longest such name: `S1_2.bam` to S1_2, never to S1. A name with the sample's name in the middle, in another case or ending `.BAM` no longer fits, so such a sample shows no BAM, Unique Reads or alignment view until you rename the file, delete the result's `taxtriage.sqlite` and select the result again. The technical record says how to repair an older result.
- **Extract Reads on a raw TaxTriage result takes a sample's own BAM file,** not the reads of a sample whose name only begins the same way, such as S1 and S10. If the own BAM is not found, it reads the one `minimap2` file whose name fits and says which in the Log and on the command line. If two files fit, it stops and names both. If the result's database took the file, it says so.

### BLAST Verify

- **BLAST Verify asks NCBI for up to 500 records per read, not 5, when it judges by species.** A perfect match no longer reads Unsupported because its first five hits were lab vectors, and a row whose supporting reads all match other records equally well, such as a vector, reads Not specific, not Supported. Send a saved row again to refresh its badge.
- **A verdict showed under the wrong row.** Unless a Kraken 2 or FASTA list search is running, the pane shows the row's own search or nothing, and a late verdict names its sample.
- **Verify with BLAST in the Kraken 2 viewer and `lungfish-cli blast verify` ask NCBI for core_nt,** where the viewer asked for nt. NCBI already searched core_nt then, so no result changes.

### Demultiplex Barcodes

- **It no longer gives a few reads to the wrong sample.** With Cutadapt and a single-index kit or a custom barcode list, it moved a read to another barcode when the bases after its barcode looked like a second barcode, about 1 read in 120 with 12 barcodes of 8 bases and about 1 in 14 with 96. ONT Rapid Barcoding, ONT 16S Rapid Amplicon and M13 Universal Primers are unchanged.
- **A run that finds no barcode above chance now stops,** where earlier versions made sample files from chance matches. A lone real sample typically needs about 0.3% of ten thousand reads to stand above chance. A barcode that falls short is named in the summary as a possible chance match. If an earlier run of this kind sent most reads to Unassigned, run it again.
- **It splits reads whose index sits only in the read names,** as bcl2fastq and BCL Convert write it, with at most one mismatch in each index and both reads of a pair kept together, by itself when the names carry the indexes of two or more of the kit's barcodes, or when you choose Read Names. A read whose index matches two barcodes, differs in two or more bases, or has its i5 in the other orientation than most of the file goes to Unassigned. `lungfish-cli fastq demultiplex` with no engine named chooses this search from the read names, where it always used Cutadapt.
- **Detect Barcodes counts every read of a custom barcode list,** where it counted only the few that also held the barcode's reverse complement, and it reads the index in the read names of Illumina and Element files.
- **It records the bundle you picked.** For a subsample, a trimmed set or other derived reads, the record named a deleted temporary copy of the reads, no barcode bundle linked back to your bundle, and the command in the row showed `-o '<derived>'`, which cannot run. The record now names your bundle, each barcode bundle links back to it, and the command can be run again. Keep that bundle, since its barcode bundles read their reads from it.
- **A subset of ONT reads keeps its platform.** A bundle made by Subsample by Count, Quality Trim or another FASTQ operation lost its reads' ONT platform, so Demultiplex Barcodes started on the TruSeq Single Index Set A kit and Map Reads and Assemble could start on short-read settings for reads of 600 bases or fewer. All three now start on ONT settings.

### Viewer and figures

- **An exported figure counts depth under the window's cutoffs.** Its Depth strip counted every read and base whatever mapping-quality and base-quality cutoffs the window had set, so its depth could be larger than the window's. It now counts depth, and draws reads, under the cutoffs, and a line under the strip says which. With Hide high-gap sites on, a figure still draws those sites, and its row ends Completed with Warnings.
- **Opening another reference or alignment starts its read filters and consensus settings at their defaults,** where the Minimum alignment confidence and the other settings you made for one stayed set for the next, so reads showed pale and depth changed under a setting made elsewhere.
- **A result you open from the Operations panel, an import, an Inspector link or an accessibility tool now shows in the viewer,** where the viewer could keep the old result's numbers.

## What's new

- **A BLAST search stuck at NCBI no longer fails or holds up your work.** It waits on its row in the Operations Panel and its result comes back on its own, also after you reopen Lungfish. When NCBI is not taking new searches, the row and the BLAST pane say so and give the retry time.
- **The Results button opens a finished Call Variants run and a finished BLAST search,** and for a search saved in a Kraken 2 result it selects that result.
- **The Demux tab has a Demultiplex… button** that opens Demultiplex Barcodes with the plan's table, where you press Run.
- **Failures explain themselves.** Most commands that beeped say what is missing and what to try, failed runs and saves name the sample, and files and results that cannot be opened say what is wrong.
- **A classifier result dragged to another project keeps its record,** and Reassemble in a copied project uses the reads inside it.
- **A used-up AI quota says so** in Settings > AI Services, the AI Assistant and `lungfish-cli genotype ai-haplotyping`, with the provider's own words and billing link.
- **Illumina Amplicon Merge keeps only merged reads** and drops every pair that does not overlap. An import that dropped pairs ends as Completed with Warnings.
- **Smaller changes.** You can install `lungfish-cli` as a symbolic link on your PATH, and sorting or filtering the mapped contigs keeps your zoom.

## Things to know

- **A Kraken 2 sample with no total.** The percent columns of an exported table, and the percent column when you select several samples together, still read 0.
- **A bundle you imported.** Its Demultiplex still makes separate barcode bundles with no link back to it.
- **Platform records.** A barcode bundle that Demultiplex Barcodes makes keeps no platform in its own record, and `lungfish-cli fastq platform` shows none for it or for an earlier build's bundle. The Workflow Operations window reads only that record, so there such a bundle with ONT reads of 600 bases or fewer can start on Illumina settings.
- **Exported figures.** A figure still draws the reads of every read group, where the window draws the groups you selected, and draws a Depth strip and a reads track for each alignment track of a bundle, where the window shows one. Each strip is exact for its own track.
- **The mapped contig list.** The viewer can still return to the whole contig a few seconds after a mapping result opens, when the list has finished counting its reads, and when you change the alignment track in the Inspector.
- **The Results button.** For a BLAST search started from any other result or submitted directly, it selects the search's own folder, which has no viewer, so the viewer and the Inspector stay on the result you were looking at.
- **The ONT import sheet.** Total size adds the unclassified folder's files, and the Fluidigm and PacBio recipes read every FASTQ under the run folder, the unclassified folder included.
- **A sample's own BAM file is gone.** On a result with no sample list, if another sample's name starts with this one's followed by a dot, underscore or hyphen (S1 and S1_2), Extract Reads can take that sample's BAM when it has a name the pipeline does not give, and names the file only after the output is written. If it is not the sample's own, put the sample's own BAM back and rerun.
- **BLAST Verify.** On an EsViritu result without NCBI Taxonomy, such as an imported one, each read is judged by organism names alone. A read whose best match is another virus whose name starts with the same word, such as Rotavirus C for Rotavirus A or Alphapapillomavirus 10 for Alphapapillomavirus 1, counts neither for nor against the row, and a best match whose name starts with another word counts against it, even when it is the same virus under another name. A read tied at one score counts as supporting when any record tied with it is in the row's species, and NCBI returns a sample of the tied records, so a read can show 100% on one run and 99.3% on the next, or read Unsupported.
- **Demultiplex Barcodes.** A barcode not in your pool can still pass as a sample, in about one run in 1,000 for each one and more often in amplicon files, and the summary and the Operations Panel say so.
- **Earlier notes.** The limits in the 2026.10.29 notes still apply, apart from the known issues about mixed FASTQ files, imported TaxTriage results and TaxTriage negative controls, the sentences about reads tied at one score and about a search that stops after about 10 minutes.

### Known issues

These faults are in this Stable release. Preview 2026.11.8 fixes them, and the next Stable release will carry the fixes.

- **Known issue: grouped Result of several datasets.** With Output Strategy Grouped Result on two or more datasets of one format, Demultiplex Barcodes and every other FASTQ operation that offers it ran one command on the first dataset only, so the others were left out and the row ends Completed with no words. Run it again on all the datasets with 2026.11.8 or later, then delete the old result.
- **Known issue: IDT for Illumina UD Indexes plans.** In 2026.11.3 to 2026.11.7 the Demux tab wrote a plan for this kit from the built-in table, whose 24 rows are not the kit's 96 pairs, so a run of that plan could put reads under the wrong sample or in Unassigned. Run it again in 2026.11.8 or later with a Custom Definition that holds the i7 and i5 sequences from your index sheet.
- **Known issue: Viral Recon inputs with one sample name.** Two inputs that went by one name, such as two barcode01 bundles from two runs, two NTC bundles, or a bundle and its copy, ran as one sample, and each result showed the joined reads, with no words. Rename one sample in its metadata and run again with 2026.11.8 or later.
- **Known issue: trim of single reads.** A trim of single reads let fastp guess its adapter from the reads it saw first, and the guess changed with the order the reads were stored in, so adapter bases could stay on some reads. Trim the original reads again with 2026.11.8 or later, or name your adapter in the trim dialog, and redo any mapping or variant calling that used the trimmed reads.
- **Known issue: trim of read pairs.** A trim of read pairs gave fastp the pairs in the order the import stored them, so it could pick the wrong adapter and leave adapter bases on some reads. Trim the original reads again with 2026.11.8 or later, or name your adapter, and redo any mapping or variant calling that used them.
- **Known issue: trim of a processing recipe.** The fastp step of a recipe let fastp guess the adapter from the order Lungfish stored the reads in. If you exported reads from a Lungfish bundle and imported them with a recipe, import them again with 2026.11.8 or later.
- **Known issue: Viral Recon read order.** Viral Recon gave fastp the reads in the order the import stored them, so it could choose the wrong adapter and leave adapter bases on some reads, which can change allele frequencies, consensus bases and Nextclade amino-acid changes at primer sites. On one real run an allele frequency went from 0.868 to 0.418. Run Viral Recon again on the same samples with 2026.11.8 or later and compare the variant table and consensus.
- **Known issue: Viral Recon lineage tables.** A sample whose name began with another sample's name and a dot, such as S1.1 beside S1, put its Pangolin and Nextclade tables into S1's lineage files, so the Inspector could show the lineage and clade of S1.1 under S1. Run the batch again with 2026.11.8 or later, or keep from each sample's lineage files only the tables whose names start with that sample's own name and then .pangolin or .nextclade.
- **Known issue: iVar codon merge.** iVar could join two changes of one codon into one record shown at the lower frequency, and could leave small changes of a shared codon out, so a variant can be missing or shown too low. Call variants again with 2026.11.8 or later, or read MERGED_AF in a merged record for each position's own frequency.
- **Known issue: EsViritu inputs of one file name.** When a folder in the input or output path held a space, two inputs of one file name (reads.fastq.gz from two run folders, or a barcode sequenced on two runs) became one link to the second file, so the detections, read counts and abundances of that sample are wrong. Run the sample again with 2026.11.8 or later.
- **Known issue: one file of a multi-file bundle.** `lungfish-cli fastq demultiplex` on one file inside a multi-file bundle, such as a chunk of an ONT import or a merge, counted the reads of part of the run with no word, and the other `fastq` subcommands that read a file the same way did too. Give the bundle itself, not a file inside it, or use 2026.11.8 or later.
- **Known issue: a saved BLAST search on the wrong row.** A search saved from a FASTA list could show as the verdict of a TaxTriage row that held no BAM owner, taxon or accessions. Do not rely on a verdict on such a row. 2026.11.8 or later shows no saved search there.
- **Known issue: the chance-match notice.** When you demultiplexed several datasets with one command each, the Operations Panel row and its Log left out the line that a barcode may be a chance match and the limit about a barcode not in your pool. Run it again with 2026.11.8 or later to see them.
- **Known issue: varVAMP and Olivar size range.** varVAMP takes the size range as a target, so a design could hold an amplicon a few bases outside it, and Lungfish then refused the whole design. No setting avoids it. 2026.11.8 or later keeps the scheme and warns, naming each amplicon.
- **Known issue: Viral Recon names with a space.** viralrecon refuses a sample name or a read file name that holds a space, and the run failed after Nextflow started. Rename the sample and its files without spaces before you start, or use 2026.11.8 or later, which refuses first and says what to rename.
- **Known issue: two datasets with one name.** A FASTQ operation run on two datasets with one name, such as `reads.lungfishfastq` in two folders, failed in Per Input and Grouped Result because both wrote to one output folder. Rename one dataset, or use 2026.11.8 or later.
- **Known issue: Copy in a reference bundle view.** Command-C said "The viewer holds no sequence" and Edit > Copy was off while the bases showed. 2026.11.8 or later copies the selected bases.
- **Known issue: a run stopped for memory.** When the Mac ended a tool for memory, the row could say only that the tool failed. A status of 137 or the word Killed most likely means memory. 2026.11.8 or later says so on the routes that share the new words.

Four more known issues follow. Preview 2026.11.12 fixes the first three. Preview 2026.11.13 fixes the fourth.

- **Known issue: Viral Recon on single-end reads.** A single-end Viral Recon run let fastp guess the adapter from the first reads, so the same reads in another stored order could be trimmed differently. Preview 2026.11.12 fixes it. Viral Recon now names the Illumina adapters for single-end samples, so the same reads give the same trimmed result whatever order they are stored in. If you ran Viral Recon on single-end reads, run it again on the same samples with 2026.11.12 or later and compare the variant table and consensus.
- **Known issue: Demultiplex Barcodes with a kit that cannot be checked.** A run with a kit whose barcodes match about half of all reads or more by chance made sample files that may hold chance matches. Preview 2026.11.12 fixes it. When the barcodes of a kit match about half of all reads or more by chance, as the built-in Fluidigm Access Array kit does and as a very short custom kit can, the run now stops before it makes any sample file. Check each sample against your sample sheet, and note that a new run with 2026.11.12 or later makes sample files from such a kit only if you choose Keep Unchecked Samples.
- **Known issue: Exact Bare Barcode on barcodes in the read names.** Exact Bare Barcode searched the read sequences for barcodes that sit in the read names, so its sample files may hold chance matches. Preview 2026.11.12 fixes it. If the read names carry two or more of the barcodes of your list, the run now stops before it makes any file and points you to the engine Read Names, because a search of the read sequences finds those barcodes only by chance. Run Demultiplex Barcodes again with the engine Read Names, which reads the barcodes from the read names.
- **Known issue: a Custom Definition of dual indexes.** In this version, Demultiplex Barcodes with Cutadapt looked for each pair of barcodes of a Custom Definition of dual indexes anywhere in each read when you used Both Ends with no sample sheet, so a sample file could hold reads that carry no barcode. On real reads with no barcodes this put 8 to 11 reads in 100 into samples at error rate 0 and 74 to 82 in 100 at the default 0.15. This version shows no warning on such a result. Preview 2026.11.13 looks for each pair only at the two read ends, and it shows a warning on results that this version and the Previews up to 2026.11.11 made. Check each sample against your sample sheet, then run Demultiplex Barcodes again with 2026.11.13 or later. If your barcodes sit some bases in from the ends, set 5' Distance and 3' Distance to that many bases, and if the indexes are in the read names, use the engine Read Names.

Two more known issues follow. Preview 2026.11.13 fixes both.

- **Known issue: a Custom Definition of dual indexes at 5' End or 3' End.** Demultiplex Barcodes with a custom dual-index barcode file at 5' End or 3' End and no sample sheet left the reads of the reverse strand in Unassigned, and the sample files of such a run can hold reads that matched by chance, enough in an amplicon pool to fill a sample. Preview 2026.11.13 stops this setup and says why. Run such a split again at Both Ends with 2026.11.13 or later, and if your barcodes sit some bases in from the read ends, set 5' Distance and 3' Distance to that many bases.
- **Known issue: two rows of a Custom Definition of dual indexes that swap.** Demultiplex Barcodes at Both Ends with no sample sheet looked for the secondary sequence of each row just as you wrote it. When your definition listed the i5 primer's barcodes, which appear reverse complemented at the end of the read, and two rows had first barcodes that matched and secondary sequences that were reverse complements of each other, each within the error rate, those two samples got each other's reads with no warning. Run such a split again with Preview 2026.11.13 or later, which reads the secondary sequence the way your reads carry it or stops and says why.

Two more known issues follow. Preview 2026.11.8 does not fix them.

- **Known issue: Viral Recon lineage of September results.** Viral Recon results made with versions 2026.9.6 to 2026.9.52 gave every sample of a batch the Pangolin and Nextclade tables of every sample, so the lineage and clade listed first for a sample could belong to another sample, whatever the sample names. The app does not mark these results yet. Run the batch again with this version, or keep from each sample's lineage files only the tables whose names start with that sample's own name and then .pangolin or .nextclade.
- **Known issue: poly-G tails at import.** If you pick Trim Galore as the Compression Tool when you import FASTQ files, Trim Galore can also cut poly-G tails when its own check finds them, and the import record keeps Trim Galore's own answer, which the app does not show yet. A recipe you write yourself that leaves out `trimPolyG` lets fastp decide from the read names (for example, it cuts on NextSeq names). The built-in VSP2 and wastewater presets always cut poly-G tails.

Three more known issues follow. Preview 2026.11.10 fixes the first two and does not fix the third. Preview 2026.11.11 warns about the third.

- **Illumina amplicon genotyping, two samples with one file stem.** Two sample IDs that give one file name, such as `S-1` and `S--1`, or differ only in letter case, make the pair merge write one file for both, so the first sample's genotype is called from the second sample's reads, with no words. Fixed in Preview 2026.11.10 (GENOTYPE-MERGE-STEM, `fc7be5181`). Until you update, give each sample ID its own file stem and run an affected batch again.
- **Extract Reads on a TaxTriage result built before 2026.11.6.** The database can record a BAM of another name for a sample, such as `S1_2.bam` for S1, and Extract Reads writes that file's reads under S1. Fixed in Preview 2026.11.10 (BUILDDB-OLDER-DB-CLI, `2bfd0e02e`), which stops before it writes a read and names the repair. Until you update, run `lungfish-cli build-db taxtriage "<result folder>" --force` on such a result before you extract.
- **A TaxTriage result can show another sample's BAM.** In a TaxTriage result where a sample's own BAM file is missing, Lungfish can use another file in the minimap2 folder whose name fits the sample. The alignment view, its coverage, the Inspector, BLAST Verify and Extract Reads then read that file, and it may hold another sample's reads. Check the BAM line in the Inspector. If it is not the sample's own file, put that file back and run `lungfish-cli build-db taxtriage <result folder> --force`. Preview 2026.11.11 warns about it. When a sample's BAM is another file whose name fits the sample, the result's action bar (its tooltip holds the whole text), the Inspector and the BLAST Verify row say so and say what to do, and the file is still read.

Three more known issues of Demultiplex Barcodes follow. Stable 2026.11.14 fixes the loss of a sample's reads in the first two. Preview 2026.11.13 and later also fix the reads placed in another sample, and the next stable release will carry that fix. Runs that split the reads by the indexes in their read names, as the engine Read Names does, are not affected. To find a sample that was left out, check that the counts of the samples and of Unassigned add up to the read count of your input file.

- **Known issue: a single-index kit with a distance above 0.** Affected runs of Demultiplex Barcodes use the engine Cutadapt, which is the default, a 5' Distance or 3' Distance above 0, and TruSeq Single Index Set A or B or a Custom Definition with one barcode a row. Such a run could put some reads in another sample. On single-end reads it could also leave out all the reads of a sample. Neither came with a warning. Runs with both distances at 0, the default, do not have these faults. Stable 2026.11.14 no longer leaves out a sample, but only Preview 2026.11.13 and later also fix the reads placed in another sample, so run it again with Preview 2026.11.13 or later, and redo anything you made from the old sample files.
- **Known issue: a dual-index kit.** Affected runs of Demultiplex Barcodes use the engine Cutadapt, which is the default, and TruSeq HT Dual Index, Nextera XT Index Kit v2, or a Custom Definition made on one of them or on IDT for Illumina UD Indexes. With a 5' Distance or 3' Distance above 0, such a run could put some reads in another sample. On single-end reads, at any distance, it could leave out all the reads of a sample, and the run's counts left the missing reads out too. Neither came with a warning. Stable 2026.11.14 and Preview 2026.11.13 and later no longer leave out a sample. If both distances were 0, run it again with 2026.11.14 or later. If your file holds reads from both strands, run it again with Preview 2026.11.13 or later instead (see the line on reads from the other strand). If either distance was above 0, run it again with Preview 2026.11.13 or later, which also fixes the reads placed in another sample. Redo anything you made from the old sample files.
- **Known issue: reads from the other strand with a dual-index kit.** Demultiplex Barcodes with the engine Cutadapt, which is the default, at Both Ends with TruSeq HT Dual Index, Nextera XT Index Kit v2, or a Custom Definition made on one of them or on IDT for Illumina UD Indexes looks for each pair only in reads that start with the i7 index and end with the i5 index. If your file holds reads from both strands, as long reads of such a library do, the reads from the other strand go to Unassigned, so each sample holds only about half of its reads. The counts still add up to your input, and no warning says why Unassigned is so large. Stable 2026.11.14 does not fix this. Preview 2026.11.13 and later place the reads of both strands, and the next stable release will carry the fix. If such a run left many reads in Unassigned, run it again with Preview 2026.11.13 or later, and redo anything you made from the old sample files. Runs that split the reads by the indexes in their read names, as the engine Read Names does, are not affected.
