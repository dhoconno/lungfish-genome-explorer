# Lungfish 2026.10.12

Channel: Preview

Previous versioned release: v2026.10.11

Stable baseline: v2026.9.78

Dependency set: 2026.2

Preview builds are under rapid iterative development. Features may be incomplete, change quickly, or require additional feedback.

This release makes a cancelled run stop every program it started, fixes hangs when a tool writes a lot of output and when a Kraken2 result opens, repairs EsViritu installs that a newer polars broke, and reports progress for long FASTQ imports and large combined PrimalScheme panels.

## Cancelling stops the whole run

Cancelling a run in the Operations Panel now stops every program the run started. Before this release a cancelled TaxTriage or Viral Recon run could leave Nextflow and its Java processes running, and a cancelled BBTools step could leave its Java process behind. Each tool now starts in its own process group, and a cancel stops that group and every process it started. The same holds when you quit with a run in progress, when you press Control-C on a `lungfish-cli` command in Terminal, and when the command receives SIGTERM or SIGHUP.

## Hangs on large tool output

A tool could hang when it wrote more than 64 KB to both of its output streams, because only one stream was read until the tool ended. This could happen in VCF import, which runs bcftools, and in calls to Docker. VCF import and the Docker calls now run through the shared launcher, which reads both streams while the tool runs.

## Kraken2 results

Opening a Kraken2 result could freeze the app. To show the sample's name, the result view searched the folder that holds the project, often Documents, along with every folder inside it, on the main thread. It now searches only the project.

## FASTQ import progress

A long FASTQ import showed only "Launching import pipeline" until it finished, and then every step at once. Each step now appears in the Operations Panel as it starts and ends, so a slow import can be told apart from one that has stopped.

## Clearer failures

- A tool that exits with status -1 is now reported with exit status 255, as the shell reports it, instead of 16777215.
- A hifiasm assembly that writes no contig graph is now reported as a failed run. Before, it read as an assembly with no contigs.
- When minimap2 fails during a genotyping alignment, the run now fails. Before, samtools could still leave a BAM that looked valid.
- A read-group coverage step that runs out of time now says that it timed out and gives the time limit, and a failing `samtools view` reports its own error.
- Storage deduplication no longer crashes when another program holds open a file on a device whose number has its top bit set.

## EsViritu installs

A fresh install of EsViritu 1.3.3 could pull in polars 2, and every EsViritu run then failed while it built the assembly table. EsViritu now installs from an explicit list of the 191 packages of a working install, with polars 1.44.2. On first launch this release reinstalls the EsViritu environment on a Mac whose installed packages differ from that list. The same check repairs Olivar and varVAMP environments whose packages differ from their locks. Provenance records now give EsViritu's own version, 1.3.3, instead of the version of its Python.

## Large combined PrimalScheme panels

A combined PrimalScheme panel runs as one long native process, and the Operations Panel showed one unchanging message for all of it. It now reports which alignment PrimalScheme is searching for primer candidates and how many amplicons the panel holds, so a long run can be told apart from one that has stopped.

PrimalScheme skips any amplicon whose primers would form a dimer with primers already in the pool, so a panel built from many alignments can finish successfully with gaps. On the Overview, each reference of a combined panel with less than 90% coverage now carries a warning that names this cause. The Primer Design dialog now says what a combined design means for each engine, and the PCR primer design guide gains a section with measured runs of 3, 10 and 40 alignments at 2, 4 and 6 pools.

## For contributors

The process launcher:

- `NativeToolRunner`, `CondaManager.runTool`, `ProcessManager`, `LungfishCLIRunner` and `CLISubprocessTransport` now start every tool through one primitive, `ToolProcess` in LungfishCore. `docs/contracts/RUNNING-A-TOOL.md` describes it.
- `scripts/ratchets/process-spawn.sh` counts the files that still create a raw `Process()` and the raw `terminate()` calls. The counts fell from 74 files and 31 calls to 56 and 15.
- 103 tool output goldens in `Tests/Fixtures/golden/tools/` hold the argv, exit code, stdout and named outputs of each external tool, run through the runner that serves it. `ToolOutputGoldenTests` runs in the conformance tier, and `LUNGFISH_REQUIRE_TOOLS=1` turns a missing tool into a failure.

Testing and release:

- The golden comparison masks the macOS version, the macOS build and the active core count. It runs from a locked environment in `/Users/Shared/lungfish-golden` on a self-hosted runner, and `docs/contracts/MACHINES.md` says which Mac builds which channel.
- Unit tests no longer install databases into real managed storage. `ManagedStorageTestWriteGuard` stops a test process that is about to download, update or install a metagenomics database under a real channel root, and the NAO-MGS import tests use a local taxonomy fixture.
- The pre-push hook and `release.py package` wait for a unit-tier run that is already going on the same code instead of starting a second one.
- The Nextflow tool goldens set `NXF_DISABLE_CHECK_LATEST=true`, so a newly published Nextflow release no longer changes their stderr.

## Dependency versions

Dependency set 2026.2 is unchanged. EsViritu 1.3.3 now installs from an explicit lock, and `lungfish-cli tools update` reinstalls an environment whose packages differ from its lock. All other managed tool, optional pack, pipeline, database, and bootstrap versions are unchanged from v2026.10.11.
