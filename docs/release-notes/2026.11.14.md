# Lungfish 2026.11.14

Channel: Stable

Previous versioned release: v2026.11.7

Stable baseline: v2026.11.7

Dependency set: 2026.2

This Stable release is a patch of Stable 2026.11.7. It fixes one fault of Demultiplex Barcodes, which could leave out all the reads of a sample while the counts looked complete. It carries no other fix, so the faults named under Things to know stay until the next stable release. If you ran Demultiplex Barcodes in Lungfish Genome Explorer (LGE) 2026.11.7 or in any version from 2026.8.1 up to Preview 2026.11.12, read What works differently and check your counts.

## What works differently

### Demultiplex Barcodes

- **A sample of a large run is no longer left out.** In 2026.11.7, a sample whose file grew past about 200 KB compressed could come out empty. The run still ended without an error, and its counts showed only the reads it kept, so it looked complete. A sample of a few thousand short reads can pass that size. The run now writes such files uncompressed and compresses them at the end, so it needs free disk space for the uncompressed reads, takes longer, and cannot be cancelled while it compresses.
- **Who is affected.** Runs with the engine Cutadapt, which is the default, on single-end reads. The kit is a dual-index kit (TruSeq HT Dual Index, Nextera XT Index Kit v2, or a Custom Definition made on one of them or on IDT for Illumina UD Indexes) at any distance, or a single-index kit (TruSeq Single Index Set A or B, or a Custom Definition with one barcode a row) with 5' Distance or 3' Distance above 0. Runs that split the reads by the indexes in their read names, as the engine Read Names does, are not affected. A single-index kit with both distances at 0, the default, is not affected either. The same fault is in every version from 2026.8.1 to 2026.11.12, so check older runs made with them too.
- **What to do.** To find a sample that was left out, add up the counts of the samples and of Unassigned, and compare the total with the read count of your input file itself. The run's own Input reads left the missing reads out too, so it cannot show the loss. If the total is lower, or a sample you expect holds no reads, run Demultiplex Barcodes again and redo anything you made from the old sample files. If both distances were 0, run it again with this version. If either distance was above 0, or your file holds reads from both strands with a dual-index kit, run it again with Preview 2026.11.13 or later, because this version can still put reads in another sample or leave the reads of the other strand in Unassigned (see What stays until the next stable release). This version does not mark an older result as affected, so the check is yours.

## Things to know

### What stays until the next stable release

- **A read in the wrong sample at a distance above 0.** This patch does not fix it. With 5' Distance or 3' Distance above 0, a run with the engine Cutadapt and one of the kits above could put some reads in another sample, with no warning. Adding up the counts cannot find it. Preview 2026.11.13 fixes it, and the next stable release will carry the fix. If you ran with a distance above 0, run it again with Preview 2026.11.13 or later, which also stops a sample from being left out, and redo anything you made from the old sample files. Download it from the [Releases](https://github.com/dhoconno/lungfish-genome-explorer/releases) page, where it is marked Pre-release. It installs beside Stable.
- **Reads from the other strand with a dual-index kit.** Demultiplex Barcodes with the engine Cutadapt, which is the default, at Both Ends with TruSeq HT Dual Index, Nextera XT Index Kit v2, or a Custom Definition made on one of them or on IDT for Illumina UD Indexes looks for each pair only in reads that start with the i7 index and end with the i5 index. If your file holds reads from both strands, as long reads of such a library do, the reads from the other strand go to Unassigned, so each sample holds only about half of its reads. The counts still add up to your input, and no warning says why Unassigned is so large. Stable 2026.11.14 does not fix this. Preview 2026.11.13 and later place the reads of both strands, and the next stable release will carry the fix. If such a run left many reads in Unassigned, run it again with Preview 2026.11.13 or later, and redo anything you made from the old sample files. Runs that split the reads by the indexes in their read names, as the engine Read Names does, are not affected.
- **Viral Recon with another caller, or on Nanopore reads.** A Viral Recon run that names another variant caller in Extra parameters, such as `--variant_caller bcftools`, the example the field shows, writes its variant calls, consensus and lineage tables to folders that this version does not read. LGE then shows no variant track, consensus or lineage tables (Pangolin and Nextclade) for its samples, and no message says that they are missing. A run that names only another consensus caller, such as `--consensus_caller ivar`, shows its variant track but no consensus or lineage tables. A run on Nanopore reads shows none of these, and no alignment or coverage either. A default Illumina run, with iVar variants and a BCFtools consensus, is not affected. The run's own files are still in its results folder. Stable 2026.11.7 has the same fault, and this patch does not fix it. Preview 2026.11.16 reads each output from the folder the run used and says in the Inspector which variant, consensus or lineage output a sample lacks, and the next stable release will carry the fix. It reads them when a run ends, so opening an old result in it does not add them. If you ran Viral Recon this way, run it again with Preview 2026.11.16 or later. The run's consensus and lineage tables can be read in its results folder.
- **Two FASTQ bundles named like the two reads of one sample.** TaxTriage, Classification (Kraken2) and EsViritu run two FASTQ bundles whose names differ only by an ending of _1 and _2, or _R1 and _R2, as the two reads of one paired sample. So two files named like Swab_1 and Swab_2 from two specimens ran as one sample named Swab. The run ends with no error and shows one result, with the organisms of both specimens mixed together and no result for either specimen alone. If one of the two was marked as a negative control, the mark is lost, so it no longer serves as a control. When the two hold different numbers of reads, the extra reads of the larger one are left out with no message. Classification and EsViritu do this in a batch of several bundles too, so Sample_1 and Sample_2 of a batch became one sample named Sample. If a third bundle with the shorter name, such as Swab, was chosen as well, one of the three was left out of the run, and in a command line batch the same happened to a loose read file such as Swab.fastq beside Swab_1.fastq and Swab_2.fastq. A single bundle that holds both reads of a pair is not affected. Two bundles join when their names end in _1 and _2, _R1 and _R2, or _R1_001 and _R2_001. Classification and EsViritu also join names that end in .R1 and .R2 or -R1 and -R2, and they match every ending in upper or lower case. Bundles whose names end in none of these are not affected. You can spot such a result by a sample name that lacks the ending of its bundles, such as Swab from Swab_1 and Swab_2. Stable 2026.11.7 has the same fault, and this patch does not fix it. Preview 2026.11.16 runs each FASTQ bundle as its own sample under its whole name and leaves out no file, and the next stable release will carry the fix. If you ran one of these tools on bundles named this way, run it again with Preview 2026.11.16 or later. In 2026.11.14, rename the bundles so that their names no longer end in _1, _2, _R1, _R2, _R1_001, _R2_001, .R1, .R2, -R1 or -R2 before you run them together, or run each bundle alone.
- **Read files of one name in several folders, in a command line batch.** A batch command of Classification (Kraken2) or EsViritu given mixed file lists could pair reads from two specimens. When read files of the same names, such as S_R1.fastq.gz and S_R2.fastq.gz, sit in two folders and the list names the folders in a different order for R1 and for R2, the run takes R1 from one folder and R2 from the other as one pair. It can also happen with whole folders when one folder holds a compressed R1 and a plain R2 and the other folder the reverse. The run ends with no error, and each such sample mixes the reads of two specimens. TaxTriage is not affected, and neither is a batch in which the files of each sample name, such as S in S_R1 and S_R2, sit in only one folder. You can spot such a run by samples named like S_1 and S_2, made from files of one name in two folders. Stable 2026.11.7 has the same fault, and this patch does not fix it. Preview 2026.11.16 pairs R1 and R2 only within one folder, and the next stable release will carry the fix. If you ran such a batch, run it again with Preview 2026.11.16 or later. In 2026.11.14, run one folder per command.
- **A short second read file in a paired run.** A short second read file was cut without warning. When two loose read files given as a pair held different numbers of reads, TaxTriage, Classification (Kraken2) and EsViritu ran them with no check. In TaxTriage the reads past the end of the shorter file are left out of the result, and the only sign is a warning in the fastp log in the run's results folder. A file that was cut short, or subsampled or written on its own, can cause this. Stable 2026.11.7 has the same fault, and this patch does not fix it. Preview 2026.11.16 stops such a run before it starts and names both files and both counts, and the next stable release will carry the fix. If you ran two loose read files as a pair, run it again with Preview 2026.11.16 or later. In 2026.11.14, compare the read counts of the two files before a paired run (a FASTQ file usually has four lines for each read), and if they differ, run each file as single reads.
- **Two read files of a pair whose reads are in a different order.** Two read files of a pair whose reads were in a different order ran with mismatched mates and no warning. When two loose read files given as a pair to TaxTriage, Classification (Kraken2) or EsViritu hold the same number of reads in a different order, the run pairs the first read of one file with the first read of the other, and so on, so each pair joins two unrelated reads. The run ends with no error, and nothing in its result shows the fault. This can happen when one file was sorted, shuffled or subsampled on its own, when a tool wrote one file in another order, when the two were cut to one size with different settings, or when the lane files of R1 and R2 were joined in a different order. Files as the sequencer or SRA delivers them are in step. Stable 2026.11.7 has the same fault, and this patch does not fix it. Preview 2026.11.16 compares the read names of each pair and stops such a run before it starts, and the next stable release will carry the fix. If you ran a pair made this way, run it again with Preview 2026.11.16 or later. In 2026.11.14, run each file as single reads, or make the pair again from the original files with a step that keeps both files in the same order.
- **Two read files of a pair on other routes.** The two faults above, a short second read file and reads in a different order, also reach other steps that take two loose read files as a pair. `lungfish-cli map --paired`, `lungfish-cli assemble --paired` and `lungfish-cli workflow run nf-core/viralrecon` with your own sample sheet run such a pair with no check of its read counts or read names, so the reads past the end of the shorter file can be left out, or reads of different fragments paired, with no warning. An import of two loose files with a recipe, in the app or with `lungfish-cli import fastq --recipe`, can run fastp on the pair before any check, with the same result. The plain import with no recipe, in the app and with `lungfish-cli import fastq`, and plans for the Linux executor made with `lungfish-cli import fastq --write-plan`, with or without `--staged-reads`, do not compare read names, so a pair whose reads are in a different order becomes a FASTQ bundle of mismatched mates. Every later analysis of that bundle then pairs the wrong reads, and nothing warns. `lungfish-cli fastq interleave` writes such a pair into one file the same way. Stable 2026.11.7 has the same faults, and this patch does not fix them. Preview 2026.11.16 checks the read counts and read names on each of these routes before any tool starts, and the next stable release will carry the fix. `lungfish-cli fastq ingest --pair`, `lungfish-cli debug fastq-ingest --pair`, `lungfish-cli fastq ribodetector` and `lungfish-cli fastq deacon-ribo` given two files also pair the reads by position, as in Stable 2026.11.7. Preview 2026.11.16 does not check them. Preview 2026.11.17 does, and the next stable release will carry that fix too, so run samples made this way again with Preview 2026.11.17 or later. 12S matching of a pair inside a FASTQ bundle whose read names carry no mate number also pairs the reads by position, and its result holds no warning. Preview 2026.11.17 still pairs them by position and adds the warning to the result. If such a bundle was imported from two files out of step, import the original files again as a pair with Preview 2026.11.17 or later, which stops on such a pair, and run 12S matching on the new bundle. If you imported two loose read files as a pair, import them again with Preview 2026.11.16 or later, and then redo what you made from the bundle. Run other affected samples again with Preview 2026.11.16 or later, and samples made with the four commands above with Preview 2026.11.17 or later. In 2026.11.14, compare the read counts of the two files before a paired step and make sure neither file was sorted, shuffled or subsampled on its own, or import and run each file as single reads.
- **A CZ ID report saved as a tab file imported with 0 reads.** CZ ID writes its taxon reports, the Report Table and the bulk Sample Taxon Reports, as CSV files. LGE refuses such a file with a wrong reason, that its taxon ID and rank columns are missing when they are there. A tab copy of the same report, as Excel or Numbers saves it, imports with no error and no warning, but every taxon has 0 reads and rank U, so the table and the sunburst show none of them. Anyone who imported a CZ ID report this way is affected. You can spot such a result by a taxon table and a sunburst with no taxa in them, or by NT Reads 0 on every row of `lungfish-cli cz-id summary`. Stable 2026.11.7 has the same fault, and this patch does not fix it. Preview 2026.11.16 reads the CSV and its tab copies with true read counts, and the next stable release will carry the fix. If you imported a CZ ID report, import it again with Preview 2026.11.16 or later. 2026.11.14 has no safe way to import CZ ID's own reports, so import them with Preview 2026.11.16 or later.
- **A genotype comment lost on Quit with no window open.** When a comment or review in a genotype result is still waiting for its workbook and no project window is visible, Quit closes Lungfish without asking, and the comment or review is lost with no message. Keep the project window open and in view until the workbook has updated before you quit. Fixed in Preview 2026.11.17.
- **An older TaxTriage result loses its top folder.** Opening or rebuilding a TaxTriage result from an older run or an import deletes the folder named top inside it, so a sample whose rows came only from that folder cannot be counted again. Keep a copy of the original TaxTriage run folder, and import it again with Preview 2026.11.17 or later. Fixed in Preview 2026.11.17.
- **A TaxTriage row that sums several strains.** For a row whose organism TaxTriage summed over several strains, Unique Reads, Extract Reads and BLAST Verify use the first strain's references only, so Unique Reads can read low, and a reference listed under two organisms in one sample counts in both rows. Preview 2026.11.17 counts such a result again when you open it in a project you can edit, while its report files are still in the result folder. Fixed in Preview 2026.11.17.
- **NAO-MGS Unique Reads can read low.** The NAO-MGS import counts a read as a PCR duplicate when it shares its place, strand and length with a read of a different pair, so Unique Reads can read low and PCR duplicates high. Import the results file again with Preview 2026.11.17 or later. Fixed in Preview 2026.11.17.
- **`lungfish-cli markdup` totals count alignment records.** Its total and duplicate share count secondary and supplementary records as reads, so a BAM with 2 primary reads, 1 secondary and 1 supplementary record reads 4 reads where it holds 2. Run it again with Preview 2026.11.17 or later to read the true counts. Fixed in Preview 2026.11.17.
- **Verify with BLAST… can count a record of another species by its name.** With NCBI Taxonomy installed, a check of a NAO-MGS, EsViritu, TaxTriage or NVD row counts a read as supporting when its best match is a record of another species whose name holds the row's name, such as Woolly monkey hepatitis B virus on a Hepatitis B virus row. Read the top hits of a row that reads Supported or Mixed, or run the check again with Preview 2026.11.17 or later. Fixed in Preview 2026.11.17.
- **A sample metadata import replaces a result's run record.** Importing sample metadata into a result that has its own record, such as a 12S or EsViritu result, writes the import's record over the run's, so the run's command, times and tool versions are gone. Run the analysis again for a full record. Fixed in Preview 2026.11.17.
- **`lungfish-cli fastq ingest` can drop an extraction's record.** When it replaces a FASTQ file in place in a folder of extracted reads that already has a record, the folder's record loses the extraction's source file, its digest and the per-taxon read counts. Extract the reads again if you need that record. Fixed in Preview 2026.11.17.
- **Fluidigm datasets show quality figures that no instrument measured.** Fluidigm sample and amplicon datasets, whose reads are built from sequence counts, show Mean Q 40, Q20 and Q30 of 100 percent, a read table Mean Q of 40.0 and flat quality charts, and so do datasets made from them by a filter, a trim, a demultiplex, a merge or an extraction. The Assembly dialog can preselect Nano HQ from them. Read no quality figure from these datasets or from any dataset made from them. Preview 2026.11.17 reads "No quality scores" for them, except for a dataset that Merge into New Bundle made with other reads ahead of them. Fixed in Preview 2026.11.17.
- **Est. Coverage in the Inspector assumes reads of 150 bp.** For a one-sequence alignment, the Inspector's Est. Coverage multiplies the mapped reads by an assumed 150 bp, so for long reads it can be off by a large factor and disagrees with the mean depth of the mapping table. Read the depth from the mapping table. Fixed in Preview 2026.11.17.
- **Demultiplex Barcodes at Both Ends with two distances can run for hours.** With a dual-index kit at Both Ends and both 5' Distance and 3' Distance above 0, the run writes one Cutadapt search for every pair of offsets with no limit, and can stay at "[ 10%] Running cutadapt demultiplexing..." for hours. Keep the distances small, or cancel a run that does not move. Fixed in Preview 2026.11.17.
- **A very large distance can crash Demultiplex Barcodes.** The 5' Distance and 3' Distance fields take any whole number, and a run builds one search for every offset up to it, so a very large distance can crash the run or use up the Mac's memory. Type a distance no longer than the reads. Fixed in Preview 2026.11.17.
- **A run from the Demux tab uses the kit's sequences and default settings.** A plan run started from the Demux tab uses the kit's barcode sequences and the default Min Overlap and Allow Indels, whatever the tab shows. If you changed any of them in the tab, check the settings in the run's record before you use its samples. Fixed in Preview 2026.11.17.
- **A typed impact=HIGH filter can count one tool's variants.** In a file with both CSQ_IMPACT and ANN_IMPACT, a typed impact=HIGH filter counts one tool's variants. Filter again with Preview 2026.11.17 or later. Fixed in Preview 2026.11.17.
- **A typed gene= filter reads one gene key only.** With CSQ and ANN annotations, or a GENE key beside them, it counts one source's variants, and in a file whose only gene key is SYMBOL it counts none. Filter again with Preview 2026.11.17 or later. Fixed in Preview 2026.11.17.
- **GenBank export can spell feature keys in lower case.** GenBank files exported from GFF3, BED or an edited annotation spell feature keys in lower case, such as cds. Export them again with Preview 2026.11.17 or later. Fixed in Preview 2026.11.17.
- **FASTQ drawer:** sample names, kits, the demultiplexing plan and primer-trim settings that you type and do not save with Save are lost, with no message, when you select another dataset, close the project window or quit Lungfish. Press Save before you do any of these. Fixed in Preview 2026.11.17.
- **The annotation drawer can leave out the annotations of a track with no word.** When the annotation database of a track in a reference is missing or cannot be read, or the track has none, the drawer shows only the other tracks, so its count is lower and a search in it does not find the genes of that track. A reference whose tracks have no database at all reads 0 annotations. With no filter typed, compare the count in the drawer with the Annotations line in the Inspector, and if the drawer reads fewer, import the annotations again. Fixed in Preview 2026.11.17.
- **A FASTQ operation's new dataset shows the quality of the reads before they were stored.** Its Mean Q and quality charts describe the reads before Lungfish stored them, which raises every score of 0 or 1 to 2, so if the reads held scores of 0 or 1, they can read a little lower than the stored reads. Q20 and Q30 are not changed. To measure the stored reads, run the operation again with Preview 2026.11.17 or later. Fixed in Preview 2026.11.17.
- **Merge Overlapping Pairs writes quality scores that no instrument measured.** The app's Merge Overlapping Pairs keeps one copy of each read sequence and writes a quality score of 40 on every base, so the dataset's Mean Q, Q20, Q30 and read count are not measured, and reads that did not merge lose their mate pairing. Merge the original read pairs again with Preview 2026.11.17 or later, and redo what you made from the merged reads. Fixed in Preview 2026.11.17.
- **Genotyping can reuse a sample whose saved files were overwritten.** A full-length ONT MHC rerun that reuses earlier results checks only that a sample's saved files exist, so a later run with other settings, stopped part way, can leave files whose calls do not match the run's settings. Run the genotyping again without reusing earlier results. Fixed in Preview 2026.11.17.
- **Extract Reads from a Kraken2 result can fill the Mac's memory.** Extracting a taxon with many reads, such as the host or the root of the tree, keeps every matched read name in memory inside LGE, so at about 20 million reads it can take all of a 16 GB Mac's memory. Extract a smaller taxon, or extract on a Mac with more memory. Fixed in Preview 2026.11.17.
- **A large demultiplex by Read Names or Exact Bare Barcode can use more memory than the Mac has.** Demultiplex Barcodes with the engine Read Names or Exact Bare Barcode keeps a line for every read in memory until the run ends, about 560 bytes a read in the one test measured, with Read Names, so a run of 40 million reads (20 million pairs) can need about 22 GB. On a 16 GB Mac such a run can be very slow or end for memory. Split the input into smaller files, or run it on a Mac with more memory. Fixed in Preview 2026.11.17.
- **A large file can fill the Mac's memory.** Map Reads on a Nanopore run imported as a folder, the check after a download from Search SRA…, Merge Into New Bundle…, Copy to Clipboard or Share… in Extract Reads, and a FASTQ operation such as a trim when it stores its new dataset keep the whole file in memory while they read it. When the files are larger than the Mac's memory, the Mac can slow down a great deal, or run out of memory and stop the run. Results are not changed. Until you update, close other apps before such a step, and download one run at a time. Fixed in Preview 2026.11.17.
- **An export can leave out an annotation track with no word.** When the annotation database of a track in a reference is missing or cannot be read, GFF3 and GenBank export, the drawer's table export and extraction to a new bundle write the other tracks only, and Go to Gene… does not find a gene on that track. If it is the first track, iVar variant calling gives calls with no codon or amino-acid change. If the drawer reads fewer annotations than the Annotations line in the Inspector, import the annotations again, then export or call again. Fixed in Preview 2026.11.17.
- **Extract to a new bundle can leave out an annotation.** It can leave out an annotation that shares its name, type and exact position with another, such as two modification sites on one codon. The source bundle keeps every annotation, so extract the region again with Preview 2026.11.17 or later. Fixed in Preview 2026.11.17.
- **GFF3 and GTF import can drop a feature.** Importing a GFF3 or GTF file drops a feature that shares its name, type and position with another, such as an exon that two transcripts share, and the track's count leaves it out. Exports of that track, and bundles extracted or merged from it, lack it too. Import the source file again with Preview 2026.11.17 or later, then remove the old track. Fixed in Preview 2026.11.17.
- **A transcript or CDS from a GTF annotation track can extract, copy or translate without its exons joined.** A track imported before Preview 2026.11.17 gives a transcript with its introns and a CDS as one exon's piece, with no word. Attach the GTF file again with Preview 2026.11.17 or later before you extract, copy or translate from it. Fixed in Preview 2026.11.17.
- **A spliced feature split after a GFF3 import.** When a GFF3 file names one feature on several lines with one ID, as Export Annotations as GFF3 writes an mRNA, misc_RNA or misc_feature of several parts, a new bundle made from it or an attach in the Import Center makes one row for each part, with no warning. An mRNA of three exons then shows as three rows of the same name, and Extract or Copy as FASTA of a row gives only that exon. Coding sequences (CDS) are not affected, and the file itself is right for other tools. If you made a bundle or a track from such a file, import the file again with Preview 2026.11.17 or later. Fixed in Preview 2026.11.17.
- **Some feature types exported as genes.** Export Annotations as GFF3, and export to GenBank, write a feature whose type Lungfish does not list, such as misc_RNA, lnc_RNA, snRNA, snoRNA, miRNA, precursor_RNA, rep_origin or LTR, as a gene, with no warning. The bundle keeps the right type, but the exported file, and a bundle made again from it, count those features as genes. Check the feature types in an exported file before you count or filter by type, or export again with Preview 2026.11.17 or later. Fixed in Preview 2026.11.17.
- **A filter can stop applying after you pick other samples.** In a Kraken2 or EsViritu result with several samples, picking other samples in the Inspector can leave your text in the filter field while the table lists every row. Type the filter again after you pick samples. Fixed in Preview 2026.11.18.
- **The limits of 2026.11.7.** Every limit under Things to know on the 2026.11.7 page still applies.

### The other known issues of the 2026.11.7 page

This patch fixes none of these. The [page of Stable 2026.11.7](https://github.com/dhoconno/lungfish-genome-explorer/releases/tag/v2026.11.7) holds the words of each one, who is affected and what to do. The names follow, grouped by the Preview that fixes them. The next stable release will carry the fixes.

- **Fixed in Preview 2026.11.8.** Grouped Result of several datasets, IDT for Illumina UD Indexes plans, Viral Recon inputs with one sample name, trim of single reads, trim of read pairs, trim of a processing recipe, Viral Recon read order, Viral Recon lineage tables, iVar codon merge, EsViritu inputs of one file name, one file of a multi-file bundle, a saved BLAST search on the wrong row, the chance-match notice, varVAMP and Olivar size range, Viral Recon names with a space, two datasets with one name, Copy in a reference bundle view, and a run stopped for memory.
- **Fixed in Preview 2026.11.10.** Extract Reads on a TaxTriage result built before 2026.11.6, and Illumina amplicon genotyping, two samples with one file stem.
- **Fixed in Preview 2026.11.12.** Viral Recon on single-end reads, Demultiplex Barcodes with a kit that cannot be checked, and Exact Bare Barcode on barcodes in the read names.
- **Fixed in Preview 2026.11.13.** A Custom Definition of dual indexes, a Custom Definition of dual indexes at 5' End or 3' End, and two rows of a Custom Definition of dual indexes that swap.
- **No fix named on the page.** Viral Recon lineage of September results and poly-G tails at import, which Preview 2026.11.8 does not fix. A TaxTriage result can show another sample's BAM, which Preview 2026.11.11 warns about.

## Updating

Choose Check for Updates… in the app menu to install this release. It adds no tool to install on the Mac. It also brings every change of Stable 2026.11.7, so if you update from an older Stable, read the [page of Stable 2026.11.7](https://github.com/dhoconno/lungfish-genome-explorer/releases/tag/v2026.11.7) before you compare with old results. If you run Preview 2026.11.13 or later, you already have the fix of this release and the fix of the wrong-sample faults.
