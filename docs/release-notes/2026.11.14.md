# Lungfish 2026.11.14

Channel: Stable

Previous versioned release: v2026.11.7

Stable baseline: v2026.11.7

Dependency set: 2026.2

This Stable release is a patch of Stable 2026.11.7. It fixes one fault of Demultiplex Barcodes, which could leave out all the reads of a sample while the counts looked complete. It carries no other fix, so the faults named under Things to know stay until the next stable release. If you ran Demultiplex Barcodes in Lungfish Genome Explorer (LGE) 2026.11.7 or in any version from 2026.8.1 up to Preview 2026.11.12, read What works differently and check your counts.

## What works differently

### Demultiplex Barcodes

- **A sample of a large run is no longer left out.** In 2026.11.7, a sample whose file grew past about 200 KB compressed could come out empty. The run still ended without an error, and its counts showed only the reads it kept, so it looked complete. A sample of a few thousand short reads can pass that size. The run now writes such files uncompressed and compresses them at the end, so it needs free disk space for the uncompressed reads, takes longer, and cannot be cancelled while it compresses.
- **Who is affected.** Runs with the engine Cutadapt, which is the default, on single-end reads. The kit is a dual-index kit (TruSeq HT Dual Index, Nextera XT Index Kit v2, or a Custom Definition made on one of them or on IDT for Illumina UD Indexes) at any distance, or a single-index kit (TruSeq Single Index Set A or B, or a Custom Definition with one barcode a row) with 5' Distance or 3' Distance above 0. Runs that split the reads by the indexes in their read names, as the engine Read Names does, are not affected. A single-index kit with both distances at 0, the default, is not affected either. The same fault is in every version from 2026.8.1 to 2026.11.12, so check older runs made with them too.
- **What to do.** To find a sample that was left out, add up the counts of the samples and of Unassigned, and compare the total with the read count of your input file itself. The run's own Input reads left the missing reads out too, so it cannot show the loss. If the total is lower, or a sample you expect holds no reads, run Demultiplex Barcodes again and redo anything you made from the old sample files. If both distances were 0, run it again with this version. If either distance was above 0, or your file holds reads from both strands with a dual-index kit, run it again with Preview 2026.11.13 or later, because this version can still put reads in another sample or leave the reads of the other strand in Unassigned (see What stays until the next stable release). This version does not mark an older result as affected, so the check is yours.

## Things to know

### What stays until the next stable release

- **A read in the wrong sample at a distance above 0.** This patch does not fix it. With 5' Distance or 3' Distance above 0, a run with the engine Cutadapt and one of the kits above could put some reads in another sample, with no warning. Adding up the counts cannot find it. Preview 2026.11.13 fixes it, and the next stable release will carry the fix. If you ran with a distance above 0, run it again with Preview 2026.11.13 or later, which also stops a sample from being left out, and redo anything you made from the old sample files. Download it from the [Releases](https://github.com/dhoconno/lungfish-genome-explorer/releases) page, where it is marked Pre-release. It installs beside Stable.
- **Reads from the other strand with a dual-index kit.** Demultiplex Barcodes with the engine Cutadapt, which is the default, at Both Ends with TruSeq HT Dual Index, Nextera XT Index Kit v2, or a Custom Definition made on one of them or on IDT for Illumina UD Indexes looks for each pair only in reads that start with the i7 index and end with the i5 index. If your file holds reads from both strands, as long reads of such a library do, the reads from the other strand go to Unassigned, so each sample holds only about half of its reads. The counts still add up to your input, and no warning says why Unassigned is so large. Stable 2026.11.14 does not fix this. Preview 2026.11.13 and later place the reads of both strands, and the next stable release will carry the fix. If such a run left many reads in Unassigned, run it again with Preview 2026.11.13 or later, and redo anything you made from the old sample files. Runs that split the reads by the indexes in their read names, as the engine Read Names does, are not affected.
- **Viral Recon with another caller, or on Nanopore reads.** A Viral Recon run that names another variant caller in Extra parameters, such as `--variant_caller bcftools`, the example the field shows, writes its variant calls, consensus and lineage tables to folders that this version does not read. LGE then shows no variant track, consensus or lineage tables (Pangolin and Nextclade) for its samples, and no message says that they are missing. A run that names only another consensus caller, such as `--consensus_caller ivar`, shows its variant track but no consensus or lineage tables. A run on Nanopore reads shows none of these, and no alignment or coverage either. A default Illumina run, with iVar variants and a BCFtools consensus, is not affected. The run's own files are still in its results folder. Stable 2026.11.7 has the same fault, and this patch does not fix it. Preview 2026.11.16 reads each output from the folder the run used and says in the Inspector which variant, consensus or lineage output a sample lacks, and the next stable release will carry the fix. It reads them when a run ends, so opening an old result in it does not add them. If you ran Viral Recon this way, run it again with Preview 2026.11.16 or later. The run's consensus and lineage tables can be read in its results folder.
- **Two FASTQ bundles named like the two reads of one sample.** TaxTriage, Classification (Kraken2) and EsViritu run two FASTQ bundles whose names differ only by an ending of _1 and _2, or _R1 and _R2, as the two reads of one paired sample. So two files named like Swab_1 and Swab_2 from two specimens ran as one sample named Swab. The run ends with no error and shows one result, with the organisms of both specimens mixed together and no result for either specimen alone. If one of the two was marked as a negative control, the mark is lost, so it no longer serves as a control. When the two hold different numbers of reads, the extra reads of the larger one are left out with no message. Classification and EsViritu do this in a batch of several bundles too, so Sample_1 and Sample_2 of a batch became one sample named Sample. If a third bundle with the shorter name, such as Swab, was chosen as well, one of the three was left out of the run, and in a command line batch the same happened to a loose read file such as Swab.fastq beside Swab_1.fastq and Swab_2.fastq. A single bundle that holds both reads of a pair is not affected. Two bundles join when their names end in _1 and _2, _R1 and _R2, or _R1_001 and _R2_001. Classification and EsViritu also join names that end in .R1 and .R2 or -R1 and -R2, and they match every ending in upper or lower case. Bundles whose names end in none of these are not affected. You can spot such a result by a sample name that lacks the ending of its bundles, such as Swab from Swab_1 and Swab_2. Stable 2026.11.7 has the same fault, and this patch does not fix it. Preview 2026.11.16 runs each FASTQ bundle as its own sample under its whole name and leaves out no file, and the next stable release will carry the fix. If you ran one of these tools on bundles named this way, run it again with Preview 2026.11.16 or later. In 2026.11.14, rename the bundles so that their names no longer end in _1, _2, _R1, _R2, _R1_001, _R2_001, .R1, .R2, -R1 or -R2 before you run them together, or run each bundle alone.
- **Read files of one name in several folders, in a command line batch.** A batch command of Classification (Kraken2) or EsViritu given mixed file lists could pair reads from two specimens. When read files of the same names, such as S_R1.fastq.gz and S_R2.fastq.gz, sit in two folders and the list names the folders in a different order for R1 and for R2, the run takes R1 from one folder and R2 from the other as one pair. It can also happen with whole folders when one folder holds a compressed R1 and a plain R2 and the other folder the reverse. The run ends with no error, and each such sample mixes the reads of two specimens. TaxTriage is not affected, and neither is a batch in which each file name sits in only one folder. You can spot such a run by samples named like S_1 and S_2, made from files of one name in two folders. Stable 2026.11.7 has the same fault, and this patch does not fix it. Preview 2026.11.16 pairs R1 and R2 only within one folder, and the next stable release will carry the fix. If you ran such a batch, run it again with Preview 2026.11.16 or later. In 2026.11.14, run one folder per command.
- **A short second read file in a paired run.** A short second read file was cut without warning. When two loose read files given as a pair held different numbers of reads, TaxTriage, Classification (Kraken2) and EsViritu ran them with no check. In TaxTriage the reads past the end of the shorter file are left out of the result, and the only sign is a warning in the fastp log in the run's results folder. A file that was cut short, or subsampled or written on its own, can cause this. Stable 2026.11.7 has the same fault, and this patch does not fix it. Preview 2026.11.16 stops such a run before it starts and names both files and both counts, and the next stable release will carry the fix. If you ran two loose read files as a pair, run it again with Preview 2026.11.16 or later. In 2026.11.14, compare the read counts of the two files before a paired run (a FASTQ file usually has four lines for each read), and if they differ, run each file as single reads.
- **Two read files of a pair whose reads are in a different order.** Two read files of a pair whose reads were in a different order ran with mismatched mates and no warning. When two loose read files given as a pair to TaxTriage, Classification (Kraken2) or EsViritu hold the same number of reads in a different order, the run pairs the first read of one file with the first read of the other, and so on, so each pair joins two unrelated reads. The run ends with no error, and nothing in its result shows the fault. This happens only when one file was sorted, shuffled or subsampled on its own, or the two were cut to one size with different settings. Files as the sequencer or SRA delivers them are in step. Stable 2026.11.7 has the same fault, and this patch does not fix it. Preview 2026.11.16 compares the read names of each pair and stops such a run before it starts, and the next stable release will carry the fix. If you ran a pair made this way, run it again with Preview 2026.11.16 or later. In 2026.11.14, run each file as single reads, or make the pair again from the original files with a step that keeps both files in the same order.
- **The limits of 2026.11.7.** Every limit under Things to know on the 2026.11.7 page still applies.

### The other known issues of the 2026.11.7 page

This patch fixes none of these. The [page of Stable 2026.11.7](https://github.com/dhoconno/lungfish-genome-explorer/releases/tag/v2026.11.7) holds the words of each one, who is affected and what to do. The names follow, grouped by the Preview that fixes them. The next stable release will carry the fixes.

- **Fixed in Preview 2026.11.8.** Grouped Result of several datasets, IDT for Illumina UD Indexes plans, Viral Recon inputs with one sample name, trim of single reads, trim of read pairs, trim of a processing recipe, Viral Recon read order, Viral Recon lineage tables, iVar codon merge, EsViritu inputs of one file name, one file of a multi-file bundle, a saved BLAST search on the wrong row, the chance-match notice, varVAMP and Olivar size range, Viral Recon names with a space, two datasets with one name, Copy in a reference bundle view, and a run stopped for memory.
- **Fixed in Preview 2026.11.10.** Extract Reads on a TaxTriage result built before 2026.11.6, and Illumina amplicon genotyping, two samples with one file stem.
- **Fixed in Preview 2026.11.12.** Viral Recon on single-end reads, Demultiplex Barcodes with a kit that cannot be checked, and Exact Bare Barcode on barcodes in the read names.
- **Fixed in Preview 2026.11.13.** A Custom Definition of dual indexes, a Custom Definition of dual indexes at 5' End or 3' End, and two rows of a Custom Definition of dual indexes that swap.
- **No fix named on the page.** Viral Recon lineage of September results and poly-G tails at import, which Preview 2026.11.8 does not fix. A TaxTriage result can show another sample's BAM, which Preview 2026.11.11 warns about.

Includes no Preview. It patches v2026.11.7.

## Updating

Choose Check for Updates… in the app menu to install this release. It adds no tool to install on the Mac. It also brings every change of Stable 2026.11.7, so if you update from an older Stable, read the [page of Stable 2026.11.7](https://github.com/dhoconno/lungfish-genome-explorer/releases/tag/v2026.11.7) before you compare with old results. If you run Preview 2026.11.13 or later, you already have the fix of this release and the fix of the wrong-sample faults.
