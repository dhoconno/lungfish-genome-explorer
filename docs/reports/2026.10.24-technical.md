## The plan

**`import fastq --write-plan <folder>`** (C4 lane F, C5 lane LAUNCH) writes a submit folder in place of importing (`Tests/Fixtures/golden/cli-help/lungfish-cli.import-fastq.txt:76-94`). The folder holds `run.dag`, `sample.sub`, `lge-job.sh`, `logs/`, one plan folder a sample with that sample's `plan.tar`, and `staging-files.json`, which lists each file the jobs read with its size, its SHA-256 and the file on the Mac to copy (`:78-82`). Since C5 it also holds `jobs.tsv`, `run-local.sh` and `README.txt` (`:82-84`, LAUNCH.md Docs facts row 7). `--project` is not needed with `--write-plan` (`:85`, C4 commit `c02d67778`). The plan fixes the threads, the clumpify heap, the clumping choice and the compressor, and it pins the database and image digests (V1). The Mac writes one template per recipe and fills it per sample with paths, names and input digests only (V5, ARCH-fill).

**The plan sheet** (C4 lane U, C4-12, UX-XC26). The Sequencing Reads tab of the Import Center gains the cards Plan for a Linux Machine and Linux Run Result (`Sources/LungfishApp/Views/ImportCenter/ImportCenterViewModel+ActionText.swift:11-51`). The sheet asks for the staging folder, an absolute path (`Sources/LungfishApp/Views/FASTQ/FASTQPlanSheetModel.swift:75-78`), the threads per job, 8 by default (`:31`), and the clumpify memory in GB, 16 by default (`:32`). Its Optimize storage box opens on with BBTools clumpify, and since lane US it clears for a batch of ONT, PacBio or Unknown reads once the sheet has read the first sample's headers (`FASTQPlanSheetModel.swift:64-83` and `FASTQPlanSheet.swift:154-166` at `9127db708`, below). The popup offers BBTools and Trim Galore and no Automatic (`:30`). It sends the tool it shows, so the plan records source `option` (`:69-72` at `cfe90c4cc`), and `--no-optimize-storage` with the box clear (`:124-125` at `9127db708`). It runs `import fastq --write-plan` with the bundled executor manifest and image record (`:86-109`) and records that argv on an Operations row titled `Plan for a Linux Machine: <folder>`, which ends `Plan written to <folder>` (`Sources/LungfishApp/Services/FASTQIngestionService+LinuxRun.swift:44-59`, `:110`). Release builds include it.` (`FASTQPlanSheetModel.swift:19-20`, `FASTQPlanSheet.swift:96`, `:109`, `:192`, QA-parity-4). The sheet takes no recipe (Q-UX26-1, plan:669-670).

**Clumping in a plan** (C5 lane MOS1, owner O49). An `auto` plan resolves the platform first. Short reads get BBTools clumpify at the plan's heap whatever their size, and a plan whose `--platform` is `ont`, `pacbio` or `unknown` gets no clumping. The reasons are at `Sources/LungfishWorkflow/Ingestion/ClumpingTool.swift:54`, `:57` and `:59`, and the rule is `automaticChoice(for:)` at `:67`. A plan that names no platform is planned as short reads, since the plan writer reads no read file (help `:93-94`, MOS1.md "Not foreseen" 2). For an `auto` plan of ONT, PacBio or Unknown reads the storage launch is `reformat.sh` in place of `clumpify.sh` (MOS1.md, "After the code" table). Fix 5 corrected `docs/formats/executor-plan.md:70` (commit `745e2e1ce`).

**A lone fastp step** (C5 lane BF M1, D18). `Sources/LungfishWorkflow/ExecutorPlan/ExecutorPlanLoneFastpSteps.swift` gives `FastpTrimStep` and `FastpDedupStep` plan forms with the Mac's argv, so `--write-plan` plans the built-in recipe with `--no-remove-duplicates`, where it refused with `unfusedFastp` before (commit `d62c80aa8`). **Job requirements and disk** (C5 lane LAUNCH M1, D9 and D17). `--job-requirements <expression>` replaces the whole default clause, which asks for staging access, EL9 or later and x86-64 (help `:115-120`). `ExecutorPlanBatchWriter.checkRequirements` (`Sources/LungfishWorkflow/ExecutorPlan/ExecutorPlanBatchWriter.swift:171`) and `HTCondorValueRules.checkRequirements` (`Sources/LungfishWorkflow/HTCondor/HTCondorSubmitTemplate.swift:405`) refuse a blank value, more than 4096 bytes, a control character and U+2028 or U+2029, in the real run and in `--dry-run`. The sheet's `request_disk` column wins, and none of it reaches `plan.json` (OQ-9).

## Running the plan

**On an HTCondor pool** (C4 lane H, C5 lane LAUNCH M1). `run.dag` holds one JOB a sample with its VARS. Since C5 it ends with `CATEGORY ALL_NODES lge`, `MAXJOBS lge 10` and `NODE_STATUS_FILE run.dag.status 60` (`Sources/LungfishWorkflow/HTCondor/HTCondorDAG.swift:94-95`, `ExecutorPlanBatchWriter.swift:145`, D13). Each job returns `run-record.json`, each report under `work/` and the payload under `out/` to `<staging>/batches/<batch>/<sample>/result/`, with each remap keyed by its listed path, and its step logs to `<sample>/logs/` of the submit folder (D1 in form R-b, LAUNCH.md M1). `run.dag`'s `SCRIPT PRE` makes `result`, `result/out` and each report's folder in one `mkdir -p` line. The plan tar sits in its sample's plan folder and is no longer copied to the staging folder (D15). The template passes node facts as `--site-fact` (FC-A1), sets `retry_until` so that a refused run is never retried (C4-08) and asks `request_memory` as the heap plus the margin of ruling CHTC-H2, 8 GiB for a first job (H2-1). C-FAIL showed that D1's form returns every file of a passing job (below).

**On one Linux machine** (C5 lane LAUNCH M2). `run-local.sh`, written by `Sources/LungfishWorkflow/ExecutorPlan/LinuxRunScript.swift` with the usage line at `:58-59`, runs each sample's plan with `apptainer exec --containall --no-home` or `docker run --rm --platform linux/amd64`, at most `--jobs` samples at once. The default is 10, the value of `MAXJOBS` (`:65`). For each sample it copies, never links, the tar, `lge-job.sh` and each file into a scratch folder, checks the tar's SHA-256 and runs `lge-job.sh` unchanged. With Apptainer it hashes the image once a batch and refuses one whose SHA-256 is not the batch's (`:192`), and with Docker it needs `--image` (`:197`). It moves only `run-record.json`, `out/<payload>` and each `work/<r>` into `<sample>/result/`, and only when the run record came back, moves `plan/logs` to `<sample>/logs/`, writes the run's output to `logs/<sample>.out` and `.err` and skips a sample that has a `result/` folder. It exits 0, 1 when a sample did not finish, 2 for a refusal before any sample and 64 for a usage error (LAUNCH.md Continuation 1, `LinuxRunScript.swift:56-57`, `:71-72`). It retries nothing (same file, "Not foreseen" 5). The site facts of D10 are `Machine`, `Arch`, `OpSysAndVer`, `ContainerRuntime`, `ContainerRuntimeVersion`, `ImageSHA256` for Apptainer or `ContainerImageID` for Docker, and `Launcher` (`HTCondorSubmitTemplate.swift:156-164`), each passed as one argument through `"$@"` and never through `eval`. `jobs.tsv` holds one row a sample, in the order of `sample.sub`'s arguments.

**`README.txt`** (`Sources/LungfishWorkflow/ExecutorPlan/ExecutorPlanBatchReadme.swift:14-151`). It gives the HTCondor run with `MAXJOBS` and `--job-requirements` (`:33-49`), the sample sheet and its three-line example (`:51-58`, LAUNCH fix 1), the five held-job steps of D14 (`:61-87`), the plain run (`:90-112`) and the copy step and the whole-batch adopt in the order of the BADOPT ruling (`:115-149`), with the three refusal lines a lab may meet (`:142-145`). It names no site (O41).

Two checkouts of one commit then give the same stripped file, and landing 1's Linux tier built `755d825b32391aa97924909c90a88dfdc6b4b65b4358e584db52d58ac40730e1`, 58,829,184 bytes, which equals REPRO's value from other checkouts (land-1.md "The Linux tier"). ## Bringing the result back

## The Mac's import

**Clumping `auto` follows the plan's rule** (C5 lane MOS1, O49 closing MO-S1, D5, D8). `ClumpingTool.storageRequest` (`ClumpingTool.swift:82`) and `automaticChoice(for:)` (`:67`) decide the platform first. A short-read import with `auto` clumps with BBTools clumpify at the clumpify heap whatever its size, where at `2667f6cad` an import above half of the clumpify memory budget skipped clumping. ONT, PacBio and Unknown reads with `auto` are not clumped, with the reasons at `:57` and `:59`. A named tool now wins for ONT and PacBio, and an Unknown import that asks to optimize storage without naming a tool clumps nothing (MOS1.md "Not foreseen" 1). The record keys move as MOS1.md's M1 table gives. `resolvedClumpingToolSource` reads `default`, `clumpingEstimatedInputBytes` and `clumpingThresholdBytes` are null, the reason is the shared sentence, and `options.defaults.clumpingTool` reads `auto` for ONT, PacBio and Unknown. The replay argv of an ONT `auto` import reads `--clumping-tool auto` where it read `--clumping-tool none --no-optimize-storage`. The Import FASTQ sheet's box opens on for short reads at every size and off for ONT, PacBio and Unknown (`Sources/LungfishApp/Views/FASTQ/FASTQImportConfigSheet.swift:593-603`), and its tool default is `bbtools` (`:609-612`). Clumpify keeps level 4 and ignores the sheet's level (O50, O51).

**The free-disk check** (C5 lane DISK). `Sources/LungfishWorkflow/Ingestion/ClumpifyDiskNeed.swift` asks for five times the sample's read file bytes (`:28`, `:32-35`), read with `.volumeAvailableCapacityForImportantUsageKey` (`:43-46`) on the volume of the pipeline's output folder. `FASTQIngestionPipeline.swift:275` calls it first in `case .bbtools:` and throws `insufficientDiskForClumpify` (`:112`).
