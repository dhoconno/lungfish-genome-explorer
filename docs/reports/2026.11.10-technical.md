## S1 and S2 results

GENOTYPE-MERGE-STEM (S1 as if, rare). Two Illumina amplicon samples that shared a file stem, or differed only in letter case, wrote one `<stem>.for-mapping.fastq`, so the first sample's genotype came from the second's reads. The fix is `fc7be5181`, after the pure move `69ae913d7`, the helper with its red tests `5d67686d1` and before the BIO review's `d86eab964`. `IlluminaMergeStemCollisionTests` and, with real bbmerge, `IlluminaMergeStemCollisionConformanceTests` pass (`~/lungfish-phase-records/s1s2-sweep/lanes/GENOTYPE-MERGE-STEM.md`). Closed by `bcae73ebf`.

BUILDDB-OLDER-DB-CLI (S1 by effect). A sample of a TaxTriage database built before 2026.11.6 could read another sample's BAM through `lungfish-cli extract reads` and the app's Extract Reads. The fix is `2bfd0e02e` (red tests `8c77b8654`, pins `a3f2a94ef` and `c1bbcd0df`, doc line `6926124c0`, manual sentence `8f53680ac`). The same commits closed rows whose fixes were already in v2026.11.7, TAXTRIAGE-CONTROL-PARTIAL-RESULT (`c7e9e3bb3`) and the four rows of `89cf76930`. BIO-WALK-T2-VIEW (S1 in kind, rare, not fixed here). When a recorded BAM that `build-db` took by a fit of its name is really another sample's, the alignment, the depth and coverage, the Inspector's BAM line, the reads BLAST Verify sends and the row's Unique Reads are that sample's, with no words. The row's Reads is the report's own count for the sample (`BuildDbCommand.swift:71,210-214`), so a Unique Reads above it reads as a dash and a lower one reads as a plausible number. In the walk's setup nothing on screen was false, since `S1_2.bam` is a copy of S1's own BAM (`SCR/rulings/BIO-WALK-T2-VIEW.md` What binds 2 and 3). It reads the stop of `SCOPE-AND-DELIVERY.md:34` as not binding for a fault that lives in Stable, and the owner may reverse that (What binds 9). Its BACKLOG row is not in `d94d12d21`, and What binds 6 asks for it.

FASTP-STAGING-MEMORY (S2, `78aa134f0`). Since 2026.11.8, trimming of paired reads and Viral Recon hold about all the staged reads in memory. ## Limits added

- `rnaseq index` needs about 16.6 GB of memory and 64 GB of free disk, refuses before it starts on a Mac with less, gives salmon 8 threads and refuses `--threads` (`c51c60543`).
- `rnaseq quant` works on one reference set and one index, trims only with `--trim` and keeps duplicates (`SCR/lanes/FIX-RS-QUANT.md`). A pseudobulk result leaves out a group under 10 cells, and its export refuses a tested factor with a level under 3 animals (`5d59e4a2a`).
- The single-cell import reads Matrix Market text only, refuses any other header and a duplicate barcode, and publishes nothing when it refuses (`docs/formats/rnaseq-bundle.md:55-57`).
- A schema 1 reference set counts with salmon and a STAR route refuses it in words that name the rebuild (`STARIndexPlan.swift:10`). An index record needs a plain folder name for its set id and key, and the STAR plan pins `--sjdbOverhang 100` (`592defc4c`, `60085ee3c`).

The commands added after the first package carry more limits.

- `quant --write-plan` plans salmon on the index `rnaseq index` published for the set, and an index of another salmon version counts as missing (`docs/formats/reference-set.md`, section The index a Linux plan pins). A STAR chain pins the one record of its STAR version that has no 10x filter, and a set with none or with two is refused in words. `--k` or `--decoys` with a STAR chain and `--chain` without `--write-plan` are refused (`SCR/lanes/EX-PLAN-STAR.md:158`).
- A plan refuses an interleaved bundle in words, since the image has no tool that splits it, and a virtual bundle with words to materialize it first (`SCR/lanes/EX-PLAN-SALMON.md:34`).
- `import rnaseq --adopt` takes one reference set and one route for all samples and refuses a STAR or featureCounts table counted on a GTF other than the set's `derived/genes.gtf`. It reads the count table that the run returned and counts no read itself. The featureCounts chain runs featureCounts with `-M`, so each reported alignment of a multimapping read counts, and a read that maps to two genes counts once in each, while STAR's own `ReadsPerGene.out.tab` of the same run counts by STAR's rule and differs by design (`SCR/lanes/EX-ADOPT.md:232,466`, `SCR/lanes/EX-PLAN-STAR.md:88`, `e094bae71`).
- A STAR plan takes its memory, CPUs and disk from the person unless the genome is Macaca_fascicularis_6.0 (`SCR/lanes/EX-PLAN-STAR.md:89`).
- No adopt exists for a UMI result (`SCR/lanes/EX-UMI.md:110`). The STARsolo adopt refuses the introns preset in words, and the exon matrix of such a run imports with `import rnaseq <result folder>/solo`, by the folder reader's header and not run (BIO SF1). The adopt read the two returned batches of M2's Docker gate and no pool ran, and no run has taken a plan that `rnaseq solo-plan` wrote (`SCR/lanes/SOLO-PLAN.md:286,320,327-330`).

## Known-issue lines for Stable 2026.11.7

Two faults that this Preview fixes and one that it leaves open live in v2026.11.7. The faulty lines of GENOTYPE-MERGE-STEM are in the tag (`ONTBarcodeDemuxGenotypingPipeline.swift:1948,1980-1981`, `IlluminaAmpliconPairMerger.swift:302`), and `438890557` of 2026-05-30, which made `assignedStems`, is an ancestor of it. `ClassifierReadResolver+TaxTriageLayout.swift:23` has no refusal in the tag, and its first commit `7fc768ba2` is an ancestor of it. Neither fix commit is an ancestor of v2026.11.7 or v2026.11.9.

- **Illumina amplicon genotyping, two samples with one file stem.** Two sample IDs that give one file name, such as `S-1` and `S--1`, or differ only in letter case, make the pair merge write one file for both, so the first sample's genotype is called from the second sample's reads, with no words. Fixed in Preview 2026.11.10 (GENOTYPE-MERGE-STEM, `fc7be5181`). Until you update, give each sample ID its own file stem and run an affected batch again.
- **Extract Reads on a TaxTriage result built before 2026.11.6.** The database can record a BAM of another name for a sample, such as `S1_2.bam` for S1, and Extract Reads writes that file's reads under S1. Fixed in Preview 2026.11.10 (BUILDDB-OLDER-DB-CLI, `2bfd0e02e`), which stops before it writes a read and names the repair. Until you update, run `lungfish-cli build-db taxtriage "<result folder>" --force` on such a result before you extract.
- **A TaxTriage result can show another sample's BAM.** In a TaxTriage result where a sample's own BAM file is missing, Lungfish can use another file in the minimap2 folder whose name fits the sample. The alignment view, its coverage, the Inspector, BLAST Verify and Extract Reads then read that file, and it may hold another sample's reads. Check the BAM line in the Inspector. If it is not the sample's own file, put that file back and run `lungfish-cli build-db taxtriage <result folder> --force`. Not fixed in Preview 2026.11.10 (BIO-WALK-T2-VIEW, `SCR/rulings/BIO-WALK-T2-VIEW.md` What binds 5, 8).

FASTP-STAGING-MEMORY gets no line on the Stable page, since `SeededPairOrder.swift` does not exist at `6b6e0c0f3` and `SCOPE-AND-DELIVERY.md:23` puts a line on the Stable page only for an S1 or S2 that lives in that Stable (`SCR/rulings/BIO-FASTP-LINE.md` What binds 2).
