## The release

Stable 2026.11.7 is the stable release that follows Preview 2026.11.6, the Preview that closes Phase 4 (`docs/plans/2026-11-09-phase-4.md`). It is a promotion and not a candidate of its own. Every fix was made and walked in Preview rounds, and the stable package is built once from the same code with the notes and this record added (`docs/contracts/VERIFICATION-ORDER.md`, section Promoting a Preview to a stable release). So it adds no product change to Preview 2026.11.6. What it brings to a user of Stable 2026.10.29 is the work of the six Previews 2026.11.1 to 2026.11.6, which the notes list under What works differently, What's new and Things to know. It corrects results that Stable 2026.10.29 could show or make, among them TaxTriage read counts, the BAM file a TaxTriage sample takes, Kraken 2 totals, the Mean Q of a merged FASTQ bundle, the depth of an exported figure and a few reads that Demultiplex Barcodes gave to the wrong sample.

### How to repair a result an earlier version made

The notes end the TaxTriage bullet with "The technical record says how to repair an older result", so these are the steps. The words of the BIO review (`SCR/reviews/BUILDDB-FIX-BIO.md` sections 6.1 to 6.5) and of the UX read (`SCR/reviews/NOTES-FINAL-UX.md` section 7) are the source.

In the app, nothing is needed in a project you can edit. When the app shows a result whose database an earlier version built with a BAM file for a sample under a name other than `S1.bam` or `S1.S1.dwnld.references.bam` (S1 standing for the sample's name), it builds the database again once a session. Only such a database can hold another sample's file. The narrowed rule is `isStale` with `recordsUnmarkedFittedBAM` in `Sources/LungfishIO/Formats/TaxTriage/TaxTriageDatabase.swift` and `TaxTriageDatabase+FittedBAM.swift` (`e63e79c54`). A database counts as stale for want of the mark only when it has no `fitted_bam_samples` key and a row records a BAM whose name is neither `{sample}.bam` nor `{sample}.{sample}.dwnld.references.bam`. The manager folded in the backlog row B1 of BIO as MGR-1 and first asked for a blanket rule, every database without the mark stale. BIO objected to it, since it would drop stored Unique Reads where a BAM has gone since the first build, hide every older TaxTriage result in a read-only project and make `lungfish-cli taxtriage export` refuse every older database.

In a read-only project the app does not show such a result and says so, so open it in a project you can edit.

On the command line nothing rebuilds it, because `extract reads` calls neither the check of the display nor the check of the export. Run the following command.

```text
lungfish-cli build-db taxtriage <result folder> --force
```

For a BAM file that was renamed, rename it so that its name starts with the sample's name, delete `taxtriage.sqlite` in the result folder and select the result again.

What the repair costs, from BIO sections 6.1 to 6.3. The rebuild gives the same Unique Reads while the BAM files are there. It runs the legacy cleanup again, so a result whose first build ran with `--no-cleanup` loses `count/`, `top/` and its fastp FASTQs at the first show. A rebuild that finds no BAM, because a file was removed since the first build, writes no BAM path and loses the stored Unique Reads for that sample. A failed or cancelled rebuild puts the earlier database back. `lungfish-cli taxtriage export` stops with `staleDatabase` on a database that needs the rebuild, until it is rebuilt (`TaxTriageExportLoader.swift` lines 278 to 280). The words that UX cut from the notes, word for word from `6b1857d3b` line 33, were these.

```text
When the app shows a result whose database an earlier version built with a BAM under a name other than the sample's own `S1.bam` or `S1.S1.dwnld.references.bam`, it builds the database again once, in a project it can write to; a read-only project does not show the result, with words, until it can. On the command line nothing rebuilds it: run `lungfish-cli build-db taxtriage <result folder> --force`.
```

The fit cut the older-result steps from the second bullet (U2), shortened the first (U3 and U4), changed two words (U1 and U9), and swapped the two lines so that the bullet about the sample comes first in the notes. The steps it cut are in the section Known limits, under How to repair a result an earlier version made.

```text
- **Extract Reads on a raw TaxTriage result takes a sample's own BAM file,** not the reads of a sample whose name only begins the same way, such as S1 and S10. If the own BAM is not found, it reads the one file in the `minimap2` folder whose name fits and says which in the Log and on the command line. If two files fit, it stops and names both. If the result's database took the file, the words say so and tell you to delete `taxtriage.sqlite` and select the result again.
- **A TaxTriage sample no longer takes another sample's BAM file.** Since July 2026, Stable 2026.10.29 among them, a result's database could give a sample whose own BAM was missing another sample's `minimap2` file, so its alignment view, Unique Reads and Extract Reads came from that sample. A file now goes only to the sample whose name it starts with, then a dot, underscore or hyphen, and to the longest such name: `S1_2.bam` to S1_2, never to S1. A name with the sample's name in the middle, in another case or ending `.BAM` no longer fits, so such a sample shows no BAM, Unique Reads or alignment view until you rename the file. When the app shows a result whose database an earlier version built with a BAM under a name other than the sample's own `S1.bam` or `S1.S1.dwnld.references.bam`, it builds the database again once, in a project it can write to; a read-only project does not show the result, with words, until it can. On the command line nothing rebuilds it: run `lungfish-cli build-db taxtriage <result folder> --force`.
```

The words about "Since July 2026" are right. The fuzzy fit came with `e881cb8db` of 2026-07-07 (fix of downsampled minibam outputs), and its parent took only `minimap2/{S}.{S}.dwnld.references.bam`, so no earlier version had the fault (`SCR/reviews/NOTES-FINAL-UX.md` section 2).
