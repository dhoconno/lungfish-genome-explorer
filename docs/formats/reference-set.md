# Reference sets and the salmon index cache

A reference set of Lungfish Genome Explorer (LGE) is one named folder with checksums that RNA-seq counting shares across bulk and single cell, the Mac and Linux (`docs/plans/2026-10-02-architecture-program.md:111`). This page gives its kind, where it lives, its one owner, its id, its layout and its deposit layout, how a reference written before Phase 5 still opens, and the salmon index cache beside it. It is written for developers and for the lanes RS-REFSET and RS-INDEX. Phase 5.1 sets the layout, and `ReferenceSetOwner` in `Sources/LungfishWorkflow/RNASeq/` writes it (lane RS-REFSET). The results that name a set are in [rnaseq-bundle.md](rnaseq-bundle.md).

## A new kind, not a `.lungfishref`

A set is a new kind, `<set id>.lungfishrefset`, and no extension of the `.lungfishref` reference bundle.

- A `.lungfishref` holds one genome with the tracks drawn on it (`docs/formats/reference-bundle.md:3`). A set holds the genome FASTA, the GTF with its source and release, the transcript FASTA and gene table derived from them, and extra sequences such as a virus (`docs/plans/2026-10-02-architecture-program.md:111`).
- The reference manifest is `BundleManifest` in LungfishCore (`docs/formats/reference-bundle.md:43`). Adding the set's parts there would put RNA-seq types outside `Sources/LungfishWorkflow/RNASeq/`, the domain folder that may leave for its own target only when no other folder names its types (`docs/plans/2026-10-02-architecture-program.md:188`).
- A set's id comes from its content, so a changed virus sequence makes a new id (`docs/plans/2026-10-02-architecture-program.md:193`). The reference bundle's `identifier` is a reverse-DNS name (`docs/formats/reference-bundle.md:48`), and its mutators set a new modified date with every track (`docs/formats/reference-bundle.md:61`).

No project holds a set, so it gets no row in [bundle-kinds.md](bundle-kinds.md) and no sidebar row.

## A shared cache, not the project

Sets live in one folder of the LGE storage root, `<storage root>/rnaseq-reference-sets/`, beside the `conda` and `databases` folders that root already holds (`Sources/LungfishCore/Storage/ManagedStorageLocation.swift:41-47`). The default root is a folder in the home folder named by the app identity (`Sources/LungfishCore/Storage/ManagedStorageLocation.swift:58-67`), and a root inside a project is refused (`Sources/LungfishCore/Storage/ManagedStorageLocation.swift:16-17`), so a set never sits inside a project.

- A human set holds the whole GRCh38 genome and its indexes, and C1's decoy-aware salmon index alone took 23.7 GB to build (`docs/plans/2026-10-02-architecture-program.md:174`). A copy in each project would repeat that.
- Bulk and single cell, the Mac and Linux share one set by its id (`docs/plans/2026-10-02-architecture-program.md:111`).
- A result keeps what it needs to read without the set. Its `genes.tsv` holds the set's gene rows for the result's genes, and equals the set's gene table by sha256 when the result keeps every gene. Its manifest names the set's id and layout ([rnaseq-bundle.md](rnaseq-bundle.md)). A project moved to a Mac without the set opens every count and shows the set as not on this Mac.

The owner derives the folder from `ManagedStorageLocation.rootURL` (`Sources/LungfishCore/Storage/ManagedStorageLocation.swift:35`), so no Core or IO type names it.

## The one owner

One component in `Sources/LungfishWorkflow/RNASeq/` creates, settles and discards every set, and writes its root record last (`docs/contracts/EXPERT-PANEL.md:49`). RS-REFSET writes it. No other component writes under `rnaseq-reference-sets/`.

1. It builds in a staging folder `.<set id>.lungfishrefset.creating-<UUID>` inside `rnaseq-reference-sets/`, the staging form of a result folder (`Sources/LungfishIO/Bundles/AnalysesFolder.swift:136`).
2. It copies each input, checks its sha256 as it reads it, derives the transcript FASTA and gene table, and publishes `reference-set.json` through `DurableReplace` (`docs/formats/analyses-layout.md:42`).
3. It writes the root record `.lungfish-provenance.json` last through `ProvenanceWriter` (`Sources/LungfishWorkflow/Provenance/ProvenanceWriter.swift:11,113`).
4. It renames the folder into place with `RENAME_EXCL` through `PortableRename` (`Sources/LungfishIO/Bundles/AnalysesFolder.swift:159`, `AGENTS.md:76`). When a set of the same id is already there, the rename fails, the owner removes its staging folder and uses the published set after it checks the manifest.

A failed or cancelled build removes its staging folder. A published set changes only by the files of `uses/`, which the owner adds after the root record and no record names. Settling means the owner checks the manifest and each file's size before a run, and every sha256 when the person asks for a check, and refuses in words a set whose files differ.

## The id

A set's id is `<species>-<assembly>-<annotation source and release>-<layout>-<digest>`, such as `macaca_mulatta-Mmul_10-ensembl100-lge-3f9a1c2b7d10`. The digest is the first 12 hex digits of the sha256 of a content list, one line `<role>\t<file name>\t<sha256>` for the genome, the annotation and each extra sequence by name, with `extra annotation\t<file name>\t<sha256>` right after its extra's line when that extra brings its own GTF (the deposit layout only) and `extra mask\t<file name>\t<sha256>` after that when the person gives the extra an rRNA mask GTF (either layout), then `assembly report\t<file name>\t<sha256>` when the person gives an assembly report and `mitochondrial contig\t<name>\t` for each contig the person names, so another report or another contig makes another id, then `layout\t<layout>`, `derive\tgffread <version>` and `derive\tlungfish <rule version>`. The rule version names every rule LGE applies to the annotation and the set's layout (`ReferenceSetID.lungfishDeriveVersion`). It is 2 since a set keeps `derived/genes.gtf`, and a set of schema 1 was built before the line, so the same inputs now give a new id (ARCH-COUNTING-GTF item 1). The lines keep the order given, so each GTF stays tied to its extra, and two sets that differ only in an extra's GTF or mask get two ids. A changed byte in any input, a changed extra, a changed layout, a changed gffread or a changed rule version makes a new id, so a changed virus sequence makes a new id (`docs/plans/2026-10-02-architecture-program.md:193`). The derived files are not in the list, since they follow from it.

## Layout

```
<set id>.lungfishrefset/
  reference-set.json
  .lungfish-provenance.json
  provenance/
  genome/<file as given>
  annotation/<file as given>
  extras/<name>.fa
  extras/<name>.gtf
  extras/<name>.mask.gtf
  derived/transcripts.fa
  derived/genes.gtf
  derived/genes.tsv
  derived/transcripts.tsv
  derived/genes-without-features.tsv
  uses/
```

An input given as a symbolic link is read and copied as the file the link names, under the name given, so a set holds no link.

| Key of `reference-set.json` | Holds |
| --- | --- |
| `schemaVersion` | 2, which adds `derived.countingGTF`. A set of 1 still opens (section A set written before its counting GTF), and a higher number is refused in words before the rest is read, as a result's is ([rnaseq-bundle.md](rnaseq-bundle.md)) |
| `id`, `name`, `species` | The id above, a display name and the species |
| `assembly` | The assembly name, accession and source URL, such as GRCh38, Mmul_10 or T2T-MFA8v1.1 (`docs/plans/2026-10-02-architecture-program.md:111`) |
| `annotation` | The GTF's source and release, its path and sha256 |
| `genome` | The genome FASTA's path and sha256, and the `.lungfishref` it came from with that bundle's `md5_checksum` when it came from one |
| `extras` | One entry a sequence the person added, with its name, kind (virus, bacterium or spike-in), path, sha256 and records, and in the deposit layout the path and sha256 of the extra's own GTF (`annotationPath`, `annotationSHA256`, kept as `extras/<name>.gtf`), each flagged not-host (`docs/plans/2026-10-02-architecture-program.md:113`). An extra's rRNA mask is its entry in `masks` and never its own features |
| `layout` | `lge`, or `deposit` with the study it reproduces |
| `mitochondrialContigs` | The contigs whose genes are mitochondrial, since a gene is never called mitochondrial by its name (`docs/plans/2026-10-02-architecture-program.md:111`). An empty list means the set holds no mitochondrial contig, as in the two T2T sets, whose RefSeq files leave the mitochondrion out although the assembly report lists it. A reader says `mitochondrial share not measured (no mitochondrial contig)` and never 0%, and the leaf prints a note. |
| `masks` | One entry an extra the person gave a mask GTF (`lungfish-cli rnaseq reference-set --extra-mask <name>,<gtf>`), with the extra's name, the copy `extras/<name>.mask.gtf` (`.gtf.gz` when given gzip) and its sha256, the rule, and each `gene` line of `gene_biotype "rRNA"` as an interval of `record`, `start` and `end` (1-based, as given) and `geneID`, as `scripts/repro/rnaseq/gse296788/mtb.py:71-79` reads them. A mask holds intervals and not features, since in both layouts a bacterium's rRNA genes are no feature of the set. A not-host count moves a UMI whose alignments all overlap a mask gene by 1 base or more out of the default column ([rnaseq-bundle.md](rnaseq-bundle.md), Single cell). The build refuses in words a mask GTF that names a sequence the extra lacks and one with no rRNA gene, so an empty mask never passes. A bacterium with no mask still builds, and its not-host flag reads `not computed: no rRNA mask for <extra>` with its counts shown (`docs/plans/2026-10-02-architecture-program.md:113`, BIO-NOTHOST-BARCODE items 1 to 6) |
| `derived` | The transcript FASTA, the gene table and the transcript table, each with its path, sha256, size, tool and version, and `countingGTF`, the same five for `derived/genes.gtf` with tool `lungfish` and the app's version. A set of schema 1 has no `countingGTF` |
| `derivation` | What the owner changed from the annotation as given, in `exonsAdded`, the genes given their CDS and stop codon as an exon (LGE's layout), `keptWithoutExon`, the genes with a CDS and no exon kept as the deposit gave them (the deposit layout), `droppedFeatures`, each feature of empty `gene_id` as `<contig>\t<type>\t<start>\t<end>`, `renamedTranscripts`, each transcript id that named more than one gene, contig or strand with its gene and its new id, and `genesWithoutFeatures`, the path, count and sha256 of `derived/genes-without-features.tsv` |

In LGE's layout a not-host sequence counts as one feature a sequence record (`docs/plans/2026-11-13-phase-5-rnaseq-reproduction.md:91`). A gene with a CDS and no exon gets its CDS and stop codon as an exon that the record names, or a refusal in words (`docs/plans/2026-10-02-architecture-program.md:111`). A transcript id in one file and not the other is refused with the names listed, and nothing is renamed (`docs/plans/2026-10-02-architecture-program.md:193`). A name that `derived/transcripts.fa` holds twice is refused the same way, since a count could not tell the two records apart. The check counts names, not sets of names.

`derived/genes.tsv` has the columns `gene_id`, `name`, `biotype`, `contig`, `length`, `not_host`, `mask` and `unreliable`, the names the result's reader reads ([rnaseq-bundle.md](rnaseq-bundle.md)). Its genes come in the order of their first exon line, or of their first CDS line for a gene with no exon, as a deposit's feature list reads (`scripts/repro/rnaseq/gse296788/ref.py:4-10`), and each extra's genes come last in the order given. `length` is the gene's exonic length in bases, 0 for a gene kept without an exon. `not_host` is `true` or `false`, and `mask` and `unreliable` are empty, since a mask holds intervals of genes that are no feature of the set. A feature of empty `gene_id` is dropped. `derived/transcripts.tsv` has `transcript_id` and `gene_id` first, as `scripts/repro/rnaseq/seqc-gse47774/tx2gene.py:5-6` writes them, one row a record of `derived/transcripts.fa`, so gene sums read it. A gene with no exon line and no CDS line, such as a pseudogene that RefSeq gives only a gene line, is listed in `derived/genes-without-features.tsv` with the columns `gene_id`, `contig` and `biotype`, in the order of its first line, and stays out of `genes.tsv` and `transcripts.tsv`. The build is not refused, since no read can land on such a gene. Cynomolgus RefSeq 5.0 has 4,523 such genes and rhesus RefSeq Mmul_10 5,664.

gffread writes the transcript FASTA from the genome and a GTF that LGE writes in the stage (`gffread -w <out> -g <genome> <gtf>`), and never reads the annotation as given. That GTF holds the annotation's feature lines with these changes.

- Each line of empty `gene_id` is left out.
- A gene line loses a `transcript_id ""` attribute, so gffread reads the gene by its `gene_id`, as it reads the gene lines of Ensembl and of RefSeq Macaca_fascicularis_5.0. RefSeq Mmul_10 release 103 and the two T2T releases write `transcript_id ""` on each gene line, and gffread 0.12.9 refuses such a line with `no valid ID found for GFF record`.
- Each line of a gene with no exon and no CDS is left out, since gffread 0.12.9 writes a record from a transcript line alone.
- A `transcript_id` that names more than one `gene_id`, contig or strand becomes `<gene_id>:<transcript_id>` on each line, and `renamedTranscripts` lists each old id, gene and new id. RefSeq gives the tRNA, rRNA and CDS lines of a mitochondrion one id, `unknown_transcript_1`, and gffread 0.12.9 then writes two chimeric records of that one name.
- In LGE's layout each transcript of a gene given an exon gets one exon line from its CDS and stop codon span.
- In the deposit layout each line of a gene kept without an exon that carries a `transcript_id` is left out, so gffread writes no record for a gene that counts 0.

Each extra's records follow in the order given, as `scripts/repro/rnaseq/seqc-gse47774/ref.sh:30` joins ERCC92. An extra with its own annotation in the deposit layout gives gffread's records of a GTF that LGE writes from that annotation by the same rules. The mitochondrial contigs are the ones the person names, else the sequence an NCBI assembly report types Mitochondrion, else a FASTA header that says mitochondrion, else a contig named `MT`, `chrM`, `chrMT`, `M` or `Mt`, never a gene name prefix (`scripts/repro/rnaseq/refs/refcheck.py:225`).

`derived/genes.gtf` is the only GTF that STAR, STARsolo and featureCounts read (BIO-COUNTING-GTF item 2). It holds the bytes of the GTF that gffread read, with every change above, then each extra in the order given. A transcript of CDS lines and no exon line gets one `exon` line a span of its CDS and stop codon, joined where they touch, right after the GTF it comes from, since gffread 0.12.9 writes its record from those spans. RefSeq Macaca_fascicularis_5.0 release 101 has 232 such transcripts, the CDS of 220 V_segment and 12 C_region genes whose exons carry another id, named `<gene>:unknown_transcript_1` by the rename above. In LGE's layout an extra adds one line a record, `<record>\tLGE\texon\t1\t<length>\t.\t+\t.\tgene_id "<record>"; transcript_id "<record>";`, the one feature it counts as. In the deposit layout an extra with its own annotation adds the GTF that LGE wrote from it. Before the manifest is published, the build checks that the transcript ids of the file's `exon` lines equal those of `derived/transcripts.tsv`, and that each transcript's merged exon length, each base counted once, equals its record's length in `derived/transcripts.fa`. A difference is refused in words that name up to 5 transcripts of each kind, a length with both numbers, and the stage goes as for any failed build. So salmon, STAR and featureCounts count on the same exons. An extra's line is on `+`, as salmon reads a record forward only, and its effect on stranded reads is not measured. `annotation/<file as given>` stays the record of the source and is never a counting input in either layout.

### The deposit layout

The deposit layout is a named reproduce option, `deposit layout`, and never LGE's default (`docs/plans/2026-11-13-phase-5-rnaseq-reproduction.md:91`). It keeps a deposit's own not-host features, only to check that deposit (`docs/plans/2026-10-02-architecture-program.md:113`). Its id carries `deposit-<study>` where LGE's layout carries `lge`, and its record says which deposit it reproduces. Mmul_10 Ensembl 100 with NC_045512.2 gives 35,443 features in the deposit layout of GSE183579 and 35,433 in LGE's layout (`docs/plans/2026-11-13-phase-5-rnaseq-reproduction.md:91`). The deposit layout also keeps a gene with a CDS and no exon as the deposit gave it. It adds no exon, so the gene counts 0. In GSE296788's deposit layout the 13 mitochondrial genes keep no exon, as all 15 deposits do, and the quality view reads `mitochondrial share not measured (13 genes without exons)` and never 0% (`docs/plans/2026-11-13-phase-5-rnaseq-reproduction.md:91`). RefSeq Macaca_fascicularis_5.0 release 101 with the two Mtb scaffolds KK339487.1 and KK339488.1, one feature each, gives the deposit's 28,847 features in order in both layouts, and the 24 tRNA and rRNA exons of empty `gene_id` are dropped and listed in the set's record (same line).

## A reference written before Phase 5

Nothing in the `.lungfishref` kind changes, so every reference bundle written before Phase 5 opens as it does today (`docs/contracts/EXPERT-PANEL.md:50`). `BundleManifest.load(from:)` reads an older manifest as before (`docs/formats/reference-bundle.md:61`). A set may take its genome from a `.lungfishref`. The owner reads the FASTA that the manifest's `genome` names, records the bundle's `md5_checksum` beside its own sha256 (`docs/formats/reference-bundle.md:71`) and writes nothing into the reference bundle.

## A set written before its counting GTF

A set of schema 1 keeps no `derived/genes.gtf`. It still loads and settles, and it counts with salmon as before, so its salmon indexes and the results that name it open and are reused, since the salmon readers read only the three entries it keeps. It is never upgraded in place. Every STAR, STARsolo and featureCounts plan calls `ReferenceSetManifest.requireCountingGTF()`, which refuses it in words that read `The set <id> was built before LGE kept the GTF that STAR and featureCounts read. Build the set again from the same files. It gets a new id, and <id> stays for its salmon results.` When the set's `exonsAdded`, `renamedTranscripts` or `droppedFeatures` is not empty, or the set holds an extra, each reason comes before `Build`, such as `LGE gave 13 genes an exon from their CDS and stop codon (ND1, ND2, COX1 and 10 more), and the set keeps no GTF with those exons, so STAR would count 0 for them.`, `The set holds the extra <name>, which has no GTF line.`, `LGE renamed <n> transcripts.` or `LGE left out <n> features with no gene_id.` A build of the same inputs publishes beside the old set under its new id, and the old set goes only when the person asks (section Cleanup).

## STAR indexes on Linux

The plan of a STAR index pins the set's `derived/genes.gtf`, its genome and each extra FASTA, and never the annotation as given. A set of schema 1 is refused through `requireCountingGTF()` in the words of section A set written before its counting GTF, and the plan adds no refusal of its own. Its step runs STAR with the argv of `scripts/repro/rnaseq/gse225770/star.sh`, which is 8 threads, `--genomeSAindexNbases` from the bases of the FASTA files and `--genomeSAsparseD 2`, unless `index-plan --genomeSAsparseD <n>` names another whole number from 1. A larger value needs less memory and maps more slowly. It also changes which reads map. On 2 million reads of a 30 Mb slice of GRCh38, mapping at 1 and at 2 differed in tens of thousands of reads and in hundreds of GeneCounts rows, for STAR 2.7.3a and 2.7.11b alike, so compare a result only with an index of the same value. STAR's own default is 1, which the scripts of `scripts/repro/rnaseq/gse304256/star.sh` and `scripts/repro/rnaseq/gse152418/star.sh` run, so an index that must equal their runs needs `--genomeSAsparseD 1`. A value of 1 keeps every suffix and needs about twice the suffix-array memory of 2, and the request figures below were measured at 2, so the plan writer refuses 1 without `--request-memory-mib`. A value of 0 is refused in words. It adds `--sjdbOverhang 100`, which is STAR's default and the value of every reproduction script that sets it, so the plan and the key name it. The plan and its key are `STARIndexPlan` and `STARIndexKey` in `Sources/LungfishWorkflow/RNASeq/`.

The index stays on the Linux machine. Each of its 15 files is its own `staged` output, never a folder and never packed, since the batch remaps one file a name (`docs/formats/executor-plan.md`, Outputs that come home and outputs that stay). The job's `Log.out` comes home. No step of the plan writes gzip. A STAR index is never byte-pinned across platforms, so the plan pins the FASTA, the GTF and the argv.

The key names the index as the salmon key does. Its folder name is `star-<version>-sa<n>-sparse<d>`, such as `star-2.7.11b-sa14-sparse2`. The key holds the set id, the STAR pin, `--genomeSAindexNbases`, `--genomeSAsparseD`, `--sjdbOverhang`, the genome and the extras in the gentrome's order, the sha256 of `derived/genes.gtf` and the sha256 of `reference-set.json`.

Two commands drive the build. `lungfish-cli rnaseq index-plan --set <set> --output <folder> --staging-folder <path>` writes the plan folder, with `--star 2.7.11b` or `--star 2.7.3a` and `--genomeSAsparseD <n>`. Its last line states the sparsity, as `STAR builds the suffix array with --genomeSAsparseD 2, LGE's default.` or, for another value, `STAR builds the suffix array with --genomeSAsparseD 3, where LGE's default is 2. A larger value needs less memory and maps more slowly, and it changes which reads map, so counts from indexes of different values are not equal. The key <key> holds the value.` `index-adopt` takes no such option, since it reads the value from the run's argv. It takes the executor, the image and its tool manifest from the app, or from `--executor-manifest`, `--image` and `--image-tool-manifest`. A run that `index-adopt` will read takes the manifest of the executor you built, since the plan pins it. `lungfish-cli rnaseq index-adopt <result folder> --set <set> --staging-folder <path> --batch <folder name>` reads the `run-record.json` that the run returned and writes the record below. It exits 3 and writes nothing when it refuses.

The adopted record is the one place a later plan finds an index. `STARIndexRecordStore` is its one owner and writes `<storage root>/rnaseq-index-records/<set id>/<key>/index-record.json` through `DurableReplace`. It holds the set id, the key, the tool `{id, version, build}` and, for each file, its path inside the index, its plan path, its staging path `<staging folder>/batches/<batch>/index/staged/<plan path>`, its bytes and its SHA-256. A record of schema 2 adds `run`, which names the run that built the index, so a later STAR or STARsolo result can name the executor build and the run. `run` holds five keys. `runRecordSHA256` and `runRecordBytes` are the SHA-256 and the length of the `run-record.json` the adopt read. `executor` is that run record's `executor`, key for key, with the binary's `sha256` and `size` and the plan's `buildPin` ([executor-run-record.md](executor-run-record.md)). `batch` and `sample` are the adopt's options. The store keeps a byte copy of that run record as `run-record.json` beside `index-record.json`, written through `DurableReplace` before the record, so the record is the commit point, and the copy's SHA-256 equals `run.runRecordSHA256`. A record of schema 1, which an adopt wrote before LGE kept the run, still reads with no `run`, and a plan pins its files with the same entries. A record of a schema above 2 is refused in words before the rest is read, as a set's is (the `schemaVersion` row above), and the words name the file, say to read the record with the LGE that wrote it, and say to remove that file and adopt the index again with this build. `STARIndexAdopt` reads the tool, `--genomeSAindexNbases`, `--genomeSAsparseD`, `--sjdbOverhang` and each file's bytes and SHA-256 from the run record, and never from the plan. Each staging path comes from `--staging-folder`, `--batch` and `--sample`. The set id, the FASTA paths, the sha256 of `derived/genes.gtf` and the sha256 of `reference-set.json` come from the set folder, and the run record must name that GTF by the same sha256. The adopt refuses in words a record that is not `succeeded`, one that names another set, one with no STAR step, one of a STAR other than 2.7.11b and 2.7.3a, one whose argv lacks a value of the key, one that lacks a staged file and one whose `executor` lacks `buildPin`, `sha256` or `size`. The store refuses a set id or key that is not one plain folder name. The same record again changes nothing, except that a copy which is missing or damaged is written again from the bytes the adopt read. Another record for the same set and key is refused in words that name the record's file and what differs, such as other digests, the same digests under another staging folder, another run record or another executor build. A refusal writes no copy, so the copy of the run kept is never touched. A schema 1 record of the same index is refused in words of its own. They say it was adopted before LGE kept the run, so it names no executor build, and that it was not replaced. To record the run, adopt with another `--storage-root`, or remove that file and adopt again. If the new record is the right one, remove that file and adopt again. No cleanup of LGE reaches `rnaseq-index-records/`, and a later cleanup that walks the storage root skips it as it skips the other two folders. The record names an index, so nothing removes it while a result's record names that index.

The STARsolo index is a variant of the same plan, never a second one. `index-plan --tenx-filter <list>` makes a GTF on the Mac from `derived/genes.gtf` by the 10x filter rule with the biotype list `mkgtf-3.0.0` or `gencode-2020-A` of `scripts/repro/rnaseq/tenx-controls/tenx_gtf.py`, and each list has its own rule version. Rule version 1 reads `mkgtf-3.0.0`. It reads a gene's biotype from its `gene` line, or from its `transcript` lines when the gene line names none, and keeps every line of a gene whose biotype is on the list. Rule version 2 reads `gencode-2020-A` as 10x's GRCh38-2020-A reference does. It keeps every line of a gene when one of its `transcript` lines has a `gene_type` and a `transcript_type` on the list and its text holds neither `tag "readthrough_transcript"` nor `tag "PAR"`. It reads the tags from the line's text, since a GENCODE line repeats `tag`. Neither version tests a line's own `gene_biotype`, and both keep the `exon` lines LGE wrote for a kept gene. Every line on an extra's record passes. Rule version 2 keeps GENCODE's versioned gene ids (ENSG00000243485.5) as derived/genes.tsv names them. 10x's GRCh38-2020-A moves the version into gene_version (ENSG00000243485), so a matrix compared with Cell Ranger's first drops the .<digits> suffix of each ENSG id. On GENCODE v32 the 36,601 kept ids stay distinct and equal 10x's. Of the 60,668 genes of GENCODE v32's primary assembly annotation, rule version 2 keeps those 36,601 and leaves out 24,067, and after 10x's version move its 2,765,969 lines equal 10x's GRCh38-2020-A `genes.gtf` line for line. 10x's file also opens with GENCODE's 5 `##` header lines, which `derived/genes.gtf` does not keep, so the digests of the two files differ. A set with no `gene_type` and `transcript_type`, such as an Ensembl or RefSeq set, keeps no gene under rule version 2, so the plan writer refuses it in words. The lists use Ensembl and GENCODE names. On the RefSeq set Macaca_fascicularis_5.0 (28,845 genes) gencode-2020-A is refused, and mkgtf-3.0.0 keeps 20,627, protein_coding only, since RefSeq writes lncRNA, V_segment and C_region, which its list does not name. Preview 2026.11.10 read `gencode-2020-A` by rule version 1, which tested each gene's biotype alone, so on GENCODE v32 it kept 887 genes that 10x's reference leaves out, and it wrote `made/tenx1-gencode-2020-A/genes.gtf`. `index-adopt` refuses a run that read that file in words that name both versions, so plan such an index again. The plan writer refuses in words a made file in which an extra's record, or a kept gene that LGE gave an exon, has no `exon` line. The file goes into the plan folder only, never into the set or the storage root, and the plan pins it as a `reference` entry with `path` `made/tenx<rule version>-<list>/genes.gtf`, which `staging-files.json` names from the plan folder. STAR's `--sjdbGTFfile` names it, and the rest of the argv is the bulk argv, `--genomeSAsparseD` included. The key adds `gtfFilter`, which holds the rule, its version and list, the made file's sha256 and size and the number of genes the rule left out, and its folder name ends in `-tenx<rule version>-<list>`, such as `star-2.7.11b-sa14-sparse2-tenx1-mkgtf-3.0.0` or `star-2.7.11b-sa14-sparse3-tenx2-gencode-2020-A`. The key's sha256 of `derived/genes.gtf` stays that of the unfiltered file. A bulk key holds no `gtfFilter`, so its bytes are as before. `index-adopt --tenx-filter <list>` makes the file again from the set and refuses in words a run record that read a GTF of another sha256, so it reads nothing from the plan. The rule is `TenxGTFFilter` in `Sources/LungfishWorkflow/RNASeq/`. The number of genes left out is the line of `index-plan` before the sparsity line, and the key's `genesLeftOut`.

The job's request figures are 8 CPUs, 40,960 MiB and 120 GiB for Macaca_fascicularis_6.0 with `--genomeSAsparseD 2`. They come from STAR's own peak of 29.79 GB and the 37.3 GiB of disk of REF's run on a node, and they reach no plan byte. A set of another genome takes its three figures from the person, and without them the plan writer refuses, since another genome needs its own SMOKE figures.

## The salmon index cache

RS-INDEX fills one cache of salmon indexes outside every project, `<storage root>/rnaseq-index-cache/`, keyed by the set id, the salmon version, k and the decoys (`docs/plans/2026-10-02-architecture-program.md:194`).

```
rnaseq-index-cache/
  <set id>/
    salmon-<version>-k<k>-<decoys>/
      index-key.json
      .lungfish-provenance.json
      provenance/
      index/
      uses/
        <sha256 of a result path>.json
```

`<decoys>` is `genome-decoys` or `no-decoys`. C1's index, salmon 2.11.0 with k 31 and the whole GRCh38 primary assembly as decoys (`scripts/repro/rnaseq/seqc-gse47774/index.sh:2-3,9`, `Tests/Fixtures/rnaseq/salmon-c1/SRR896663/aux_info/meta_info.json:2`), would be `salmon-2.11.0-k31-genome-decoys`. `index/` holds the files salmon wrote. `index-key.json` holds the four key fields, the set's `reference-set.json` sha256, salmon's build, the argv, and the four index hashes, `index_seq_hash`, `index_name_hash`, `index_decoy_seq_hash` and `index_decoy_name_hash`, which every quantification repeats in its `aux_info/meta_info.json` (`Tests/Fixtures/rnaseq/salmon-c1/SRR896663/aux_info/meta_info.json:20-25`). Each result's record names them (`docs/plans/2026-10-02-architecture-program.md:194`).

Every build passes `salmon index -t <gentrome> -d <decoy names> -k <k> -p 8 --ramLimit 4 -i index`, and no `-d` pair for `no-decoys`. `-p` and `--ramLimit` are fixed, never chosen by the Mac's memory or by the person, and are not in the key, since `--ramLimit` changes no byte of the index (Phase 5.1 ruling ADJ-SPIKE-BIO, items 1 to 5). With GRCh38 chromosomes 1, 2 and 3 as decoys, `--ramLimit` 1 and 16 gave byte-equal index files and `quant.sf`. At full scale, RS-INDEX's one build of GRCh38 with ERCC92 at `-p 8 --ramLimit 4` (set `homo_sapiens-GRCh38-ensembl100-lge-a149f6aa50d5`, salmon 2.11.0 build `hfc06a8d_0`, galah, 2026-11-14) gave all nine index files byte-equal by `cmp` to C1's build at `--ramLimit 16`, and the `quant.sf` of SRR896663 on that index byte-equal to C1's (sha256 `7bef17c6d4a502aa5b5cb1d940b77976e0d91c13fe979c925dd1a47c5dc1240d`). The four index hashes cover the input sequences and names only, so they are no evidence of equal bytes, and the nine `cmp` results are. That one build did not test a second build of the same key, another sample or set, a `-p` other than 8, another salmon build or another host. The argv in `index-key.json` names the stage's files by their names in it (`gentrome.fa`, `decoys.txt`, `index`). The gentrome is the set's `derived/transcripts.fa` and then, for `genome-decoys`, the set's genome, and each decoy name is a genome header up to its first space or tab (`scripts/repro/rnaseq/seqc-gse47774/ref.sh:28-31`). Both are written in the stage's `.work/`, which goes before the rename. The salmon version of the key comes from the `conda-meta` record of salmon's environment, so a reuse starts no process. A build whose `info.json` gives another `k`, `salmon_version` or `num_decoys` than it asked for publishes nothing.

### Its one owner

`SalmonIndexCache` in `Sources/LungfishWorkflow/RNASeq/`, which RS-INDEX writes, is the only writer under `rnaseq-index-cache/` (`docs/contracts/EXPERT-PANEL.md:49`), and `lungfish-cli rnaseq index` is its command. Before a build it checks with `RunFitPreflight` that the Mac has about 16.6 GB of memory and 64 GB of free disk, and checks again with a need scaled from the gentrome when that is larger than GRCh38 with ERCC92's (Phase 5.1 ruling ADJ-SPIKE-ARCH, items 1 to 5). A reuse runs no check. It builds in a staging folder `.salmon-<version>-k<k>-<decoys>.creating-<UUID>` beside the final name, writes `index-key.json`, then the root record last, and renames the folder into place with `RENAME_EXCL` through `PortableRename` (`AGENTS.md:76`). A second build of the same key that loses the rename removes its staging folder and uses the published index, so a second run reuses it (`docs/plans/2026-10-02-architecture-program.md:194`). C1's decoy-aware index at `--ramLimit 16` took 53 minutes and 23.7 GB on a loaded galah (`docs/plans/2026-10-02-architecture-program.md:174`). LGE's at `-p 8 --ramLimit 4` took 19 minutes 19 seconds on the same Mac at a load of 10 to 47, with a peak resident set of 20,371,177,472 bytes as `/usr/bin/time -l` reports it for the CLI and salmon together (RS-INDEX stage run, 2026-11-14). The check compares the Mac's memory with 17,780,281,048 bytes, the peak memory footprint of the `--ramLimit 16` build, which bounds the 15,681,106,880 bytes of a build at `--ramLimit 4`, and the free disk with 63,897,293,195 bytes (SPIKE-SALMON, 2026-11-14), so a build that cannot fit is refused in words before it starts (`docs/plans/2026-10-02-architecture-program.md:196`).

### The index a Linux plan pins

`lungfish-cli rnaseq quant --write-plan` plans a run on a Linux machine with the index this Mac published for the set at `salmon-<salmon version of the image>-k<k>-<decoys>`. It never builds one. It pins each file under that folder's `index/` as a `reference` entry whose `index` holds `{key, tool}`, where the key is the folder name and the tool is the salmon `{id, version, build}` of `index-key.json`, so the batch copies the files to the staging folder with the plan. A set with no index of the image's salmon version in the cache is refused in words that name `lungfish-cli rnaseq index`, and an index of another salmon version counts as missing. The job's request figures are galah's until a node measures them (`Sources/LungfishWorkflow/RNASeq/SalmonPlanSubmit.swift:24-62`), and they reach no plan byte. CPUs equal salmon's `-p`, 8 unless `--request-cpus` names another number. Memory is the 5,960,744,960-byte peak of SRR23580170 (71.9 million pairs, 8 threads) plus 2 GiB, rounded up to a whole GiB, which is 8,192 MiB for Macaca_fascicularis_6.0. Disk is 1.25 times the sum of the reads, twice the reads when Trim Galore trims, the index and salmon's 1,077,186,560 bytes of temporary files, rounded up to a whole GiB, plus 8 GiB. A set of another genome has no measured peak, so it needs `--request-memory-mib`, `--request-cpus` and `--request-disk-gib` together, and the writer refuses in words without them.

### Cleanup

Cleanup deletes nothing a record names (`docs/contracts/EXPERT-PANEL.md:51`), and an index is never deleted while a record names its hashes (`docs/plans/2026-10-02-architecture-program.md:194`). No cleanup of LGE reaches these folders today. Launch cleanup removes only temporary folders with LGE's prefixes (`Sources/LungfishCore/Services/TempFileManager.swift:75-83`), and `lungfish-cli storage dedupe` replaces duplicate files with APFS clones and keeps every byte (`Sources/LungfishCLI/Commands/StorageCommand.swift:101-104`).

- No automatic cleanup deletes a set, an index or a file in either. A later cleanup that walks the storage root skips `rnaseq-reference-sets/`, `rnaseq-index-cache/` and `rnaseq-reference-downloads/`.
- `lungfish-cli rnaseq install-reference --default <id>` (Plugin Manager > Databases) keeps the genome and GTF it downloads in `rnaseq-reference-downloads/<id with / as ->/`, named as their URLs name them, because the set's record names each input path as it was given. A second install finds them by their sha256 and downloads nothing. A half-written file is `.<name>.partial-<UUID>` in that folder and the run removes it whether it ends or fails.
- A result whose record names an index or a set gets one file in that folder's `uses/`, `<sha256 of the result path>.json`, holding the result's path and its record's sha256. The owner creates it once and never rewrites it, so two runs never write one file.
- Only the owner removes an index or a set, and only when the person asks. It lists the uses and refuses in words while a listed result still exists and its record names that index's hashes or that set's id. A use whose result is gone, or whose record names other hashes, holds nothing. A use of an index holds it while the result's `.lungfish-provenance.json` holds each of the index's hashes. Removing the last index of a set also removes that set's empty folder in `rnaseq-index-cache/`.
- A set stays while an index or a use names it.

Two events leave folders that these rules must still reach.

- A crash leaves a staging folder, `.<name>.creating-<UUID>`, in either folder. No record names it, so the owner removes the ones that no running build holds before it starts a build, and removes nothing else. A running build holds its stage with an exclusive `flock` on the folder, so a stage whose lock the owner can take is one a crash left.
- A change of storage root copies `databases` to the new root and runs the tool install there, then removes from the old root only `conda`, `databases` and the receipt, and the root itself when it is then empty (`Sources/LungfishWorkflow/Storage/ManagedStorageCoordinator.swift:43-44,75-76,104-120`). It leaves `rnaseq-reference-sets/` and `rnaseq-index-cache/` at the old root and removes none of them. The copy that carries them is `ReferenceSetOwner`'s copy of each set to the new root, which checks every sha256 at the new root first and is not built in 5.1, and neither adds a folder to the list at `Sources/LungfishWorkflow/Storage/ManagedStorageCoordinator.swift:104-108` before that copy exists.
