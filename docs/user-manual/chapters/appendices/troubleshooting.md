## What it is

Lungfish Genome Explorer (LGE) is a window over a set of established programs that were built to be typed at rather than clicked. LGE runs those programs for you and shows you the results. When something goes wrong, the message you see often came from one of those programs rather than from LGE itself, so it may use words LGE never uses. This appendix collects the symptoms people actually meet, says what each one means in plain words, and gives the action to take.

The appendix is organized by what you see on screen rather than by which part of LGE is at fault. Look up the pale gray menu item, the message, the run that stopped, or the missing result, and read across. Each entry names the chapter that covers the operation in full. The last main section, [Known defects in this release](#known-defects-in-this-release), is the one list of faults in LGE itself that this manual keeps, each with a workaround and the build it was checked against, and [Defects by chapter](#defects-by-chapter) finds the rows for one chapter.

To check which release you have, open the app's own menu, the one named for the app beside the Apple menu, and choose **About Lungfish Genome Explorer**, or **About Lungfish Genome Explorer Preview** in a Preview build.

Some sections are read in the window and some need commands typed into [Terminal](../../GLOSSARY.md#terminal), and each says which at its start. Two words are worth fixing first. An [exit status](../../GLOSSARY.md#exit-status) is the number a command hands back when it finishes, where zero means it succeeded and anything else means it stopped. A [working directory](../../GLOSSARY.md#working-directory) is the folder a Terminal window is sitting in when you type a command, and typing `pwd` and pressing Return prints it.

## Before you type anything

Open Terminal from **Applications > Utilities**. The `lungfish-cli` program ships inside LGE, but a bare `lungfish-cli` finds nothing until you do the path step in [Finding the program](cli-reference.md#finding-the-program), so do that first in every new Terminal window. A word in angle brackets, such as `<name>`, is a placeholder, so replace it, brackets included, with your own value. [Reading an On the command line block](../01-foundations/06-the-lungfish-project.md#reading-a-command-line-block) explains commands and paths.

## Start here, at the failed row

This section is done entirely in the LGE window.

A run that fails turns its row red in the [Operations Panel](../../GLOSSARY.md#operations-panel), which opens with **Operations > Show Operations Panel** (Cmd-Shift-P). Before you read any table below, right-click that row and choose **Copy Failure Report**, then paste it into a note or an email to keep it. On a trackpad with no second button, hold Control and click, or click with two fingers. Copy the command from the report rather than retyping it from memory, because a fresh typing mistake hides the real one.

Click the **Log** button at the right of the row, or select the row, to open its details pane. The pane shows the error message, the command LGE built on your behalf under **Command**, and the log the tool wrote. Read the error message first, then the last lines of the log, where a tool usually says why it stopped, and then the command.

<!-- SHOT: operations-panel-failed-row -->

The right-click menu on a failed row offers every item [The Operations Panel](../01-foundations/06-the-lungfish-project.md#the-operations-panel) describes, and three more that only a failed row has.

| Item | What it gives you |
|---|---|
| **Copy Failure Report** | The operation title, the command, the error message, the longer detail, and the log, as one block ready to paste |
| **Open GitHub Issue** | A pre-filled issue in your browser carrying the report, which you review and submit yourself |
| **Reveal Failure Report in Finder** | The report file on disk, offered once the file exists |

**Copy CLI Command** and **Copy Log**, on the same menu, copy the command alone and the log alone.

That [failure report](../../GLOSSARY.md#failure-report) file is written as the failure happens, so it survives quitting the app. It lives at `~/Library/Logs/<app name>/Operations/Failures`, where the tilde stands for your Home folder and the app name keeps a Debug or Preview build's reports apart from a stable build's. Library is hidden in Finder, so **Reveal Failure Report in Finder** is the easy way there. LGE keeps the 50 most recent reports and deletes the oldest each time it writes a new one, so copy a report you care about rather than assuming it will still be there next month. If LGE cannot write a report, for example because the disk is full, it skips the report without a second error, so a missing report says nothing about the operation itself.

### When an alert appears instead

A step that fails outside the Operations Panel, such as an import from a dialog, an export, or opening a project, shows an alert instead of a red row. Its title starts with "Could not" and names the step, such as "Could not import the VCF file". The first paragraph says what happened and the second says what to try. **Show Details** opens the error text the underlying tool gave. An alert offers no **Copy Failure Report**, so copy that text into a note or an email, since it is the part a report needs. A command that cannot act, such as a copy with no bases selected, shows the same kind of alert and says what was missing. A status bar message that is cut short shows in full when you hold the pointer over it.

## I cannot write to my project

This section is done entirely in the LGE window.

A [project](../../GLOSSARY.md#project) is the folder LGE keeps one piece of work in. A session is one open LGE window or one command-line run, and a project that another session holds opens read only, as [Shared Projects and Bundle Migration](shared-projects.md#reading-the-windows-read-only-state) explains. That appendix also gives the window route for clearing a lock left behind by a session that has really ended.

| Symptom | What it means | What to do | Chapter |
|---|---|---|---|
| The window title shows ` (Read Only)` after the project name, and an alert about the lock came first | Another session holds the [project lock](../../GLOSSARY.md#project-lock), or LGE could not read the lock file to find out. | Ask whoever has the project open to close that window or run, then reopen the project. If nobody has it open, choose **Recover and Open** when the alert offers it, as [Deciding whether to recover](shared-projects.md#deciding-whether-to-recover) describes. | [Shared Projects and Bundle Migration](shared-projects.md) |
| The window title shows ` (Read Only)` and no lock alert appeared first | The project has no [project store](../../GLOSSARY.md#project-store), because it was built only with `lungfish-cli` or copied without its hidden files, and an alert titled Opened Read Only says so. Otherwise LGE cannot write to the project folder or its store. | Check that your account can write to the folder, for example that it is not on a read-only drive or owned by another user. In Finder, select the folder, press Cmd-I, and read **Sharing & Permissions**. A folder built only on the command line gains its store once it is created in the app. A copied project needs the whole folder copied again, hidden files included, meaning files whose names begin with a dot. | [Shared Projects and Bundle Migration](shared-projects.md#what-read-only-looks-like) |
| An alert titled with the project name and "may already be open" names a user, a host, and a process id | A live lock from a named session. The alert's details name the account, the computer holding the lock, and the [process id](../../GLOSSARY.md#process-id) (pid), the number macOS gave that running copy of the app. | Ask the person who uses that computer to close the project there. Use **Recover and Open**, if the alert offers it, only after they confirm the session has ended, since clearing a live lock is how two writers end up in one folder. | [Shared Projects and Bundle Migration](shared-projects.md) |
| An alert headed "Project Is Open Read Only" appears when you click Run | You started a workflow that writes into the project while writing is blocked. The alert names the workflow. | Close the other session, then close and reopen the project. The alert keeps appearing until you reopen it, because reopening is what gives the lock to your window. | [Shared Projects and Bundle Migration](shared-projects.md) |
| The lock alert says the project's lock information is damaged | The lock file exists but LGE cannot make sense of it, so it cannot tell whether another session is using the project. Writing stays blocked until the lock is inspected or removed. | Make sure no other session is running, then clear the lock with **Recover and Open**, as [Shared Projects and Bundle Migration](shared-projects.md#deciding-whether-to-recover) describes. | [Shared Projects and Bundle Migration](shared-projects.md) |
| The lock alert says LGE "could not read the project's lock information" | LGE could not reach the lock information at all, so the alert offers only **Open Read-Only** and **Cancel**, with no **Recover and Open**. | Check that the project's storage is available, for example that its drive is connected, then open the project again. | [Shared Projects and Bundle Migration](shared-projects.md#reading-the-windows-read-only-state) |

On network storage, meaning a drive that lives on another computer and is reached over the network, a reported locking failure is often not a real lock problem. Lock failures name `.lungfish/project.lock` for a project, or a `.install.lock` file inside the tool folder for a plugin install. Those names begin with a dot, so Finder hides them until you press Cmd-Shift-period in a Finder window. Before you ask anyone to change how that drive is connected, look in the project folder, or the tool folder for a plugin install, for stray files whose names begin with `._`, which macOS leaves on volumes that cannot hold its file metadata and which confuse the lock check. Delete any you find in Finder, since macOS writes fresh ones when it needs them.

A project on an exFAT or FAT drive, or on a network share, saves every analysis as it would on the internal drive. LGE writes each file so that a save cut short, for example by unplugging the drive, leaves a complete copy, and it puts that copy back under its name the next time the project opens.

## A run stopped and I do not know why

These entries name the exact text a run prints, so you can match what you saw. The fixes are done in the window except where a command is shown.

The exit status often sits in the failure report's error line, in words such as `lungfish-cli exited with status 64`. In Terminal, `echo $?` typed right after a command finishes prints its status. [Exit status](cli-reference.md#exit-status) in the CLI Reference lists every value, and these are the ones this appendix meets.

| Exit status | What it means here |
|---|---|
| 1 | The command refused or failed, for example a lock it may not replace. |
| 2 | A usage error the command itself catches, such as `tools update --apply` without `--yes`. Nothing ran. |
| 3 | An input error, such as a missing file or a pack name that was not recognized. Nothing was installed. |
| 4 | An output error, such as an output file that already exists or an expected workflow output that was not created. |
| 5 | A format error, such as a file `analyze validate` finds malformed or, with `--strict`, irregular. |
| 10 | `tools update --plan` found pending work, which is a report rather than a fault. |
| 64 | A workflow error. The command refused the work, the work failed inside a workflow step, or the command line could not be understood. |
| 65 | The Docker daemon, the background program that runs containers, could not be reached, so a pipeline that runs in containers cannot start. See [Containers and pipelines will not start](#containers-and-pipelines-will-not-start). |
| 126 | A tool the command needs is not installed. See [Tools and databases are missing](#tools-and-databases-are-missing). |

Exit 64 covers both a run started without a required setting and a run whose tool failed, so read the message rather than assuming a typing mistake.

An analysis step has no time limit unless you set one, so a long run keeps going until it finishes, fails, or you cancel it. On the command line, eight commands, among them `map`, `assemble`, `classify`, and `variants call`, take `--time-limit <minutes>`, which stops any step that runs longer than that many minutes. A step stopped that way usually reports that it "timed out after" a number of seconds, which is your minutes times 60. It stopped at the limit you chose, so raise the number, or leave the option out, and run again. Many task chapters say how long their example takes, in **Before you start** or in the steps that run it.

## A command refused me

Every entry here is a command typed into Terminal. A refusal means nothing ran and nothing on disk was changed.

| Symptom | What it means | What to do | Chapter |
|---|---|---|---|
| `genotype-cohort` stops with a message that at least two input FASTQ bundles are required | A [cohort](../../GLOSSARY.md#cohort) is the group of samples compared together, so one bundle is not a cohort. [FASTQ](../../GLOSSARY.md#fastq) is the text format holding sequencing reads and their quality scores. | Pass two or more bundles, or run `fastq genotype` on the single sample instead. | [Running Amplicon MHC Genotyping](../09-genotyping/02-running-genotyping.md) |

## Tools and databases are missing

Every check in this section is a command typed into Terminal. The Plugin Manager, **Tools > Plugin Manager…** (Cmd-Shift-B), is the window route for seeing and installing what these commands report as missing, since its **Packs** tab marks a tool that needs work **Needs install** or **Needs reinstall**, as [What a missing tool looks like](../01-foundations/07-plugin-packs.md#what-a-missing-tool-looks-like) explains.

Most LGE operations run their tools from private folders of software, one per tool, called environments. A missing-tool error means an environment is absent, not that the operation is unsupported. On the command line the message begins with the words Required tool is missing and then names the tool, and the command exits 126. Install the pack that holds the tool, as [Plugin Packs](../01-foundations/07-plugin-packs.md#procedure) shows. A [plugin pack](../../GLOSSARY.md#plugin-pack) is a themed group of tools LGE installs on request.

A [dependency set](../../GLOSSARY.md#dependency-set) is the exact list of tool versions one LGE release was built and tested against. `lungfish-cli version --tools` prints the app version, the dependency set, and a table of every tool the release pins, marked bundled for a tool inside the app and managed for one LGE installs for you. The table lists what the release expects, not what is installed on this Mac.

The first check for any missing-tool error is `lungfish-cli tools update --plan`, which lists every install, reinstall, removal, and database update this machine is missing against the [pinned](../../GLOSSARY.md#pinned) set, the exact versions of the dependency set. It exits 10 when work is pending and 0 when there is none. A line starting `install` or `reinstall` names a tool to fetch, and a line starting `preserve` names a tool you installed yourself that LGE leaves alone, and tells you how to switch to the pinned build if you want it.

`lungfish-cli debug env --check-tools` is a quicker look at eight common programs, among them Nextflow, samtools, and bcftools, and prints each as `<name>: <version> - <description>` when it finds the program or `<name>: not found - <description>` when it does not. It looks only where Terminal itself finds programs, not in LGE's private environments, so a tool LGE installed for its own use can read not found here, and the result settles only whether you can run that program yourself in Terminal. Add `--tool <name>` to check one.

Three more `debug` commands help when you report a problem. `lungfish-cli debug resource-smoke` checks that the files packed inside the app, such as its built-in primer schemes and workflow recipes, can be found, and prints `debug-resource-smoke-ok` when they can. `lungfish-cli debug workflow-log <path>` reads a Nextflow or Snakemake log file or work folder, and `--errors-only` keeps only its error messages. `lungfish-cli debug fastq-ingest <file>` runs the storage steps of an app import on one FASTQ file and writes the result into the working directory unless `--output-dir` names another folder, which shows whether the import or the file is at fault.

Databases are managed apart from tool packs. Use `lungfish-cli conda db list` to see what is available and installed, `lungfish-cli conda db recommend` to see which Kraken 2 database suits this Mac's memory, and `lungfish-cli conda db download <name>` to fetch one. EsViritu has its own pair, `lungfish-cli esviritu download-db` and `lungfish-cli esviritu db-status`. The window route is [The Databases tab](../01-foundations/07-plugin-packs.md#the-databases-tab).

Two messages come from the lock LGE takes while it changes its tool folder, where [conda](../../GLOSSARY.md#conda) installs LGE's tools and which `lungfish-cli conda --help` names. Running two installs at once prints `waiting for conda lock held by pid <n>`, where the pid, short for process id, names the other install's process, and then continues by itself once that install finishes. A tool folder you cannot write to prints `conda root is read-only; reinstall as the admin user`, which is about the folder's permissions rather than the pack. An admin user is an account allowed to install software, and whoever set up the computer can tell you whether yours is one.

If a pack install sits at solving the environment for many minutes, a proxy is the usual cause, meaning a machine your network sends downloads through. Ask whoever runs your network whether one is in use and what its address is. Then quit LGE, open Terminal, set the [environment variable](../../GLOSSARY.md#environment-variable) `HTTPS_PROXY` with `export HTTPS_PROXY=http://proxy.example.org:8080`, using the address they give you, and start LGE from that same window with its full path, in quotation marks because the app's name can hold a space. For the Stable app that is `"/Applications/Lungfish.app/Contents/MacOS/Lungfish"`, and for a Preview it is `"/Applications/Lungfish Preview.app/Contents/MacOS/Lungfish"`. An app opened from the Dock does not see the variable. The download tool reads that variable, not LGE itself.

## Containers and pipelines will not start

Every check in this section is a command typed into Terminal, apart from starting Docker Desktop.

A [container](../../GLOSSARY.md#container) packages a program with everything it needs so it behaves the same on every machine. Viral Recon and TaxTriage run their steps inside containers through [Docker](../../GLOSSARY.md#docker) Desktop, a separate app you install yourself, and when Docker Desktop is not running they fail with "Docker daemon unreachable" or with messages that do not name it at all. [Tools that run in containers](../01-foundations/07-plugin-packs.md#tools-that-run-in-containers) says which tools need it and how to install it. The TaxTriage dialog's **Prerequisites** row shows Docker Desktop as **Running**, **Not running**, or **Not installed** before you start a run.

Start Docker Desktop first and wait until its whale icon sits in the menu bar. Then run `lungfish-cli debug container`, which checks the Docker Desktop connection the pipelines use. A working machine prints `Docker daemon reachable` under the heading "Docker (used by pipelines)", with the Docker version, and the command exits 0. When Docker Desktop is not running it prints `Docker daemon unreachable`, tells you to start Docker Desktop, and exits 65. A second section, "Apple Containerization (not used by pipelines)", reports Apple's own container system, which no pipeline uses, so its state does not matter here. Add `--pull-test` to check that the machine can also download an image, the packaged copy of a tool, through Docker. For a TaxTriage run, `lungfish-cli taxtriage check-prerequisites` checks Nextflow and the container runtime together before you commit to a run.

No setting lets these pipelines run without Docker. `lungfish-cli workflow run` lists `docker`, `conda`, and `local` for its `--executor` option, which [`workflow run`](cli-reference.md#workflow-run) describes, but it refuses any value other than `docker` for an nf-core pipeline before anything runs, and the window offers no other choice.

`lungfish-cli debug env` on its own is a quicker check that probes no tools. It prints the macOS version, the core count, the memory, the processor architecture, and whether Apple Containerization is available, and it reminds you that pipelines run through Docker Desktop. None of those figures is a target to match.

## Is this file or bundle intact

Every check in this section is a command typed into Terminal. There is no window route for these three.

`lungfish-cli analyze validate <files>...` checks whether a sequence or variant file is well formed. Add `--strict` to reject files that are readable but irregular. In a FASTA file it reports duplicate record names, empty records, and characters outside the nucleotide and protein alphabets. In a FASTQ file it reports duplicate read names and empty reads. In a VCF it reports data lines whose number of columns disagrees with the `#CHROM` header line, and records that repeat an earlier position with the same bases. A file that fails exits with status 5, so ask whoever supplied it for a corrected copy. `lungfish-cli bundle validate <bundle>` checks the structure of a reference bundle.

`lungfish-cli provenance verify` checks a signed [provenance](../../GLOSSARY.md#provenance) record, and signing is off by default. On an ordinary unsigned [provenance sidecar](../../GLOSSARY.md#provenance-sidecar) it exits 64 and reports that the signature artifact is missing, which means "not signed" rather than "not valid". To check an unsigned record, open the sidecar, the file beside the output or inside a bundle's `provenance` folder, in any text editor, read its `exitStatus` field, and check that the output files it lists exist.

Missing index files regenerate by themselves. An index file is a small companion that lets LGE jump straight to one part of a large file rather than reading all of it. LGE rebuilds a `.fai` (for a FASTA file), a `.bai` (for a BAM alignment file), or a `.tbi` (for a compressed VCF or BED file) the first time an operation needs one. If that rebuild fails, the underlying tools are `samtools faidx`, `samtools index`, and `tabix`.

## Reporting something this appendix does not cover

Gather the failure report first, with **Copy Failure Report** on the failed row's right-click menu, since it already holds the command, the message, and the log. Then add the app version, which **About Lungfish Genome Explorer** shows, or **About Lungfish Genome Explorer Preview** in a Preview build, and `lungfish-cli version` prints, and the macOS version from the Apple menu's **About This Mac**. The installed tool versions from `lungfish-cli version --tools` help but are optional.

The fastest route is **Open GitHub Issue** on the failed row's right-click menu, which opens a pre-filled issue in your browser. You review it and submit it yourself, so nothing is filed without your action. Submitting needs a free GitHub account. **Help > Report an Issue…** opens a new GitHub issue too, carrying the version string and the project's path and lock state, so it also needs an account. Without one, paste the failure report into an email to your instructor, your lab's bioinformatics contact, or whoever supports LGE where you work.

Leave your project's data files out of the report. The failure report holds LGE's own log and the command it ran rather than your sequences. The command does name your files and folders, and often your sample names, so read it before you send it and replace any name you may not share. Sequence data is rarely yours alone to share.
