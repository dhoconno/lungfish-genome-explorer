## Candidate, walk and release

The final candidate follows `docs/contracts/VERIFICATION-ORDER.md`. The unit tier runs once on a quiet Mac with no
lane building, then the replay suites and `python3 scripts/golden/golden.py compare`. A red tier whose only failures
are timed-out waits in tests that check no result gets one rerun on the same commit. The release notes are written for
bench scientists, under 15,000 characters, with the technical record and the owner check list as separate files in
`docs/reports/`. `python3 scripts/release/release.py package preview` makes the candidate, the XCUI smoke runs on it,
and the manager walks it by computer use with the owner at galah.

The walk covers every changed screen, the `STABLE-WALK-*` rows and the reruns of item 3 of `## Carry-in from Phase 2.14`
(row 18 on a virus with several segments, row 80 route with no region selected, row 89 with the ruler at base zoom, row
80 images b at 500 bases or fewer and at 20,000 or more, row ONT with a staged ONT run folder, row 13), and rows 17 and
35 (O71, O72). Its corpus holds a renamed project, a copied project, a large reference and records from an older
release. Before each drop the manager takes a screenshot of Finder's selection and lists the project before and after.
Fresh results are made in a copied project before any Extract. Each finding gets a severity, S1 and S2 are fixed, and
only the changed screens are walked again.

On the owner's go `main` is pushed by fast-forward, `release.py setup` runs right before `release.py publish preview`,
and the Preview is published. On a second go the Stable notes file with `## Included preview releases` is committed,
the full tier runs, then `release.py package stable`, `setup` and `publish stable`.
