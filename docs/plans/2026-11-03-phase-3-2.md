sidebar lists every kind through one registry. A BLAST search that gets stuck at NCBI no longer fails or holds up the work.

### It is a known problem

Now and then a search gets stuck at NCBI. It reads `Status=WAITING` for hours, while the same request sent again comes back in
a minute or two. Biopython users have met this for years: a stalled `qblast` that a restart cured in 2015, retry loops in 2017,
searches stuck for 40 minutes in issue 2865 in 2020, and online tests that tend to time out in issue 4870 in 2024. NCBI publishes
no time and no cause, and says it favours interactive users. So LGE has to cope with it, and no test may count on it not
happening. We do not know why a search sticks, and only NCBI could say.

### What LGE does (row BLAST-RESEND with BLAST-TIMEOUT-COLLECT)

| Rule | Detail |
|---|---|
| A search is a file | `NET-CLIENT.md` section 4b sets it: saved before the POST, the request ID before any check, every state change after. No limit in the client ends a search. Only NCBI's answer or the person does |
| Send again at about three minutes | Not READY at about 3 min: POST the same bytes again. Again at about 6 min. Three sends in all. Check each live copy once a minute, and the first READY wins. One constant, checked against the field log |
| A bad-day guard | Two spent searches in a row pause copies for an hour, and at most 4 copies go out in an hour. A copy never refuses a first send. On 2026-11-02 rotavirus stuck 6 of 6 and one resend stuck too, so a copy will not always help, and a stuck NCBI should not get more load from us. `SCR/rulings/ARCH-BLAST-RESILIENCE.md` sets the rest |
| Every copy stuck | The row reads waiting at NCBI, not failed, and keeps its request IDs. Checks slow to every 5, then 15, then 30 min, and go on through NCBI's retention. Known: READY at 26.8 h, UNKNOWN by 48 h. The result comes back onto its row on its own, also after a quit, through one `lungfish-cli blast resume` per in-flight search at launch. The person can send again or stop |
| A failed contact is no news | Any status or result contact that fails is counted and tried at the next tick, as `NET-CLIENT.md` section 4b sets |
| What the record keeps | The bytes sent, every request ID tried, which copy won and when. The verdict reads the winner alone. Replay sends the same bytes |
| Counting | First sends count against 50 reads an hour, and every POST counts against 100. A copy never refuses a first send, and a re-POST counts as what it repeats. Contacts stay 11 s apart across processes. The words name LGE's limit as LGE's |

What 100% can mean (O131): **no search is lost, and that one can be promised.** Every accepted search ends in a stored result, or in NCBI's own answer shown with its ID. Time to a result is reported as a distribution and is never promised, because NCBI's queue sets it. If about 8% stick and copies draw independently, two sends leave 0.6% and three sends 0.05% waiting past 6 min. That is a guess until the field log shows it, and a bad day will not be independent. Each search adds a line to `<root>/blast/search-log.tsv`: ID, copies, seconds and how it ended.

### A different server or database

Recommendation, for BIO and ARCH to test. Keep NCBI `core_nt` as the default. Add a database the person controls, searched
with local `blastn`. Leave out a free server address until a lab asks for one and a real server is there to test against.

- No common server API exists. SequenceServer and EBI each have their own, EBI offers ENA and not `core_nt`, and ElasticBLAST
  is a beta command-line tool for AWS and GCP. NCBI's AWS image spoke the URL API, but its pages at
  `ncbi.github.io/blast-cloud` returned 404 on 2026-11-03.
- `blastn` is already managed, as `bioconda::blast=2.16.0` in the `full-length-mhc-genotyping` pack, and the URL API replies
  came from BLAST 2.17.0. A local `core_nt` is for a lab server and not a laptop. NCBI's metadata of 2026-10-24 gives 261 GB
  to download, 307 GB on disk, 132.3 million sequences and 92 volumes. The search speed on a Mac is not measured.
- The gains are real. Reads stay on the Mac, no queue or hourly limit applies, and a fixed database build suits a methods
  section.
- The main risk is scientific. A narrow database gives a read nothing to contradict it, which is the false Supported of the
  S1 BIO-NAOMGS-BLAST-SCOPE. A database built without tax IDs falls to the name rules that BLAST-NAME-PHRASE-LEAK describes.
- `BlastServiceEndpoints.swift` holds that no option, project file, defaults key or downloaded field can name a host, so that
  no project can send reads to a stranger. Any new choice lives in Settings, and a replayed record asks before it uses one.

## Candidate, walk and release

The candidate follows `docs/contracts/VERIFICATION-ORDER.md`. The unit tier runs once on a quiet Mac with the xctest defaults
keys absent before and after, then the replay suites, `python3 scripts/golden/golden.py compare` and the executor plan
replay with no skip. `release.py package preview` makes the candidate, and the XCUI smoke and the view-switch tests run on the
packaged app in a session that does not lock. The release notes are written for bench scientists, under 15,000 characters,
with the technical record and the owner check list as separate files in `docs/reports/`.

A Preview round (`SCR/rulings/QA-ROUND-RERUN.md`) runs the unit tier whole on the exact commit, the replay suites, the golden compare and the executor replay, `package preview`, the XCUI smoke whole, the walk of the changed surfaces, the evidence read and the publish, and no full tier. The replay suites, the golden compare and the executor replay carry from their last green run only when the diff since it holds no path under `Sources/`, `Package.swift`, `Package.resolved`, `config/`, `Tests/Fixtures/`, `Tests/Support/` or `scripts/golden/` and no file named for Replay, and the evidence read names the carried run and the diff.
The whole tier runs once after the publish, off the path, and finishes before the next `package`. Before it starts, `DatabaseStorageLocation` and `msaBottomPane.isOpen` are cleared from `com.apple.dt.xctest.tool`. A run of `--tier full --bundles X` with no `--rerun-of` covers nothing.
For the Stable of about 2026-12-03 every fix round is a Preview round, the whole tier runs once on the Preview commit that passed its walk, a red tier takes `--bundles` and `--rerun-of` only for a fix inside test folders, and the last candidate runs the full tier, the unit tier on its own commit, replay, golden, executor replay, `package stable` and the XCUI smoke on the Stable bytes.

The walk covers every changed screen by computer use, on an unlocked screen. It includes one live BLAST search from each changed
route as a smoke, under the rules of Tests that do not count on BLAST. Each finding gets a
severity, S1 and S2 are fixed, and only the changed screens are walked again. One fresh QA expert, Sonnet at effort max, reads
the evidence as the Evidence read row sets, and `release.py publish --evidence-read` refuses a candidate with no PASS file, as lane QAGATE sets. Under the standing go, `main` is pushed by
fast-forward, `release.py setup` runs right before `release.py publish preview`, and the manager reports the release facts and
the yank command. After that Preview, the issue 35 comment goes up and the issue closes.
