## What the BLAST review found

The 3.1 manager reviewed this on 2026-11-03 from the walk records, the saved BLAST records and the code at `d60aa6d53`. It
sent nothing to NCBI, so the counts below are the walks' own and no new test ran.

### Is NCBI flaky

Partly. The direct cause of the timeouts is NCBI's queue, but the failures do not look random.

| Measure, 2026-10-27 to 2026-11-03 | Result |
|---|---|
| Sends that reached NCBI | 20. 13 came back, each in 32 to 67 s, and 7 were still queued when the app stopped at 10 minutes. No send fell in between |
| 1 or 2 sequences, `core_nt` | 9 of 10 came back |
| 3 or more sequences, `core_nt` | 2 of 8 came back, and 0 of the last 6, all since 2026-11-01 21:52 UTC |
| 3 or more sequences, `nt` (the Kraken2 route) | 2 of 2 came back, both on 2026-10-27 |
| The same 7 reads, byte for byte | Back in 33 s once, then stopped at 10 minutes three times |
| After the app stopped | Plain `curl` read WAITING on three requests for 3 to 4 hours, and they read READY by 11 hours at the latest, so the app was not holding them up |
| Sends of 3 or more sequences since the once-a-minute poll | None, so nothing shows whether that fix helped (row BLAST-POLL-NOT-SEEN-LIVE) |
| A send that never reached NCBI | On 2026-10-27 a 20-read send failed in 0.03 s on the app's own limit of 50 reads an hour, with the words `NCBI rate limit exceeded` |

Read count, virus and time of day cannot be separated. All six of the last timeouts of 3 or more sequences are rotavirus
rows. NCBI's developer page says its servers are shared and favour interactive users, that more than 100 searches in 24
hours moves a user to a slower queue, and that large projects should use a cloud provider or stand-alone BLAST. The walks
sent far fewer than 100 searches, but NCBI does not say how it identifies a user.

### Is the connector the cause

No record shows it. The app uses the BLAST URL API, the documented route and the one NCBI's own sample script uses, and
`blastn -remote` goes to the same servers, so another client would wait in the same queue. The connector does have weak
points of its own, and they turn a slow search into a failed one.

| Weak point | Code | What it costs | Row |
|---|---|---|---|
| A search is dropped at 10 minutes and cannot come back | `BlastService.swift:79`, `:809` | The failure people see most. A longer wait alone is no fix, because searches came back in about a minute or took hours. NCBI's sample script says it keeps results for 24 hours | BLAST-TIMEOUT-COLLECT |
| Three tries in about three seconds end a live search | `BlastService.swift:82`, `:891`, `:896`, `:1114` | A short outage or a 5xx ends a search that is alive at NCBI, and a failed fetch loses a finished one. No walk met it | BLAST-TRANSIENT-ENDS-SEARCH |
| The app's own limit reads as NCBI's | `BlastVerificationRequest.swift:321`, `:389` | 50 reads an hour is the app's limit, and the words blame NCBI. NCBI's published line, 100 searches in 24 hours, is not counted | BLAST-LOCAL-LIMIT-WORDS |
| Spacing lives in one process | `BlastService.swift:105`, `:108`, `:1299` | The app runs one `lungfish-cli blast submit` per send, so the 10-second gap does not hold across sends, and a fetch follows its READY check at once | BLAST-SPACING-PER-PROCESS |
| One no-reply address for every install | `BlastService.swift:70` | NCBI asks for an address it can reach, and cannot reach this one. Whether it treats every install as one user is unknown | BLAST-CONTACT-EMAIL |
| Multi-query replies come as a ZIP | `BlastService.swift:724`, `:814`, `:980` | Temp files and `/usr/bin/unzip` for each reply. `JSON2_S` is a listed format and came back as plain JSON on the four saved replies of 7 to 13 queries (59 to 109 KB). A small gain, and not a cause of any failure on record | BLAST-RESULT-ZIP |
| Five records kept for each read | `BlastVerificationRequest.swift:118` | NCBI's default `HITLIST_SIZE` is 100. Five is why the same HIV-1 reads read Supported and then Unsupported | BLAST-TIED-BEYOND-FIVE |
| Kraken2 searches `nt`, every other route `core_nt` | `TaxonomyViewController.swift:1422`, `BlastSubmitRoute.swift:79` | The same reads can get another verdict by route. The caption names the database, so the words are true | BLAST-KRAKEN2-NT |

The poll rate is already fixed, at once a minute (`BlastService.swift:76`), in Stable 2026.10.29.

### A different server or database

Recommendation, for BIO and ARCH to test. Keep NCBI `core_nt` as the default. Add a database the person controls, searched
with local `blastn`. Leave out a free server address until a lab asks for one and a real server is there to test against.

- No common server API exists. SequenceServer and EBI each have their own, EBI offers ENA and not `core_nt`, and ElasticBLAST
  is a beta command-line tool for AWS and GCP. NCBI's AWS image spoke the URL API, but its pages at
  `ncbi.github.io/blast-cloud` returned 404 on 2026-11-03.
- `blastn` is already managed, as `bioconda::blast=2.16.0` in the `full-length-mhc-genotyping` pack, and the URL API replies
  came from BLAST 2.17.0. A local `core_nt` is for a lab server and not a laptop. NCBI's metadata of 2026-10-24 gives 261 GB
  to download, 307 GB on disk, 132.3 million sequences and 92 volumes. The search speed on a Mac is not measured.
- The gains are real. Reads stay on the Mac, no queue or hourly limit applies, and a fixed database build suits a methods
  section.
- The main risk is scientific. A narrow database gives a read nothing to contradict it, which is the false Supported of the
  S1 BIO-NAOMGS-BLAST-SCOPE. A database built without tax IDs falls to the name rules that BLAST-NAME-PHRASE-LEAK describes.
- `BlastServiceEndpoints.swift` holds that no option, project file, defaults key or downloaded field can name a host, so that
  no project can send reads to a stranger. Any new choice lives in Settings, and a replayed record asks before it uses one.

### The probe

One script by the manager, no agent loop, at most 20 sends and at most 90 sequences in any 24 hours, so it stays under NCBI's
line however NCBI counts a search. It polls once a minute, waits 10 seconds between any two contacts, and logs every request
ID. It uses the walk clones and public test data only, under the standing go. It takes at most 2% of the budget, about $60.

It compares 1, 3, 7 and 20 reads, rotavirus against another virus, one request against one request per fragment, `core_nt`
against `nt`, and a real contact address against the shared one. It sets two decisions only, whether a send splits into one
request per fragment and whether the shared address goes. `SCOPE-AND-DELIVERY.md` says an upstream defect gets a retry and
not a study, so the probe stops at the first clear answer. A result with no clear answer is itself the answer, and the
queue stays a Known limit that BLASTCOLLECT makes bearable.

## Candidate, walk and release

The candidate follows `docs/contracts/VERIFICATION-ORDER.md`. The unit tier runs once on a quiet Mac with the xctest defaults
keys absent before and after, then the replay suites, `python3 scripts/golden/golden.py compare` and the executor plan
replay with no skip. `release.py package preview` makes the candidate, and the XCUI smoke and the view-switch tests run on the
packaged app in a session that does not lock. The release notes are written for bench scientists, under 15,000 characters,
with the technical record and the owner check list as separate files in `docs/reports/`.

The walk covers every changed screen by computer use, on an unlocked screen. It includes one BLAST search from each changed
route, and it reads the once-a-minute poll on a queued search if one comes (row BLAST-POLL-NOT-SEEN-LIVE). Each finding gets a
severity, S1 and S2 are fixed, and only the changed screens are walked again. One fresh QA expert, Sonnet at effort max, reads
the evidence as the Evidence read row sets, and no publish runs without its PASS. Under the standing go, `main` is pushed by
fast-forward, `release.py setup` runs right before `release.py publish preview`, and the manager reports the release facts and
the yank command. After that Preview, the issue 35 comment goes up and the issue closes.
