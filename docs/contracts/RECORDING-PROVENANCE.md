# Recording provenance

This contract says what a provenance record is in Lungfish Genome Explorer (LGE), which code writes one, and what may change while the writers converge. It answers review finding R8, where each new tool copied the nearest writer and picked its own file name. Provenance had 183 distinct writer code paths when sub-phase 2.4 began. Sub-phase 2.4 stopped LGE writing the two legacy run shapes, a bare `WorkflowRun` and a run nested in an envelope, and it froze every other writer and path helper behind two ratchets until the sub-phase that moves it.

## What a record is

A record is one `ProvenanceEnvelope` (`Sources/LungfishWorkflow/Provenance/ProvenanceEnvelope.swift`). One encoder, `ProvenanceEnvelope.encode(to:)`, turns it into JSON. One writer, `ProvenanceWriter` (`Sources/LungfishWorkflow/Provenance/ProvenanceWriter.swift`), rewrites its paths for the project, signs it when a provider is set and publishes it, so an envelope encoded anywhere else skips all three. `ProvenanceRunBuilder` assembles a record, `ProvenanceEnvelopeReader` reads one, and the `ProvenanceRecorder` actor gathers the steps of a multi-step pipeline until sub-phase 2.7. A rewrite, a signed write and an observed write publish through `DurableReplace`, as `docs/contracts/EXTERNAL-VOLUMES.md` describes.

## Rules

| Rule | Why |
|---|---|
| Write a record with `ProvenanceRunBuilder` and `ProvenanceWriter`, or with `CLIProvenanceSupport.recordSingleStepRun` in a CLI command | One encoder and one writer keep every record readable by the same readers |
| Never write a bare `WorkflowRun` or a nested `legacyWorkflowRun`, and never add a sidecar file name | Every shape and every name is one more thing each reader must learn |
| Never let finding, loading, listing, displaying or exporting a record change an existing file in a project | A read once rewrote a real TaxTriage record and cleared its signatures |
| Store the full SHA-256 of every byte, and never change path code that feeds a digest without a science review | A partial hash hides a cut file, and other records cite those digests |
| Keep reading every compat key and never write one again | Records written before schema version 2 hold them, and a version 2 record holds each fact once |
| Copy a step with `ProvenanceStep.with`, never field by field | A field-by-field copy drops every field added later |
| Capture a writer's facts before changing it, and never edit a frozen or expected file to make a test pass | A fixture edited to pass proves nothing about the bytes users already have |
| Never record the inherited environment | It holds API keys and home folders, and sidecars travel with shared projects |
| Record the writer's own executable as `<external>/<file name>` and no process ID, inside a project and outside one | An install path names folders on one Mac and a process ID names nothing after the run, while the name and the app version say which build ran. `ProvenanceRuntimeIdentity` does both for a writer, and a reader builds the identity a record holds through the initializer that takes `processIdentifier`. The alignment and tree records are not envelopes and keep both until 2.7 |
| Never raise a ratchet count without a reviewed reason | The counts are the only thing that stops the next copy |

| Typed records stay | A record that is also application state, such as `mapping-provenance.json`, keeps its own schema. 2.4 does not change it. |

## Status, parameters, stderr and hashes

| Field | Rule |
|---|---|
| Status | `ProvenanceEnvelope.status` is a stored `RunStatus` (`running`, `completed`, `failed` or `cancelled`) under the existing `status` key. The bytes do not change when it equals the status derived from `exitStatus` (nil is running, 0 is completed, anything else is failed). The decoder reads the key tolerantly and never throws over it. Cancelled is never derived, because a run cancelled in Bracken preparation can end with the exit status 0 of its last step. A writer records `cancelled` itself when the user cancels. In 2.7 `kraken2 classify` does too, with the exit status 125 taken from the cancel request and never from how a child ended (decision E5), where its record said failed before. Code that rebuilds an envelope from another passes `status: source.status`, and so do the rehydrators. Ten other rebuild sites in import, publication and markdup code and the lineage export still drop it, so a copy made there of a cancelled run can read failed, or completed when its last step exited 0, and 2.7 ends that with one copy helper. |
| Parameters | `ProvenanceRecorder.save(runID:to:bundleLayoutRoot:options:dropMissingRunLevelFiles:)` merges the run's parameters into the explicit options, and the caller's value wins on a clash. Since 2.10 the Kraken2 and EsViritu pipelines pass `readSetPlan` among the resolved defaults of the options they save with, so it is no run parameter (B16). |
| Stderr | A stored stderr over 10,240 characters keeps the whole lines that start it, within its first 2,048 characters, and the whole lines that end it, within its last 8,192, because tools print banners and versions first and errors and summaries last. A cut inside a line would leave a part of a path that the writer cannot rewrite. A window that holds no line break lies inside one line, so that side keeps nothing and a stderr of one long line keeps only the marker (2.8 decision P4). The cut never falls at a space or inside a line, because a path may hold a space, and a line in the middle that neither window holds is left out whole. A value of 10,240 characters or fewer is kept whole, and a value the rule already cut comes back unchanged. A blank value, one that holds only whitespace and line breaks, follows the same size rule in `truncated`, except that a blank value over 10,240 characters comes back empty, because neither of its windows holds a line and the cut would leave the marker alone, which reads as a stderr that said something. `normalized` answers nil for a blank value of any length and cuts every other value as `truncated` does. The omission marker carries no count, so it is the same in every run, and the golden normalizer (rule R13 in `scripts/golden/normalize.py`) replaces the line on each side of it and puts the same token on a side that keeps nothing. `ProvenanceStderr` in `Sources/LungfishCore/ProvenanceStderr.swift` applies the bound, and `RecipeStepResult`, `FastqScrubHumanSubcommand.normalizedStderr` and `limitedForProvenance` call it when a record is made, never when one is read. `CLIProvenanceSupport.recordSingleStepRun` in LungfishCLI applies no bound to a step's stderr, so only the run's top-level stderr is cut there. The capture is a step before the bound. A ToolProcess capture keeps the last 4 MiB of a stderr by default (`ToolProcessSpec.defaultStderrCaptureLimit`), so a capture that hit its limit starts inside a line, and on a path line that start is folder names without their root, which the writer cannot rewrite either. `ToolProcessResult.stderrWholeLines` in `Sources/LungfishCore/Process/ToolProcessResult.swift` drops the first line of such a capture through `ProvenanceStderr.wholeLines(ofCapture:truncated:)` before the bound applies. A capture with no line break lies inside one line and keeps nothing, and a capture that stayed under its limit comes back as it is. The drop also takes one whole line when the limit fell exactly at a line start, because the capture cannot tell that case from a cut inside a line. Every site that turns a result into stderr text that can reach a record reads `stderrWholeLines`. Those sites are the three builders of `NativeToolRunner`, `CondaManager.runTool`, the streaming stdout runner of `ManagedMappingPipeline`, `ProcessPBAANextflowRunner`, `ProcessGATKCommandRunner` and `ManagedToolSourceInstaller.run`. A site that only feeds a failure message may read `stderrText`, and a new adapter over ToolProcess that hands stderr to a recorder reads `stderrWholeLines`. A site that reads a log file instead of a ToolProcess result cuts the same way. `FullLengthONTMHCAlignmentProcessRunner` keeps the last 65,536 bytes of its stdout and stderr logs for a record, and its `boundedTail(of:)` passes them through `ProvenanceStderr.wholeLines(ofCapture:truncated:)`, with `truncated` true when the read started past the first byte of the log. A log of 65,536 bytes or fewer is kept whole, and a tail with no line break keeps nothing. |
| Hashes | A named file carries the full SHA-256 and size of every byte, through `ProvenanceFileHasher`. A partial hash is never right, because a cut or appended file differs only at its end. A digest cache may come in 2.7 under one key rule, which is volume UUID, inode, size, nanosecond times, a 2 second racy window and APFS or HFS+ volumes only. |
| Path code | Path code that feeds a recorded digest never changes without a science review. Known cases are `relativePath(for:relativeTo:)` in `ProvenanceFileHasher.swift`, `relativePath(of:from:)` in `MetagenomicsDatabaseInstallProvenance.swift`, `relative(_:to:)` in `PrimalScheme3DesignPipeline.swift`, `relativePath(from:to:)` in `FASTQPBAAArtifactStore.swift` and `CanonicalFilePath.relativePath(of:within:)`. That last helper builds the hashed path lines of `directoryChecksum(at:)` in `MultipleSequenceAlignmentBundle.swift`, of the same function in `MSAReferenceBundleBuilder.swift` through `visibleDirectoryFileRecords`, of `treeDigest` in `PhylogeneticTreeProvenanceIO.swift` and of `bundleDigest(checksums:)` in `TreeCommand.swift` through `regularFileRelativePaths(in:)`. Other records cite those digests, so even a bug fix changes recorded checksums. |

## How to write a record today

| You are writing | Use |
|---|---|
| One run in Workflow code | `ProvenanceRunBuilder`, completed with `complete(exitStatus:stderr:startedAt:endedAt:)`, then `ProvenanceWriter.write(_:to:)` or `write(_:toSidecar:)` |
| One tool run in a `lungfish-cli` command | `CLIProvenanceSupport.recordSingleStepRun` in `Sources/LungfishCLI/Support/CLIProvenanceSupport.swift`, which takes `status:` and writes the record |
| A multi-step pipeline of the six that already record | `ProvenanceRecorder.shared` with `beginRun`, `recordStep`, `completeRun` and `save`. The callers are `ClassificationPipeline`, `EsVirituPipeline`, `TaxonomyExtractionPipeline`, `TaxTriagePipeline`, `NativeBundleBuilder` and `FastqDeaconRiboSubcommand` |

The recorder's API is frozen and 2.7 rebuilds it on the builder, so each new caller is one more site to move. `NativeToolRunner` and the other runners never call it, so a tool run through one leaves no step unless its caller records it. Take the file name from `ProvenanceRecorder.provenanceFilename` or `ProvenanceRecorder.fileSidecarURL(for:)` and add no new sidecar name, because the finder and every reader would have to learn it. The recorder's lookup sits in `ProvenanceRecorder+SidecarLookup.swift`, its file records in `ProvenanceRecorder+FileRecords.swift`, `ProvenanceError` in `ProvenanceError.swift` and `droppingMissingRunLevelFiles` in `ProvenanceEnvelope+RunLevelFiles.swift`. A writer's file-system changes follow `docs/contracts/EXTERNAL-VOLUMES.md`.

A test that builds a writer passes `signingProvider: nil`, because a default writer signs whenever `LUNGFISH_PROVENANCE_SIGNING_KEY` or `LUNGFISH_PROVENANCE_SIGNING_KEY_FILE` is set. A writer's test asserts that the file passes `ProvenanceEnvelopeReader.decodeCanonical`, which rejects a bare run, that the file holds no `legacyWorkflowRun` key, and that `ProvenanceCompleteness.issues(in:)` is empty for the success record or the test lists each known gap. Nothing refuses a write at run time, because a refusal at the last step would fail a finished analysis.

## Reading a record

`docs/formats/provenance.md` gives the record shapes, the version rule and what version 2 removes. A reader follows these rules.

| Rule | Why |
|---|---|
| Read a record file with `ProvenanceEnvelopeReader.load(fromSidecar:)` or `read(fromSidecar:)`, and never decode a `WorkflowRun` from one | A version 2 record has no `WorkflowRun` keys, and the tolerant reader takes every released shape. `ops stats` dropped every version 2 record and every genotype record whose steps hold no start date until it moved |
| Use the strict reader, `loadCanonical` or `decodeCanonical`, only to check what a writer just wrote | Released records in the bare run and primitive shapes must keep reading |
| Keep every alias, read any `schemaVersion` and ignore unknown keys | Old records keep their meaning and newer records stay readable |
| Leave a fact the record never held empty and show it as Not recorded | The readers once filled the app version, executable, process ID, OS, architecture, dependency set and workflow version from the reading Mac |
| Take the shape, a derived status and an invented date from `read(fromSidecar:)`, or from `ProvenanceRecorder.findProvenanceReading(for:)` for the record the finder picks | Only a bare run or a primitive record is the Older record format, never a typed record such as `mapping-provenance.json`, and an invented date reads Not recorded |

`ops stats` counts files named exactly `.lungfish-provenance.json`, and counts a run as completed only when its record decodes as an envelope or a bare run and states that it completed. A recorded file value, such as `<workspace>/reads.fastq`, reads back as written, never with the reading folder or the reading user's home in front of it. The finder falls back to any root `*-provenance.json` only for a folder that never had a record. When the folder's own record is empty, unreadable, or missing beside its own `.lungfish-swap-` tombstone, `.lungfish-stage-` copy or `.provenance-displaced-` aside, another operation's record never stands in, and the read runs no recovery.

## Reading never writes

Finding, loading, listing, displaying and exporting a record change no existing file in a project and create nothing but the export the user saves. The Inspector audit and the File > Export > Provenance items once called backfills that wrote a record dated at the read with the reading app's version, and that rewrote a real TaxTriage record with an invented step and its signatures cleared. Those calls are gone. A result with no batch record shows Missing provenance, and the Raw JSON pane shows the sidecar's own bytes. The backfills stay inside the operations that made a result until 2.8 deletes them. The GUI walk of 2026-10-10 found three read-time writes left, all older than 2.4. None changed a result. One changed records, because on a bundle annotated with `lungfish genotype apply-annotations` the genotype seed rewrote `annotations.json`, replaced that command's record of it and left three more of its records with a stale SHA-256. ## Exporting a record as a script

A shell, Python, Nextflow or Snakemake export promises that someone else can rebuild the environments a run used, so these four formats pass a pin gate first (plan decision S7). A methods or JSON export never does. `ProvenanceExporter.pinGate(for:shape:format:sourceSidecarURL:sourceRootURL:)` assesses the plan `exportBundle` would render, so it sees the expanded chain of upstream records, the step synthesized for a record with no steps and the spec each environment variant writes. The CLI asks it before `exportBundle`, and both GUI paths ask it before the save panel through `ProvenanceExportPinGatePresenter`. `exportBundle` never refuses anything.

| A script step is unpinned when | Why |
|---|---|
| Its recorded version has no lock entry of that version | The gate compares the recorded version with the lock entry of that version and never with the current pin of another version, so no written environment installs a version that did not run |
| It recorded no version, `unknown`, an error line or LGE's own version | Nothing can be pinned, and a version recorded as an empty string reads as not recorded |
| The lock builds the tool from source or in a Python runtime | A conda spec cannot express either, which makes Bracken unpinnable (S20) |
| The lock does not hold its environment | No lock entry pins it |
| A tool piped after the first ran in another environment | The script writes the environment of the first tool of a pipe only, and writing each piped tool's environment is 2.7 work |

A step's environment is the one its version text names, a `micromamba run -n` prefix, an executable under `envs/<name>/bin/`, or the `condaEnvironment` of its runtime identity when that identity's executable is the environment's copy of the step's own program. The last is how `ClassificationPipeline` records kraken2 and Bracken, while a step that only inherits the record's identity, such as gzip, gains no environment from it.

A record that decoded as the Older record format, a bare run or a primitive record, is never exported as a script, with or without the override (V6). Neither is a record whose chain reads one, because the script would replay its steps. The gate reads the sidecar of each record the chain merges, counts `mapping-provenance.json` and an adopted track's `<bam stem>.mapping-provenance.json` as typed, and names the file it refuses. A typed record such as `mapping-provenance.json` is not the Older record format, and the finder's `findProvenanceReading(for:)` gives each entry point the shape from the same walk that found the record. A script with an unpinned step is written only with `--allow-unpinned` in the CLI or **Export Anyway…** in the app's sheet, where **Cancel** is the default. The override names each unpinned step in the script header and comments each such step, the export record keeps `allowUnpinned` among its explicit options and the steps under `unpinnedSteps` among its resolved options, and its recorded command carries `--allow-unpinned`.

A tool step that recorded no output file and holds `stdoutReadInProcess` stays in the methods text and the Provenance tab, and a script names it in a comment and does not run it. A step of an older record never holds the mark, so its script does not change.

## The frozen legacy corpus

Old records are evidence and must keep reading as they do. Three sets freeze them. A writer change keeps all three green unless the change declares a difference and a reviewer accepts it.

| Set | What it freezes |
|---|---|
| `Tests/Fixtures/provenance-compat/`, with `ProvenanceCompatCorpus` and `ProvenanceCompatFacts` in `Tests/Support/LungfishTestSupport` and the `ProvenanceCompat*` suites | Real legacy bytes such as the 0.4.0-alpha.11 bare run and an early MSA sidecar, and captures of the shapes writers produced before 2.4, each with expected facts |
| `Tests/Fixtures/demo-projects/lge-demo-mhc-genotyping-2026.9.58.zip`, with `DemoProjectProvenanceLoadTests` and `DemoProjectProvenanceSweepTests` | The released MHC demo. Reading, finding, lineage and export leave every byte of the installed project unchanged. The sweep covers the other demo archives in the folder `LUNGFISH_DEMO_ARCHIVE_DIR` names |
| `Tests/Fixtures/provenance-display/`, with `ProvenanceLegacyDisplayTests` and `ClassificationCommandParityTests` | What the Inspector's Provenance tab shows for each legacy shape, and that Copy Classification Command prints the same text with and without a nested run |

Freeze, then change. A change to a writer starts with a commit of the facts its current output holds, captured on unchanged code with `ProvenanceCompatFacts` and green before anything moves. The change follows in its own commit, and the new output's facts must equal the captured ones except the fields the commit declares, such as the record shape. Facts leave out the host values a record holds, such as the executable path, process ID, architecture, dependency set, app version, OS version and workflow version, and a date taken from the file's modification time. Since 2.6 a reader leaves a fact the record lacks empty instead of filling it from the reading Mac. A test copies a case to a temporary folder before anything reads it, because some readers write. A difference in a frozen or expected file is a reviewed commit that says which behavior moved. Bytes that a golden holds change in a commit of their own, and `python3 scripts/golden/golden.py compare` must confirm it.

## The ratchets

`scripts/ratchets/provenance-writers.sh` and `scripts/ratchets/path-helpers.sh` run in the pre-push hook. Run `bash scripts/install-git-hooks.sh` again to add them to a hook installed before 2.4. Each count may only fall, counts occurrences and not files, and ignores text after `//`. Each script keeps its baseline in a `.baseline` file beside it.

| Count | What it counts | Do this instead |
|---|---|---|

| `bare_workflow_run_writes` | `.writeSidecar(`, which writes a bare `WorkflowRun` | Write `run.canonicalEnvelope()` through `ProvenanceWriter.write(_:toSidecar:)`. The count is 0 once 2.4 lands |

The scan reads one line at a time, so review catches the rest. `write_provenance_functions` reads a definition from its `func` to the brace that closes it. A renamed writer function escapes `write_provenance_functions`, and a definition that names the writer counts 0 even when it writes another file itself. `envelope_encodes_outside_writer` reads the names a file binds as an envelope. An envelope reached through a name the file never binds or types that way, such as a generic value, a closure argument or a binding whose `=` sits on a later line than its name, escapes it. An inline `dropFirst(base.count + 1)` escapes the path counts. Run a script with `--print` to list every counted site. A count under its baseline passes with a hint. Lower the baseline with `--update` once the sites are gone and commit the `.baseline` file. In a session of parallel lanes only the manager does this, after the wave. Raising a count needs a reviewed reason, and `--update` is never the way to make a push pass. A commit that moves counted sites changes nothing else and never sits inside a pure move.

## The ToolProcess observer hook

Sub-phase 2.7 builds the hook, with the recorder rebuilt on `ProvenanceRunBuilder` and the run executor as its first consumers. Nothing records through it before then, because a hook with no consumer cannot be tested. It follows these rules.

| Rule | Detail |
|---|---|
| A task-local read once per launch | The observer is `ToolProcessObservation.observer`, a `@TaskLocal` in `Sources/LungfishCore/Process/ToolProcessObservation.swift`, as `NativeProcessObservation.onEvent` is and as `docs/contracts/CONCURRENCY-PLAYBOOK.md` asks, and not a static variable. It is read once where a run is built, in the caller's context beside the priority read of `ToolProcessExecution.init`, whether a single run, a handle or a pipeline, and never on the run's queue. The observer itself is never a field of `ToolProcessSpec`. |
| Opt-in for each run | A caller sets the observer for a scope together with a step context that holds the tool name, the version, and the input and output files with their roles. A launch outside that scope records nothing, so a version probe, `micromamba --version` or `docker info` never becomes a step. The observation fills the exit status, times, termination and stderr of the declared step and never replaces its argv. |
| Delivered once per run | One `ToolProcessRunObservation` for each run, whether a single run, a handle or a pipeline, with one entry for each declared stage, because the pipeline verdict on a stage reads every stage. It is delivered on the run's queue in the `.complete` branch of `evaluateCompletion()` in `Sources/LungfishCore/Process/ToolProcessExecution+Lifecycle.swift`, just before `onComplete` runs, a point that every single run, handle and pipeline passes even when no caller waits for the result. It lands before `ToolProcess.run`, `ToolProcess.runPipeline`, `ToolProcess.runBlocking`, `ToolProcessRun.result()` or `waitBlocking()` returns. A launch failure and a cancellation deliver one too, a cancellation before the launch included, whose entries read never launched. An invalid spec builds no run and delivers nothing. The entries are built from the same per-stage values `outcome()` returns, through one shared helper, so the record and the result never disagree. |
| Never from these places | Line delivery or a drain callback, `cancel()` or a stop request, or while a run holds its lock. Output stops being read during a handler, `cancel()` must return at once and a call under the lock blocks every waiter. The hook never turns on line framing. |
| Nothing slow inside | No hashing, no version probe, no file access and no waiting. The observer appends to a buffer and returns, and the recorder does the rest later. |
| What it carries | Per stage the label, executed argv, working directory, wall-clock start, monotonic wall time, how the stage ended (exited with a code, signaled, a status lost to another reaper, a launch failure or never launched), the stop reason (`cancelled`, `timedOut` or `pipelineStageFailed`), whether the output was complete (not recorded for a stage that streams stdout, whose reader is judged after the run), whether the stage failed on its own by the rule of `failedStageIndices`, the stderr bounded to its first 8,192 and last 32,768 bytes, the stage index and count, the environment change and an identity hint from the adapter such as the conda environment or the `NativeTool` name. It holds no stdout bytes. It also carries the peak memory that `wait4` reports, which no record writes until a golden normalizer rule for it is approved. |
| Environment | `ToolProcessSpec.environment` stays the whole child environment, and a record never holds the inherited environment. It records the name of every variable the caller changed, and a value only for a variable on an allowlist of those LGE's own adapters set, `ToolProcessEnvironmentChange.valueRecordedNames` in `Sources/LungfishCore/Process/ToolProcessEnvironmentChange.swift`. `HOME`, `TMPDIR`, `MAFFT_TMPDIR` and `XDG_CACHE_HOME` keep their names only, because their values name the account's home or scratch folder and say nothing about the result. A name pattern fails open, because a secret can sit in a value such as a proxy address or a `DATABASE_URL`. Values pass through `PortablePath` sanitizing first. The change travels with the spec as a defaulted `ToolProcessEnvironmentChange` with `base` (inherited or hermetic), `set`, `unset`, `pathPrefix` and `pathReplaced`, and the adapters fill it where they call `inheritedEnvironment(overriding:)` today. For PATH only the entries the adapter put before the base PATH are recorded, never the user's PATH, which an allowlisted PATH value would otherwise leak. When an adapter on an inherited base sets a PATH that does not end with the inherited PATH, `pathPrefix` holds the whole PATH the child got and `pathReplaced` is true, so a reader never takes a replaced PATH for a prefix. A hermetic base keeps it false (Phase 2.10 S8). |
