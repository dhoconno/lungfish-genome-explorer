## Decisions

- Storage policy (Task 1): **reference durable inputs in place; copy only transient inputs.** An execution input is durable when it exists, is a regular file, and is located inside (or equal to) one of the `originalInputFiles`, or is inside the project (`*.lungfish`) tree. Only materialized temp files (virtual subset/trim/demux bundles) are copied. The replay command then points at the in-place payload. Existing copies in old results are not deleted by the app; the user can remove them manually (replay commands for old runs reference the copies).
- Bracken report (Task 2b): pass `-w <outputDirectory>/classification.bracken.kreport` explicitly (both dialects), model it as `ClassificationConfig.brackenReportURL`, declare it as a bracken step output and in result/known outputs; keep reading legacy `classification_bracken_species.kreport` when the explicit path is absent.
- Stale declarations (Task 2a): kraken2 step output and gzip step input stay as the raw file *at the time of the step* (historically true), but the run-level `files`/`outputs` and the result sidecar must only list files that exist at the end of the run. Implement by dropping records for paths that no longer exist when finalizing the run (or by recording the compaction as replacing the raw output). Tests assert no declared path is missing on disk at the end of a successful run.
- Degraded status (Task 2c): a sample whose classification completed but whose Bracken profile degraded is `completed` with the degradation recorded in options/stderr, not `failed`. Batch `exitStatus` is 0 when `failedCount == 0`; degradation is surfaced via `degradedCount` and stderr. This matches OperationCenter's completed-with-warning.
- BLAST (Task 4): `onBlastVerification` gains the owning sample ID (`findSampleAncestor(of:) ?? currentBatchSampleId`); the handler resolves the source FASTQ through the same logic as `ClassifierReadResolver.resolveKraken2SourceFASTQs` (promoted to a public helper).
- Extraction (Task 5): bundles go to `<project>/Extractions/` (user decision 2026-08-22: extractions are kept apart from sequence imports); FASTA-format bundles write a `FASTQDerivedBundleManifest` with `.fullFASTA` payload so they resolve; on any failure after directory creation the partial bundle is removed.
- Viewport (Tasks 3, 6): restore the `NSSearchField` ("Filter taxa…") in `TaxonomyTableView` header driving `applyFilter()` (match + descendants + ancestors; existing behavior); add an optional "Bracken" column (reads) shown only when any node has `brackenReads`.
- Debug build rule (Task 7): record in the shared `releasing-lungfish` skill that a test build for the user is `bash scripts/build-app.sh --debug` (bundle id `com.lungfish.browser.debug`, display name "Lungfish Debug", output `build/Debug/Lungfish.app`), unsigned and un-notarized, never uploaded, built from the feature branch after the unit tier passes.

## Follow-up: "Failed to install package: " on the first debug-build rerun (2026-08-22)

Root cause chain: `scripts/build-app.sh` runs `sanitize-bundled-tools.sh` (in-place byte rewrite of embedded build paths in every Mach-O under `Tools/`) but the debug path never re-signed those binaries, so the bundled micromamba had an invalid signature and macOS SIGKILLed it. On launch `CondaManager.ensureMicromamba` could not read the bundled version, fell back to the lock string `2.9.0-0`, compared it to the installed `2.9.0`, and replaced the user's working `~/.lungfish/conda/bin/micromamba` with the dead copy. Every micromamba call then failed with exit 137 and no output, surfacing as the bare message.

Fixes: (1) `build-app.sh` ad-hoc re-signs every Mach-O under `Tools/` after sanitizing, verifies each, and fails the build unless the bundled micromamba runs; (2) `ensureMicromamba` probes the bundled binary first, never replaces a working install with one that cannot run, compares normalized versions (`2.9.0` == `2.9.0-0`), and restores the previous binary if the fresh copy fails to run (`CondaError.micromambaUnusable`); (3) `runMicromamba` failures report the command, exit status or signal, output, and a code-signature hint. The user's conda root was repaired by restoring the valid 2.9.0 binary from the installed `/Applications/Lungfish.app`.

User request: every BAM viewer opens at full contig width, and differences relative to the reference are visible whenever individual reads are drawn (Geneious shows them at ~1,500 bp visible; LGE only showed them within ~500 bp).

Applies to all BAM viewers since they share the renderer.

## Follow-up: machine-wide OOM during Kraken2 batch + FASTQ import (2026-08-22 19:02)

Evidence (`/Library/Logs/DiagnosticReports/JetsamEvent-2026-08-22-18594{8}.ips`, `-190213.ips`, 48 GB machine): top residents were fseventsd 28.5 GB, java (BBTools, Lungfish's child) 18.1 → 20.9 GB, kraken2 `classify` 12.6 → 16.4 GB, CrashPlan 6 GB; the Lungfish process itself was 0.5 GB (lifetime max 5 GB). The Force Quit "42 GB" figure was footprint, not resident memory. The app was "not responding" because FSEvents deliveries were handled on the main thread while two tools flooded the exFAT (FSKit) project volume with file events.

Root causes and fixes:
- BBTools heap was sized at 60–80 % of physical RAM at seven call sites (28 GB on this machine) with no regard for a concurrently resident kraken2. New `ManagedJavaHeapPolicy` (LungfishCore): min(35 % of physical, available − 8 GB reserve, 31 GB compressed-oops ceiling), floor 4 GB (1 GB for small derivative steps). All seven sites use it; `ClumpingTool.clumpifyHeapBytes` too.
- `FileSystemWatcher` used per-file FSEvents with a 3 s latency on every volume and ran its callback on the main thread. Now: volume-aware `StreamPolicy` (APFS/HFS keep per-file events; exFAT/FAT/SMB/unknown get directory-level events, 10 s latency), the stream is scheduled on a private serial queue with pure `classify(...)` off-main and exactly one main hop, and deliveries above a burst threshold (2,000 native / 500 foreign paths) collapse into one coalesced full reload.
- Not changed: kraken2's own memory (Standard-16 needs ~16 GB; `--memory-mapping` is the existing user option).

## Follow-up: high-depth read rendering (options 1-3)

The BAM read track re-did its entire layout and mismatch analysis on every draw, so panning, hovering, or selecting a read on a high-depth sample re-sorted and re-packed the full read set and re-parsed every read's MD tag. Three contained changes fix that without altering a single pixel of output. (1) **Pack once**: packing now routes through `SequenceViewerView.packedReadLayout(key:pack:)`, a single choke point shared by the bundle-backed and detached-evidence paths, keyed by `ReadPackCacheKey` (read-set generation, chromosome, quantized scale, sort mode/position, max rows, vertical compress, and — only when a row cap is active — the prioritized region and pack window). `packReads` is genuinely scale-dependent, since it drops reads narrower than `minReadPixels` and separates rows by a fixed 2px gap, so the key carries the quantized bp-per-pixel rather than pretending packing is purely genomic; conversely, with unlimited rows the prioritized region cannot change the result, so it is excluded and panning reuses the layout. (2) **Cull by visible rows and x-range**: `drawPackedReads`/`drawBaseReads` iterate through `forEachVisiblePackedRead`, which derives the intersecting row range arithmetically from the content-space clip rect (the bundle path passes the clip offset by `readScrollOffset`, so rows scrolled above the viewport are skipped, not just those below) and then binary-searches each row's position-sorted bucket for the first read that can reach the window, stopping at the first read past it. Both draw functions keep their original flat-array signature, so callers that pass only `packedReads` fall back to the previous linear walk unchanged. (3) **Precompute mismatches**: `ReadMismatchCache` parses each read's MD tag once on the fetch's background thread in `fetchDetachedReads`/`fetchReadsAsync`, hands the result to the main actor via `pendingReadMismatchCache`, and is rebuilt automatically by the `cachedAlignedReads` `didSet`; only the MD/CIGAR string parse is cached, because with a reference loaded the comparison is already a cheap byte loop.

Test seams: `packInvocationCount` counts actual packs (a repeat draw must not increment it), `testCachedReadMismatchCache` and `testCachedPackedReadLayout` expose the caches, and `invalidatePackedReadLayoutCache()` forces a repack. `ReadTrackCulling.visibleRowRange`/`visibleReadRange` and `PackedReadLayout` are pure and unit-tested directly, including a property test asserting culling selects exactly the reads a full scan would. Coverage lives in `Tests/LungfishAppTests/ReadLayoutCacheTests.swift` (21 tests), which also carries a benchmark skipped unless `LUNGFISH_READ_RENDER_BENCH=1`: at 200k reads it packs once in ~8.9 s and then serves 60 further frames in ~0.04 ms total, versus repeating that pack every frame before.

## Follow-up: debug app SIGABRT at 19:27 and the in-app 20 GB growth

Crash report `~/Library/Logs/DiagnosticReports/Lungfish-2026-08-22-192759.ips`: main thread aborted inside CoreText (`TAttributes::ApplyFont` → `-[__NSPlaceholderDictionary initWithObjects:forKeys:count:]: attempt to insert nil object`) from `EnhancedCoordinateRulerView.drawInfoBar`. The fonts and colors there are non-optional system values; CoreText failed to build a CTFont because the process was out of memory (21 GB malloc, footprint 4.5 → 16.5 GB in 140 s per the 19:22 cpu_resource diag).

Where the memory went: the background threads were `GzipInputStream.lines()` and `FASTQReader.records(from:)` — producer tasks yielding into unbounded `AsyncThrowingStream` buffers while a slower consumer (`FASTQStatisticsService` read-length histogram for the freshly imported pair) iterated. gzip decompresses far faster than per-record parsing, so the whole decompressed FASTQ accumulated in the buffer. This is also the most likely source of the earlier "42 GB" footprint reading.

Fix: both streams are now pull-based (`AsyncThrowingStream(unfolding:)`): `GzipLineSource` decompresses one chunk per demand and owns the gzip subprocess; `FASTQReader.RecordSource` parses one record per demand with identical grammar/error behaviour; the plain-text branch wraps Foundation's `AsyncLineSequence` iterator. Tests: `GzipLineSourceBackpressureTests` (one chunk per demand, early abandonment, gzip/plain parity, truncated-record error) plus the existing `FASTQReaderTests`.
