# Olivar and varVAMP in the optional PCR Primer Design pack

Status: user-approved design, implemented in `codex/primer-pack-olivar-varvamp`; final review and rebuilt-app acceptance are complete. Native product installation, offline import, relocation and MHC execution have passed their recorded gates. See [MHC validation](../../reports/2026-09-24-primer-pack-mhc-validation.md) for current results and limitations, and [initial smoke](../../reports/2026-09-24-primer-pack-installation-smoke.md) for the historical feasibility gate.

## Outcome and scope

Extend the existing optional `pcr-primer-design` pack so installing primer tools installs Primer3, PrimalScheme3-LGE, Olivar, and varVAMP. Preserve existing managed installations and portable/offline pack behavior. The new tools use the existing primer-analysis document, PrimalScheme-style viewport, selection, binding inspection, and Inspector. New results must reopen without installed design tools.

Use a new worktree at `.worktrees/primer-pack-olivar-varvamp`, branch `codex/primer-pack-olivar-varvamp`, based on `b69e43dbd`. Do not modify the active documentation/fix worktrees or the original MHC project. This work does not publish a release or merge to main.

Support Olivar tiled design and varVAMP single-amplicon, tiled-amplicon, and qPCR primer/probe design. The probe workflow can be presented for qPCR/dPCR primer-and-probe design; varVAMP has no distinct dPCR optimizer or experimental validation stage. “Single” means a primer pair for an amplicon, not a lone oligonucleotide. Preserve probes as probes throughout storage, rendering, ordering, and export.

## Selected architecture and alternatives

Use the existing pack with one managed environment per tool, native `osx-arm64` packages verified by the installation smoke, pinned versions, installation receipts, and exact runtime probes. This follows the existing Primer3/PrimalScheme separation and allows Olivar's NumPy/Plotly constraints without imposing them on other engines. Pack installation includes all four environments; selected-tool preparation retains its existing on-demand behavior. An older two-tool installation is incomplete until the two additional tools are installed, but its existing tools remain usable.

Avoid a single shared Python environment: it couples independent dependency constraints and complicates upgrades. Avoid separate packs and separate viewers: they contradict the requested install experience and duplicate document/selection behavior.

Keep engine adapters separate from shared normalized result models and UI. Reuse `PrimerAnalysisBundleWriter`, `PrimerDesignManagedRuntime`, `NativeToolRunner`, `PluginPackStatusService`, and `CondaOfflinePackService`. New engines must retain their own identities and must not impersonate PrimalScheme or satisfy its fork-specific capability contracts.

## User interface

Add Olivar and varVAMP to the existing Primer Design entry point and engine picker. Reuse the existing project input summary and explicit selection model. The primary controls are input selection, output name, mode where applicable, target/minimum/maximum amplicon size, and valid output grouping. Keep Advanced Options collapsed initially and retain settings when toggled.

Use one scheme per input as the common comparison mode. Olivar may expose its native multi-target design as a combined scheme with original input identities retained. varVAMP accepts one aligned FASTA per invocation: multiple selected inputs are an independent batch, never a falsely labeled co-optimized panel. Disable unsupported grouping rather than silently concatenating alignments or relabeling outputs.

Keep the Results viewport, amplicon overview, primer selection, binding inspection, zoom/pan, display filters, and Inspector interaction shared with PrimalScheme. Tool names, native statistics, generated reference identity and available files differ. Keep current PrimalScheme bundles and UI behavior compatible.

Advanced controls use typed, validated fields rather than an arbitrary shell-arguments box. Olivar controls cover native risk weights, degeneracy, GC/primer constraints, temperature/salinity, dimer constraint, random seed, search effort, CPU count, and optional non-target BLAST database. varVAMP controls cover consensus threshold, allowed ambiguous bases, overlap for tiled mode, result limits, primer length/Tm/GC and interaction settings, and qPCR probe length/Tm/GC, probe ambiguity and secondary-structure controls. Expose only fields the pinned engine and adapter actually support. All effective defaults are saved, including generated varVAMP configuration.

## Amplicon-size contract

The PrimalScheme, Olivar, and varVAMP scheme interfaces present minimum, target, and maximum together and validate `minimum <= target <= maximum`. Like the existing PrimalScheme UI, target is nominal: it initializes bounds until users customize them. Do not claim closest-to-target optimization where the engine does not provide it. Olivar and varVAMP tiled workflows have native two-pool behavior; display their fixed pool count instead of showing an ineffective pool-count control. SINGLE and qPCR assays are unpooled unless native output explicitly assigns a pool. Every displayed control must have an explicit recorded role; once both bounds are customized, explain if changing nominal target does not alter selection.

Define the displayed size as the full span including primer sites on the saved engine reference. Native references can differ between engines, so do not imply that equal numerical bounds guarantee the same per-allele product sizes.

Validate engine limits before launch: Olivar requires a minimum of at least 120 bp; reject smaller requests without clamping. Validate mode-specific qPCR configuration ranges and primer/probe feasibility constraints, and retain the existing PrimalScheme limits. A valid range is not a promise that the engine can find primers.

varVAMP single/tiled `--opt-length` is a hard lower bound as well as a native penalty scale. Map the requested minimum to that flag, maximum to `--max-length`, and record the mapping and nominal target separately. For qPCR, generate a run-owned `VARVAMP_CONFIG` setting `QAMPLICON_LENGTH`; it must be inherited by workers. Validate the final output spans in all modes, including any changes made by dimer-resolution routines.

Olivar's native bounds constrain primer-design regions but do not enforce every final primer-pair span. A versioned, explicitly identified LGE adapter must constrain feasible pairs before SADDLE selection and validate final spans before publication. Never silently delete out-of-range amplicons after tiling and present the remainder as the requested design. If the requested range leaves an amplicon with no valid pair, return an informative design failure (or a bounded, fully recorded retry) rather than publish an invalid scheme. Keep upstream code/version attribution distinct from adapter identity and preserve the exact adapter used for replay.

Provision both adapters as versioned app-owned Python resources under the workflow module, not by mutating installed upstream packages. Copy the exact adapter/configuration bytes into the private run and retain them in the result bundle. Invoke the selected environment’s Python explicitly, with that environment’s executable directory first in PATH. Check installed distribution versions and relevant source hashes before calling or intercepting private upstream APIs. Record adapter version/SHA-256, upstream version/source identity and full executed argv; include attribution and license notices for any adapted upstream code. Portable app packaging must include these resources, and offline pack tests must verify environment relocation plus execution through the portable app’s adapter. The existing Bracken-only source-overlay type is not an implicit extension point.

## Variant-frequency semantics

PrimalScheme already has `minimumBaseFrequency` in its pipeline and CLI, but the current GUI hardcodes zero. Expose that value without changing historical defaults.

Olivar's MSA `--min-var` is an aggregate variant-frequency cutoff, not an identical per-base policy. Label it as the minimum variant frequency considered by Olivar, preserve the native definition, and record its effect and denominator. Degenerate-mode consensus uses a separate native policy and must not be represented as controlled by this field if it is not.

varVAMP's threshold selects a cumulative fraction of bases when forming an ambiguous consensus and participates in gap processing. Do not translate it to `1 - minimumBaseFrequency`. Expose the native consensus threshold with clear tool-specific help; do not add an ineffective per-variant frequency field. Supporting a genuinely equivalent per-variant policy later would require a separate algorithm change and validation, beyond this integration.

## Results, coordinates, and preservation

Introduce a versioned engine-neutral normalized scheme result payload. It contains engine/adapter identity, mode, input/result/target identities, generated reference and input artifacts, explicit coordinate conventions, full amplicon spans, primer/probe sequences in 5-prime-to-3-prime orientation, strand, optional native pool, explicit amplicon membership, native names and available metrics. Require explicit `oligoRole` (forward, reverse, probe), stable `assayID`/`ampliconID`, source result identity, and exact member IDs. Assays carry selected-versus-alternative status and rank when provided; qPCR assay validation requires LEFT, PROBE and RIGHT with valid orientation and interval membership. Native pool identity is nullable and string-capable, with display groups separate from scientific pool membership. Alternative qPCR candidates remain distinct assays, not a combined tiled scheme. Unknown metrics remain unknown; IUPAC sequences do not acquire fabricated scalar GC percentages.

Reuse the PrimalScheme presentation components through this model. Do not fabricate PrimalScheme filenames, native pool numbers or name-based relationships to trick its loader. Existing legacy loaders stay available for existing bundles. Add a versioned generic order-row model containing oligo role, sequence, source engine, assay/amplicon membership, candidate status, optional native pool and stable result IDs. Offer explicit export of selected assays or all reported assays; all-reported qPCR alternatives stay labeled as alternatives, with probes retained. Unpooled SINGLE/qPCR rows display “Unpooled,” never an invented pool 1. Preserve native ordering sheets separately from Lungfish-derived exports and record provenance for each derived export. Any small renderer extraction must preserve current selection identities and display settings.

Olivar CSV coordinates are 1-based closed and BED coordinates are 0-based half-open; normalize exactly once. varVAMP outputs refer to a cleaned consensus, including collapsed gap regions, not the first original MSA row. Capture the preprocessing column map in the versioned adapter, retain generated consensus and cleaned alignment, and verify their relationship before publication. Maps must represent collapsed or synthetic bases explicitly. Unmappable/discontinuous binding regions are reported as such instead of inventing contiguous original coordinates. The shared viewer must not apply its current first-row projection to these references. Define a normalized binding-projection payload with generated-reference coordinates, source alignment identity, original column intervals and per-primer mappability. Exact unmasked intervals support cross-row inspection. A primer crossing a collapsed/synthetic block has an explicit unavailable/ambiguous projection state; preserve its generated-reference display but do not fabricate row mismatch counts. Olivar consensus-to-MSA projection must pass the same contract. Both engines must retain at least their generated-reference viewport even if original-MSA inspection is unavailable for a particular primer.

Store original input snapshots, stable row maps, generated inputs and configuration, all native outputs, normalized outputs, stdout/stderr, runtime receipts and complete provenance in `.lungfishprimeranalysis`. Olivar pickle files are retained as opaque native artifacts; only files created within the private current run may be consumed by the adapter. Reopening a result must never unpickle files or require the engine.

Every scientific transform records exact argv/replay command, input/output paths with checksums and sizes, visible settings and resolved defaults, tool and adapter versions, runtime identity, exit status, wall time and useful stderr. Bundle publication remains exclusive and atomic; final provenance refers to final durable payloads. A zero-primer result is not called a successful scheme: distinguish a valid empty result with a native explanation from execution, contract, parsing or provenance failures. Cancellation terminates child processes and cannot publish a partial analysis as complete.
