# Full-Length ONT MHC Annotated Artifacts And Curation Design

Date: 2026-07-09

Status: Approved for implementation planning

## Summary

Extend the full-length ONT MHC genotyping workflow so shared novel and reference-extension clusters become reviewable scientific records inside the existing `.lungfishgenotype` analysis.

When the selected MHC reference bundle contains annotated GenBank records, the workflow will:

- identify candidate clusters observed in at least two independent analysis samples;
- distinguish known full-length genomic genotypes, cDNA-to-genomic extensions, partial-genomic extensions, and novel alleles;
- create a structured, revisioned MHC curation model;
- render synchronized FASTA, GenBank, and EMBL artifacts;
- show known and candidate alleles together in a Unified genotype matrix;
- let users review and edit curated fields from the right Inspector;
- update the Unified viewport and current workbook from draft and published curation state;
- publish immutable annotation revisions; and
- create complete derived MHC reference bundles from accepted records.

The GenBank and EMBL files are internal scientific review artifacts. They use valid INSDC feature keys and qualifiers. Lungfish-specific metadata that has no valid INSDC qualifier is stored in `COMMENT` and the structured curation model rather than emitted as a custom qualifier. The records are not represented as submission-ready public-database records.

## Goals

- Make provisional allele naming understandable to a human MHC curator.
- Preserve exact sample and read-support evidence for every candidate.
- Use the exact annotated reference set selected for genotyping.
- Retain the longest supported CDS, including a short exon 8 where required.
- Distinguish database annotation assertions from Lungfish-computed CDS assessments.
- Keep known genotype calls immutable while providing a live Unified projection.
- Make manual edits auditable, reversible, and reproducible.
- Keep GenBank, EMBL, FASTA, the Unified viewport, and `current.xlsx` synchronized.
- Avoid requiring additional primer, adapter, or trimming files from users.
- Preserve complete provenance for automated analysis, publication, and reference promotion.

## Non-Goals

- Direct submission to GenBank, ENA, or IPD-MHC.
- A general-purpose GenBank feature editor for arbitrary organisms or feature types.
- Automatic mutation of the reference bundle used by a completed analysis.
- Treating provisional `_NOV` or `_EXT` names as official IPD-MHC assignments.
- Replacing the existing genotype matrix, haplotype view, or matrix-annotation workflow.

## Terminology

**Known genotype**
: A cluster that completely and exactly matches an eligible full-length genomic reference after technical-boundary resolution.

**Candidate**
: A distinct cluster sequence supported by at least two independent analysis sample IDs and classified as novel, a cDNA-to-genomic extension, or a partial-genomic extension.

**Naming reference**
: The closest reference allele used as the human-curation anchor for assigning a provisional allele name and describing differences.

**Annotation template**
: A compatible full-length genomic reference used to transfer exon, intron, UTR, and CDS structure. It may differ from the naming reference.

**Automated proposal**
: The immutable initial boundary, feature, CDS, reference, and name proposal generated by the workflow.

**Draft**
: Autosaved human overrides layered over the automated proposal. Draft changes update the Unified viewport immediately but do not rewrite published flat files.

**Published revision**
: An immutable validated snapshot of the structured model and synchronized derived artifacts.

## Architecture

The structured MHC curation model inside the `.lungfishgenotype` bundle is the source of truth. GenBank, EMBL, FASTA, the Unified matrix, and workbook rows are deterministic projections of that model.

Flat files are never parsed as the editable database. Human edits update explicit structured fields. Publication regenerates all derived files atomically.

The design has five major components:

1. Annotated MHC reference bundles and hidden mapping caches.
2. Cohort candidate analysis and provisional naming.
3. Native INSDC record modeling and GenBank/EMBL rendering.
4. Unified genotype projection and Inspector curation.
5. Revision publication and derived-reference promotion.

## Annotated MHC Reference Bundles

### Canonical Payload

An annotated GenBank file is the canonical reference payload for new MHC reference bundles. It supplies both nucleotide sequences and feature annotations.

Users do not supply a second FASTA copy. During bundle creation, Lungfish deterministically materializes an internal mapping FASTA from the GenBank records. This cache is stored in the bundle or project filesystem but is omitted from normal user-facing artifact lists.

Cache provenance must include:

- source GenBank path and checksum;
- source record accessions and sequence checksums;
- exact materialization command identity and version;
- output path, checksum, and size;
- runtime identity;
- resolved options;
- exit status and wall time.

### Reference Record Classes

Bundle validation classifies every record as one of:

- complete genomic: eligible to produce a known genotype;
- cDNA or mRNA: extension naming anchor only;
- partial genomic: extension naming anchor only.

Classification uses molecule type, feature coverage, exon content, CDS partialness, and terminal coverage. It must not rely only on a length threshold.

Differently named cDNA records must have distinct nucleotide sequences. A violation is a reference-bundle validation error, not an ambiguity handled during candidate naming.

### Legacy Compatibility

Legacy FASTA-only MHC reference bundles remain readable and usable for genotyping. They produce the existing deduplicated unmatched FASTA but cannot produce the structured annotation model, GenBank, or EMBL artifacts.

The Inspector explains that annotated artifacts are unavailable because the reference has no GenBank annotations. Existing analyses remain readable without migration.

## Candidate Eligibility

The candidate population includes:

- clusters unmatched to complete genomic references;
- genomic clusters that perfectly splice-match a named cDNA reference; and
- genomic clusters that perfectly extend a partial genomic reference.

An exact cDNA or partial-genomic match can never be emitted as a known genotype. It is an extension candidate.

A candidate must be observed in at least two independent analysis sample IDs. Technical replicates from the same biological individual count as independent samples for this rule.

The model stores both analysis sample count and biological-subject count when subject metadata is available, but analysis sample count controls eligibility.

Each cluster observation is oriented and passed through the automatic preliminary boundary resolver before exact sequence grouping. Observations with the same preliminary exported biological sequence are grouped across the cohort before expensive annotation analysis. Raw consensus sequences remain attached as evidence. Later human boundary edits do not silently regroup candidates.

Support retains:

- every sample ID;
- every source cluster ID;
- per-cluster read count;
- per-sample aggregated read count;
- occurrence count;
- independent sample count; and
- total cluster reads.

Every eligible candidate remains inspectable, including records with uncertain termini, unresolved feature transfer, or a rejected review status.

## Sequence Boundary Resolution

The raw cluster consensus is retained as hidden evidence. Exported FASTA, GenBank, and EMBL use a separate reviewed export interval.

Boundary resolution uses existing information before introducing any fallback:

1. Reuse orientation and primer trimming already performed by the workflow.
2. Screen terminal sequence against a versioned built-in ONT adapter and barcode catalog.
3. Preserve termini supported by annotated genomic-reference alignment.
4. Use agreement across supporting samples as additional evidence.
5. If a terminus remains ambiguous, clip to the outermost confidently annotated gene boundary and flag the candidate for review.

Minimap2 alignment coordinates alone must not silently define the export interval. This prevents removal of authentic extension sequence.

The model stores:

- raw consensus and checksum;
- orientation;
- proposed export start and end;
- excluded 5' and 3' sequence;
- evidence used for each boundary;
- confidence for each boundary; and
- human boundary overrides.

The same export interval drives all published sequence formats.

## Mapping And Annotation Analysis

### Known Genotyping

Per-sample known-genotype comparison uses only complete genomic reference records. The same automatic technical-boundary resolver used for candidate observations runs before exact-call classification. A known call requires complete comparable coverage and zero nucleotide differences after technical-boundary resolution.

cDNA and partial-genomic records are excluded from the known-genotype reference partition.

### Cohort Candidate Comparison

Repeated per-sample BLAST rescue is replaced with cohort-level minimap2 analysis after sequence deduplication.

- Complete and partial genomic comparisons use an assembly preset and retain CIGAR plus long `cs` strings.
- cDNA references are mapped to genomic candidates with splice-aware minimap2.
- Existing per-sample alignments are scheduling hints only. The annotation phase always materializes durable cohort-level alignments as the final candidate evidence.

The reciprocal cDNA-to-genomic direction is required for extension detection across large introns.

### Naming Reference Ranking

The workflow selects one naming reference in the order a human curator would apply the allele-name hierarchy:

1. Perfect cDNA or partial-genomic extension match, when present.
2. Exon 2 and exon 3 amino-acid similarity.
3. Remaining CDS amino-acid similarity.
4. Full coding nucleotide similarity.
5. Noncoding nucleotide similarity.
6. Comparable coverage, alignment score, and deterministic accession tie-breakers.

The chosen naming reference is the sole anchor for the naming rationale. Dataset-wide comparison does not replace the naming anchor; it seeds used numbers, identifies equivalent candidate states, and prevents collisions.

### Annotation Template Ranking

The annotation template must be a compatible full-length genomic record with the same resolved locus as the naming reference. It is selected for feature completeness, structural compatibility, boundary coverage, and CDS interpretability.

The naming reference and annotation template are stored separately. When they differ, the record and Inspector explain why.

No compatible full-length template is a manual-review condition, not a reason to invent unsupported boundaries.

## Provisional IPD-Style Naming

Names are provisional internal labels and are marked as not official IPD-MHC assignments.

The naming anchor is always the selected closest reference. Differences are classified relative to that anchor, then the next unused value is selected from all reference names and all names allocated in the analysis.

The four fields have the agreed meanings:

1. Field 1: amino-acid lineage defined by exons 2 and 3.
2. Field 2: nonsynonymous coding variation outside exons 2 and 3.
3. Field 3: synonymous coding variation.
4. Field 4: intron or other noncoding variation.

A new field 1 is allocated only when codon-level analysis proves an amino-acid difference in exon 2 or exon 3. Synonymous changes in those exons never create a new lineage.

When a higher-significance field changes, following fields begin at `01`. Dataset-wide candidate comparison prevents two candidates representing the same higher-level sequence state from receiving unnecessarily different higher-level fields. Lower fields distinguish synonymous or noncoding differences between those candidates.

Allocation is holistic across the complete retained cohort:

- seed every used field value from the selected reference bundle;
- include all candidate allocations in the same transaction;
- never assign the same putative name to two distinct candidates;
- preserve stable candidate identity when a draft name changes; and
- block publication on unresolved name conflicts.

### Extension Names

A perfect comparable match to cDNA or partial genomic sequence takes precedence over `_NOV` naming.

The first genomic extension inherits the named reference allele, padded to four fields where necessary, and receives `_EXT` directly on the allele name.

Example:

```text
Mafa-I*01:70 -> Mafa-I*01:70:01:01_EXT
```

If multiple distinct genomic candidates extend the same cDNA or partial reference, they share the inherited coding fields and receive distinct field-4 values.

```text
Mafa-B*011:02:01:01_EXT
Mafa-B*011:02:01:02_EXT
```

### Novel Names

Names that require a new IPD-style field value receive `_NOV` directly on the provisional allele name.

Exact matches to complete genomic reference records are known genotypes and receive neither suffix.

### Sorting

Known and candidate rows use a shared IPD-aware comparator. It parses species, locus, each numeric field, and suffix rather than relying on plain lexical order.

For an identical four-field core, the existing unsuffixed reference sorts before `_EXT` and `_NOV` records. Draft renames immediately trigger re-sorting in Unified.

## CDS Assessment

Database assertion and computed assessment are separate fields for both the naming reference and the candidate.

The computed candidate states are:

**intact**
: Complete start-to-stop CDS, divisible by three, no internal stop, and no frameshifting indel.

**partial_or_indeterminate**
: Missing terminal sequence, uncertain boundary, ambiguous bases, or another condition that prevents a defensible intact or pseudogene call.

**putative_allelic_pseudogene**
: Complete genomic sequence with a supported internal stop or frameshifting change that is not attributable to an uncertain boundary or ambiguous base.

For a putative allelic pseudogene, use `/pseudogene="allelic"`. INSDC explicitly includes MHC haplotypes in the definition of allelic pseudogenes.

Use partial locations for coherent partial CDS features. Use `/pseudo` only for a nonfunctional or nontranslatable feature that is not asserted to be a biological pseudogene, including indeterminate sequence or annotation problems.

An intact CDS includes `/translation` without the terminal stop. A pseudo or pseudogene CDS has no `/translation`.

Exon 8 must be retained whenever it contributes coding sequence or the terminal stop. CDS refinement evaluates the complete joined exon structure rather than assuming that every annotated exon base belongs to the CDS.

### Reference Annotation Inconsistency

The reference file may contain a CDS that is not marked pseudo but fails a strict ORF assessment. This is not collapsed into a single `pseudo_or_disrupted` label.

For example, `NHP11344 / Mafa-AG6*04:17:01:01` is not marked `/pseudo`, while its annotated CDS is 1,096 nt and has internal stops under strict translation. A derived record must say both:

- database assertion: not marked pseudogene; and
- computed assessment: disrupted ORF, with exact evidence.

## Structured Curation Model

Each candidate has an immutable candidate UUID and contains:

- project manifest identifier;
- analysis manifest UUID;
- source reference-bundle identifier and checksum;
- source cluster and support evidence;
- raw and exported sequence state;
- boundary evidence and overrides;
- naming reference and ranked alternate hits;
- annotation template;
- aligned coordinate maps;
- exon, intron, UTR, gene, and CDS features;
- structured substitutions and indels;
- query and reference CDS assessments;
- automated putative name and rationale;
- draft putative name and overrides;
- review status;
- reviewer notes; and
- audit entries.

Review statuses are:

- unreviewed;
- needs_review;
- accepted; and
- rejected.

All candidates remain in the model. Published sequence artifacts include every non-rejected candidate. Only accepted candidates are eligible for reference promotion.

Marking a record accepted requires:

- a valid unique IPD-style provisional name;
- resolved export boundaries;
- confirmed naming reference and annotation template;
- confirmed CDS classification; and
- no blocking feature or variation errors.

## Stable Record Identity

`ACCESSION` is independent of the editable putative allele name.

It has the form:

```text
LGE_P<project-token>_A<analysis-token>_C<candidate-token>
```

Token construction is deterministic:

- project token: first 10 uppercase hexadecimal characters of SHA-256 over the UTF-8 project manifest identifier;
- analysis token: first 10 uppercase hexadecimal characters of the analysis UUID after removing hyphens; and
- candidate token: first 12 uppercase hexadecimal characters of the immutable candidate UUID after removing hyphens.

The candidate UUID is created once from the automated candidate proposal and does not change when export boundaries, features, status, or putative name are edited. Before publication, accessions are collision-checked within the project. A colliding token is lengthened by two hexadecimal characters at a time, up to the full underlying identifier.

Full identifiers and human-readable names are stored in the structured model and `COMMENT`.

`VERSION` appends the published annotation revision number. A name edit does not change accession identity.

`LOCUS`, `DEFINITION`, and `/allele` display the current putative IPD-style name.

## GenBank Record Contract

The internal record follows the shared INSDC feature-table vocabulary.

### Header

```text
LOCUS       MafaAG6_04_18_01_01_NOV 2917 bp DNA linear PRI 09-JUL-2026
DEFINITION  Macaca fascicularis putative MHC class I allele
            Mafa-AG6*04:18:01:01_NOV, genomic sequence.
ACCESSION   LGE_PB4A921E3F0_A38C2D44E1_CB3D09E888352
VERSION     LGE_PB4A921E3F0_A38C2D44E1_CB3D09E888352.1
KEYWORDS    MHC class I; putative allele; full-length ONT; LGE.
```

The source header uses `Macaca fascicularis`, taxon `9541`, and the standard primate taxonomy already used by the reference records.

### Human-Readable Comment

`COMMENT` uses concise sections and whitespace:

```text
LGE MHC ANNOTATION
Putative allele: Mafa-AG6*04:18:01:01_NOV
Review status: unreviewed
Naming reference: Mafa-AG6*04:17:01:01; IPD NHP11344; INSDC HG992369
Naming decision: retained lineage 04; incremented field 2 because exon 5
contains a nonsynonymous Ile-to-Leu change

NAMING EVIDENCE
Exons 2-3: no amino-acid differences
Exon 5: codon 312, ATT->CTT, Ile->Leu
Synonymous: exon 2 codon 26, TCC->TCG, Ser unchanged
Noncoding: six substitutions in introns 2, 4, and 6

ANNOTATION
Template: Mafa-AG6*04:17:01:01; IPD NHP11344
Exported interval: raw bases 1..2917
Terminal trimming: no terminal bases excluded
Query CDS: putative allelic pseudogene; internal stops at codons 340 and 363
Reference CDS: database not marked pseudogene; computed ORF disrupted at
codons 340 and 363

SUPPORT
Samples: PN377; PN377b; PN379; PN379b; PN388; PN388b; PN392; PN392b
Independent sample count: 8
Occurrences: 10
Total cluster reads: 3660

TRACEABILITY
Project identifier: org.lungfish.project.32355
Analysis UUID: 38c2d44e-1e5a-4c1c-9e5e-2f01a1fcb2c9
Candidate UUID: b3d09e88-8352-5d03-86c0-25dbb8c0d99f
Annotation revision: 1
```

Detailed change summaries are grouped by exon in this order: exons 2 and 3, then exons 1, 4, 5, 6, 7, and 8, followed by intron and other noncoding changes.

The comment explains the naming decision. It does not copy the same full rationale into every feature note.

### Features

Every record includes:

- `source` across the exported sequence;
- `gene` across the supported gene interval;
- numbered `exon` features;
- numbered `intron` features where supported;
- UTR features only when supported by annotation or confident alignment;
- joined `CDS` when defensible; and
- one `variation` feature per difference from the naming reference.

`/allele` contains the provisional IPD-style name on `gene`, every `exon`, and `CDS`. Related features share a stable `/locus_tag` based on candidate identity.

The gene note states that the allele name is provisional and not an official IPD-MHC designation. CDS notes are limited to CDS status and evidence. Feature-transfer warnings remain on the affected feature.

### Variation Features

Every `variation` explicitly identifies the base sequence used for comparison:

- naming-reference allele;
- IPD accession;
- public INSDC accession/version when present;
- reference-record checksum in the structured model;
- reference coordinate;
- query coordinate or valid between-base location;
- reference sequence in `/replace`;
- query sequence present in the record;
- exon, intron, or noncoding region;
- codon and amino-acid consequence when coding.

Example:

```text
     variation       231
                     /allele="Mafa-AG6*04:18:01:01_NOV"
                     /replace="A"
                     /note="relative to Mafa-AG6*04:17:01:01 (IPD NHP11344;
                     INSDC HG992369), reference position 231; query G; exon 2;
                     codon 26 TCC->TCG; synonymous, Ser unchanged"
```

`/compare` is not required because the IPD accession may not be a public INSDC accession and current INSDC guidance discourages new use for large-scale variation annotation.

## EMBL Record Contract

EMBL is rendered from the same structured INSDC record model, not converted by reparsing GenBank output.

GenBank and EMBL must preserve equivalent:

- accession and version;
- definition/description;
- source organism and taxonomy;
- comments;
- nucleotide sequence;
- feature keys and locations;
- qualifiers; and
- record order.

Format-specific line wrapping and header syntax may differ, but biological content may not.

## Output Layout And Manifest

When annotated reference records are available, the analysis stores:

```text
artifacts/mhc-annotation/
  current/
    annotation.json
    alleles.fasta
    alleles.gb
    alleles.embl
  revisions/
    <revision-id>/
      annotation.json
      alleles.fasta
      alleles.gb
      alleles.embl
      provenance.json
```

These paths and filenames are the manifest contract. A future schema migration may add alternatives, but schema version 2 readers and writers use these exact members.

The `.lungfishgenotype` manifest gains a backward-compatible optional MHC annotation artifact descriptor containing current paths, revision metadata, status, and failure diagnostics.

GenBank and EMBL appear as separate artifacts in both the genotype viewport's artifact lens and the right Inspector. The structured model and mapping caches are support files rather than primary user-facing artifacts.

Without annotated references, no GenBank or EMBL paths are present.

## Unified Genotype View

The genotype viewport remains the primary workspace. The existing genotype matrix gains an independent row-scope control:

```text
Known | Unified
```

This is separate from the existing Outline/Matrix view choice.

**Known** contains accepted reference genotype calls only.

**Unified** contains Known plus all non-rejected candidate rows from the current draft curation model.

Unified reuses the existing matrix layout, sample columns, column windowing, filters, selection behavior, matrix annotations, and export behavior.

Candidate cell values are per-sample cluster-read support. Percentage denominators in Unified include non-rejected candidate reads. Known retains the original genotype-only denominators.

Candidate rows have immutable internal row IDs and editable display names. Draft changes behave immediately:

- name change: redisplay and IPD-aware re-sort;
- locus change: move to the correct locus;
- rejection: remove from Unified;
- restoration: reinsert into Unified; and
- conflict: retain stable rows, show the conflict, and block publication.

If human boundary edits make two candidate records sequence-identical at the same locus, publication is blocked until the user invokes an explicit merge action. Merge combines support evidence under one surviving stable candidate ID and records the retired candidate ID in the audit history.

Matrix annotations and selection bind to stable candidate IDs, not editable name strings. Existing known-row identities remain backward compatible.

Selecting a known row shows the existing genotype details. Selecting a candidate row opens its curation state in the right Inspector.

## Inspector Interaction

The design uses existing Inspector responsibilities rather than adding a parallel application:

**View**
: Known/Unified row scope, existing matrix filters, and candidate visibility filters.

**Selected Item**
: Candidate navigation, review status, putative name, locus, `_NOV`/`_EXT` class, naming reference, annotation template, naming evidence, CDS status, support, and reviewer notes.

**Annotations**
: Existing persistent matrix comments and styles.

**Build**
: Publish Revision, Retry Annotation, and Create Reference Bundle.

**Provenance**
: Automated analysis, draft audit history, published revisions, workbook synchronization, and reference-bundle lineage.

Previous and next controls traverse the currently filtered candidate review queue. Candidate selection remains synchronized with the Unified matrix.

### Structural Editor

`Edit sequence boundaries and features` opens a sheet with aligned tracks for:

- raw, exported, and excluded terminal sequence;
- naming reference;
- annotation template;
- exons and introns;
- joined CDS and translation;
- variation markers; and
- start, stop, frameshift, and premature-stop warnings.

Users can drag supported boundaries or enter coordinates. Structural edits re-run translation, variation consequences, CDS assessment, and naming validation. Each override can be reset to the automated proposal.

Draft writes complete before Unified is notified. A failed autosave does not leave the viewport showing state that was not persisted.

Read-only bundles expose the evidence and published records but disable curation and publication controls.

## Drafts And Published Revisions

The automated proposal is immutable revision 1 input. Draft overrides autosave separately and record:

- old value;
- new value;
- reviewer identity;
- timestamp;
- optional note; and
- affected candidate and field.

`Publish Revision` performs a cohort-wide transaction:

1. Resolve the complete effective draft model.
2. Revalidate names, boundaries, features, CDS states, and cross-record uniqueness.
3. Stage JSON, FASTA, GenBank, EMBL, and workbook changes.
4. Validate content parity and checksums.
5. Write immutable revision provenance.
6. Atomically update current artifact and workbook pointers.

Failure leaves the previous current revision and workbook untouched.

The original generated workbook remains immutable. Publication updates `artifacts/workbooks/current.xlsx` so its Unified Genotype Pivot uses current putative names and review statuses. The workbook revision records the MHC annotation revision it represents.

## Derived Reference Promotion

`Create Reference Bundle` is a separate scientific publication operation. It never mutates the source reference bundle or the completed genotype analysis.

The user may promote all accepted candidates or a selected subset of accepted candidates.

The derived reference bundle is a complete immutable snapshot containing:

- all original annotated GenBank records;
- selected accepted candidate records;
- canonical combined annotated GenBank;
- deterministic hidden mapping FASTA;
- source-reference ancestry;
- source analysis and annotation revision identity;
- collision-validation report; and
- complete provenance.

The derived bundle can be selected directly for subsequent full-length ONT MHC genotyping.

## Provenance

Every scientific data-producing step must satisfy the Lungfish provenance requirements.

Automated annotation provenance includes:

- workflow and tool names and versions;
- exact argv and reproducible commands;
- user-visible options and resolved defaults;
- app, Swift, minimap2, conda/container, and runtime identity where applicable;
- canonical GenBank and hidden FASTA-cache identities;
- input and output paths, checksums, and sizes;
- sample-support threshold and reference classifications;
- boundary-catalog identity;
- mapping and feature-transfer outputs;
- exit status and wall time; and
- useful stderr and diagnostics.

Draft audit history records human decisions but does not masquerade as a published scientific artifact.

Publication and promotion provenance additionally include:

- project identifier and analysis UUID;
- reviewer identity;
- source and destination revision IDs;
- exact changed fields;
- effective model checksum;
- every staged and final artifact checksum;
- final stored payload paths;
- workbook revision linkage;
- source-reference ancestry; and
- validation results.

GUI actions use the same command identities and service contracts as replayable CLI operations.

## Failure Policy

Invalid annotated reference bundles fail during reference-bundle creation or validation.

Candidate annotation is a post-genotyping phase. If it fails:

- known genotype outputs and deduplicated FASTA remain usable;
- no partial GenBank or EMBL is published;
- failed-step provenance, stderr, and diagnostics are retained;
- the manifest records annotation failure separately from genotype completion; and
- the Inspector offers Retry Annotation without rerunning clustering.

Atomic staging prevents mixed revisions. A publication or workbook failure leaves the previous current revision active.

Duplicate putative names, invalid feature coordinates, cross-format disagreement, missing provenance, and output paths that point only to temporary staging files are blocking defects.

## Validation Gates

Publication requires all of the following:

- every included candidate has at least two independent sample IDs;
- every putative name parses under the agreed IPD hierarchy;
- every putative name is unique within the effective cohort;
- no two unmerged included candidates have the same effective exported sequence at the same locus;
- every `_EXT` has zero differences across the comparable cDNA or partial reference;
- every variation identifies its naming reference and reference sequence;
- feature coordinates are ordered, in range, and strand-consistent;
- exon 8 is included when required by the supported CDS;
- intact translations have no internal stop;
- pseudo, pseudogene, partial, and indeterminate records use appropriate qualifiers;
- GenBank and EMBL have equivalent records, sequences, features, and versions;
- FASTA identifiers match current putative names;
- Unified and `current.xlsx` match the published model;
- rejected records are absent from published sequence artifacts;
- promoted records are accepted; and
- provenance exists with successful final status and final stored paths.

## Testing Strategy

### Unit Tests

- GenBank parsing and writing round trips current IPD-style records.
- EMBL rendering preserves the shared INSDC model.
- Long LOCUS names retain all four allele fields and suffixes.
- IPD allele parsing, punctuation, and sorting are deterministic.
- Closest-reference ranking follows the naming hierarchy.
- Field allocation is anchored to the closest match and unique cohort-wide.
- cDNA and partial genomic extension rules take precedence over `_NOV`.
- Multiple extensions of one reference receive distinct field-4 values.
- Substitutions and indels produce correct variation coordinates and consequences.
- CDS evaluation distinguishes intact, partial/indeterminate, and allelic pseudogene states.
- Database assertion and computed CDS assessment remain separate.
- Boundary evidence and overrides round trip without sequence loss.

### Pipeline Integration Tests

- Two technical replicates satisfy the independent-sample threshold.
- One sample does not satisfy the threshold.
- A perfect cDNA splice match is excluded from Known and included as `_EXT`.
- A perfect partial-genomic match is classified as `_EXT`.
- An exact complete-genomic match remains Known.
- Exon 8 contributes to the longest supported CDS where required.
- Legacy FASTA-only references produce deduplicated FASTA but no GenBank/EMBL.
- Annotation failure preserves genotype outputs and supports retry.
- Cohort minimap2 replaces per-sample BLAST rescue.
- GenBank, EMBL, FASTA, model, and workbook counts and names agree.

### Regression Fixtures

Fixtures include:

- complete seven-exon records;
- complete eight-exon records;
- cDNA records;
- partial genomic records;
- synonymous coding changes;
- nonsynonymous exon 2/3 changes;
- nonsynonymous changes outside exon 2/3;
- intron-only differences;
- substitutions and indels;
- ambiguous termini;
- premature stops and frameshifts;
- multiple genomic extensions of one cDNA; and
- naming collisions.

`NHP11344 / Mafa-AG6*04:17:01:01` is a required regression fixture for reference assertion versus computed ORF status.

### UI Tests

- Known and Unified use the same matrix layout.
- Draft rename updates and re-sorts Unified immediately.
- Draft locus edits move candidate rows.
- Reject and restore remove and reinsert rows.
- Matrix annotations and selection survive candidate renames.
- Candidate selection opens Selected Item curation.
- Known and Unified use their specified percentage denominators.
- Draft autosave failure does not produce unpersisted viewport state.
- Publish Revision updates current artifacts and workbook atomically.
- Create Reference Bundle permits accepted records only.
- Read-only analyses disable edits and publication.

### Provenance Tests

- Hidden FASTA cache derivation is recorded.
- Automated minimap2 steps include exact argv, versions, runtime, stderr, and timings.
- Every final artifact has checksum, size, role, and final path.
- Failed annotation attempts remain inspectable.
- Published revisions record human changes and prior revision identity.
- Workbook synchronization points to the final current workbook.
- Derived reference bundles retain complete base and analysis ancestry.

### Performance Tests

- Candidate sequences are deduplicated before cohort alignment.
- Runtime scales with distinct cohort candidates rather than sample occurrences.
- No per-sample BLAST database or rescue pass is created.
- Annotation retry reuses clustering and durable candidate evidence.
- Candidate comparison uses no more than one cohort minimap2 pass for the genomic partitions and one cohort splice-aware pass for the cDNA partition, independent of the number of sample occurrences.
- The 641-candidate by 2,321-reference regression fixture records wall time and peak resident memory as a checked benchmark; a change exceeding the checked baseline by 25 percent requires an explicit benchmark-baseline update and review.

## Implementation Phases

This design spans several independently reviewable subsystems and should be implemented in four phases.

### Phase 1: Reference And INSDC Foundations

- Annotated MHC reference-bundle schema and validation.
- Hidden GenBank-derived FASTA cache with provenance.
- Extended native INSDC model and GenBank round trip.
- Native EMBL writer and parity validation.

### Phase 2: Candidate Analysis And Initial Artifacts

- Correct known-genotype reference eligibility.
- Shared candidate index and boundary resolution.
- Cohort minimap2 and reciprocal extension detection.
- Closest-anchor naming, annotation transfer, CDS assessment, and variation features.
- Initial structured model, FASTA, GenBank, EMBL, manifest entries, and provenance.

### Phase 3: Unified Matrix And Inspector Curation

- Stable candidate row identities and IPD sorting.
- Known/Unified row scope and denominator behavior.
- Candidate selection bridge to the Inspector.
- Draft model store, review queue, naming controls, structural editor, and audit history.

### Phase 4: Publication And Promotion

- Cohort publication validation and immutable revisions.
- Atomic GenBank/EMBL/FASTA publication.
- `current.xlsx` Unified pivot synchronization.
- Retry Annotation.
- Complete derived-reference bundle promotion.
- Publication and promotion provenance.
