# Full-prefix checkpoint assessment — read-only recommendation

## Recommendation

The three `record_links` prefix-closure joins are mathematically redundant **for a trusted, completely validated current prefix under the documented single-writer API**. A narrowly guarded live-writer fast path is reasonable to implement and independently review. **Do not use count equality alone as the trust condition.** It can skip a corruption rejection that the current joins perform; a tiny synthetic falsification below demonstrates this for both physical formats.

Keep the current slow path for every truncated prefix and, in a first implementation, throughout cold reload/revalidation. Keep all prefix type/range/hash checks, inheritance/completeness checks, dispositions/entity checks, SQLite integrity/FK checks, record identity/canonical-byte/index checks, metadata count checks, FULL synchronization, DELETE journaling, batch1000, and snapshot commit ordering unchanged. No running or frozen source should be patched.

## Why full closure follows under the normal contract

Let E,A,V be current evidence, assessment and event counts. With contiguous validated per-stream ordinals, every evidence ordinal is in[0,E), every assessment in[0,A), every event in[0,V).

1. Normal append validates every assessment→evidence and event→assessment/parent target against its required stream before inserting the source. Targets therefore already exist. New event sequence numbers match the next ordinal; normal autogenerated record positions make references backwards. Successful insertion writes exactly the declared relations, then advances hashes/counts. Duplicate IDs either compare equal without mutation or raise a collision.
2. On successful cold reload, every physical record is decoded and indexed relationships are checked against its declared payload; references must have the correct stream and earlier physical position. Evidence, then assessments, then events are fully validated before the snapshot stream. The final metadata check must also succeed before the instance is exposed as successfully loaded.
3. Consequently, for a snapshot whose three counts equal E,A,V, every declared target is already inside the corresponding complete prefix. There cannot be a valid reference to a target ordinal≥its stream count. The three existence joins must return no rows.
4. This argument is independent of v1 textual versus v2 integer relation storage: canonical relations and stream/ordinal semantics are identical. The v2 compatibility view expands through records, which may make repeated textual joins particularly costly, but does not change the proof.
5. For a truncated evidence or assessment prefix, a valid later target may already exist in current storage but lie outside the snapshot commitment. The joins are still needed. Never optimize one relation merely because its source count is current, or mistake a current hash/count for validation of an arbitrary smaller target prefix.

## Why equality alone is insufficient

### Concrete falsification (executed only in fresh temporary tiny DBs)

For each format1 and2:

1. Append one valid evidence record and one assessment referencing it; checkpoint.
2. Construct an incomplete snapshot with the exact in-memory counts and cached prefix digests.
3. Execute a direct connection mutation changing the evidence record ordinal0→1 without updating in-memory state.
4. Verify the snapshot counts still equal `_counts` and all cached prefix digests still equal the snapshot commitments.
5. The existing `_validate_checkpoint` rejects: **`checkpoint references uncommitted prefix`**. Simply skipping those joins would accept this incomplete snapshot because there are no disposition checks to catch it.

Observed output for both formats: `cached count/hash equal; current validator rejects: checkpoint references uncommitted prefix`. The temporary mutation was rolled back and the temporary directories removed. No native source, tests, frozen worktree, live DB or biological artifact was changed.

This is out-of-band SQL rather than supported scientific API use, but it is an explicit counterexample to the claim that count/hash equality proves disk relations were validated. Similar untrusted changes may arrive through a separate committed connection. Existing cached prefix hashes are not a live disk-integrity audit; the proposed change must not silently broaden that trust boundary.

### Failed rollback/reload

Constructor reload failure closes the connection. In contrast, `rollback()` resets counters/hashes and calls `_reload()` without closing/poisoning the instance if reload raises. A caller that catches the exception could retain an instance with partially reconstructed counts. Those counts do not certify completion of validation. A guard must stay false throughout reload and after any failure; it must become true only after successful final committed-count validation. Failed/cancelled relation insertion followed by a successful rollback is safe because the entire pending batch is discarded and the durable prefix is fully revalidated. A failure during that restoration is not trusted.

### What the original joins do not promise

The existing three joins alone do not detect every arbitrary in-place payload/relation corruption (e.g. a wrong relation entirely within numeric bounds). Full reload does. Do not market the fast path as an integrity check or expand its contract to adversarial mutation; preserve existing cold validation and fail closed when a supposedly trusted writer observes unowned changes.

## Minimal safe implementation contract to review

1. Add a small explicit validity/trust state for the live writer. Start false; clear before reload/rollback and on failures; establish only after successful full reload or successful validated owned append/commit. Closed or poisoned instances cannot claim a trusted prefix. Initially keep all snapshot joins active during `_reload`, even for its final full-prefix snapshot: this preserves the independently reviewed cold oracle and limits the optimization to ordinary live stage completion.
2. Trust must include ownership of mutations, not just a Boolean set after opening. Detect unowned same-connection writes (e.g. a captured SQLite `total_changes` generation updated only after successful owned operations) and external committed writes (connection `PRAGMA data_version` checkpoint guard). On unexpected drift, refuse the shortcut and require full revalidation/fail closed; do not simply bless the new version. The decision and insertion need a stable transaction/one-writer exclusion so a second writer cannot commit between the guard and snapshot insertion. Preserve pending-batch durability semantics; no deadline or synchronization weakening.
3. After all existing hash/prior checks, skip **only** the three closure queries if trust holds and all three snapshot counts equal validated current counts. Otherwise execute the exact existing checks. Dispositions still run normally. No changes to canonical bytes, semantic IDs, schema, committed counts, evidence, snapshot lineage or export order.
4. Prefer one focused change with no CLI knob, schema migration, cached record payload graph or broad SQL rewrites. If robust ownership detection is judged too intrusive, leave the optimization unimplemented rather than silently relying on count equality under a stronger corruption claim.

The suggested generation checks are a design contract, not pre-approved code. Every internal metadata write, rollback and automatic commit must update/invalidate the captured state correctly. At checkpoint frequency these guards are bounded; their real cost still needs measurement. No implementation was performed here.

## Required minimal tests before approval

Run each storage-specific case in **v1 and v2**:

1. Valid full current snapshot with evidence/assessment/event/parent links: compare exact records, snapshot IDs/digests/dispositions/exports with forced-slow behavior; SQL tracing proves only the three joins were skipped. Cover pending batch, automatic batch boundary, empty history and duplicate reuse.
2. Truncated evidence prefix referenced by an included assessment and truncated assessment prefix referenced by an included event: correctly recompute supplied truncated digests and require unchanged rejection. Also valid truncated snapshots still load. Parent chronology/type remains validated; do not let synthetic forward/self parents bypass it.
3. Full-prefix bad digest/type/range, missing/stale disposition, touched inherited entity lacking a fresh disposition, incomplete prior snapshot and decreasing inherited prefix all still reject.
4. Close/reopen corrupted payload, entity/reference index, ordinal, FK and committed-count fixtures still fail cold validation. Assert cold reload never enters the shortcut initially.
5. Inject mid-relation failure and commit failure; successful rollback restores exact durable hashes/counts/IDs and can later take the valid shortcut. Inject reload failure during rollback; trust remains false and subsequent snapshot cannot be committed through the shortcut.
6. The reproduced unowned ordinal mutation, a same-connection reference/index mutation, and an external committed mutation: drift must invalidate trust/refuse the shortcut. Exercise transaction exclusion or a controlled mutation hook at the guard/insertion boundary. Do not weaken the existing tiny v2 insertion-race/fault regressions.

## Expected effect, not a speed claim

The potential gain is removal of three full relation-prefix scans/joins during trusted current-prefix stage completion. It does not accelerate primer enumeration, family expansion, writes, integrity scans, cold reload, truncated-prefix hashing, disposition construction/validation, snapshot serialization or later catalog publication. Those costs can dominate after these joins disappear. The current frozen cold run cannot benefit without prohibited source modification; future sources can only claim a checkpoint improvement after a bounded identical-record/digest benchmark. No seconds, percentage or full-MHC speedup estimate is supported by this assessment.
